Topic 36 — HttpClient & API Integration

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — The basic get/post calls are straightforward, but understanding typed responses, error handling, request configuration, and the interplay with RxJS operators is what separates production-quality HTTP code from tutorial-level code.
Angular Relevance: Critical — Almost every Angular app communicates with a backend. HttpClient is the official Angular mechanism for all HTTP communication. It is RxJS-native, interceptor-aware, and testable by design — understanding it deeply is non-negotiable for professional Angular development.

Section 1 — Explanation
The Postal Service Analogy
Imagine your Angular component is an office worker who needs to send and receive parcels from a warehouse (your API server).
HttpClient is the postal service. You hand it a parcel (a request — URL, method, body, headers) and it delivers the response back to you. You don't manage the trucks, the routing, or the network — that's the postal service's job.
But here's the key: the postal service doesn't hand you the parcel directly. It hands you a tracking slip — an Observable. The parcel (the HTTP response) hasn't arrived yet. You subscribe to the tracking slip, and when the parcel arrives, your callback runs.
This is why HttpClient methods return Observables, not values. The HTTP call hasn't happened yet when the Observable is created — it only starts when something subscribes.
Three important rules about this postal service:

No subscription = no request. The Observable is cold — it only fires when subscribed.
Each subscription = a new request. Subscribing twice sends two HTTP calls.
Unsubscribing = cancelling the parcel. If you unsubscribe before the response arrives, Angular cancels the in-flight request.


Technical Explanation:
HttpClient is an injectable Angular service (@angular/common/http). Every method returns a cold Observable that, when subscribed, fires an HTTP request and emits the response.

Real Angular Service — The correct architecture
typescript// services/user.service.ts
// API calls always live in a service — never directly in a component

import { Injectable, inject } from '@angular/core';
import { HttpClient, HttpParams, HttpErrorResponse } from '@angular/common/http';
import { Observable, throwError } from 'rxjs';
import { map, catchError, retry } from 'rxjs/operators';

// Define the shape of your API responses with interfaces (Topic 13)
export interface User {
  id:        number;
  name:      string;
  email:     string;
  role:      'admin' | 'user';
}

export interface PaginatedResponse<T> {
  data:       T[];
  total:      number;
  page:       number;
  pageSize:   number;
}

@Injectable({ providedIn: 'root' })
export class UserService {
  private http    = inject(HttpClient);
  private baseUrl = 'https://api.example.com';

  // ─── GET: fetch a list with query params ──────────────────────────────────
  getUsers(page: number = 1, pageSize: number = 20): Observable<PaginatedResponse<User>> {
    // HttpParams builds the query string immutably: ?page=1&pageSize=20
    const params = new HttpParams()
      .set('page',     page)
      .set('pageSize', pageSize);

    return this.http
      .get<PaginatedResponse<User>>(`${this.baseUrl}/users`, { params })
      .pipe(
        // Transform if the API shape doesn't match your model
        map(response => ({
          ...response,
          data: response.data.map(u => ({ ...u, name: u.name.trim() }))
        })),
        catchError(this.handleError)
      );
  }

  // ─── GET: fetch a single resource ─────────────────────────────────────────
  getUserById(id: number): Observable<User> {
    return this.http
      .get<User>(`${this.baseUrl}/users/${id}`)
      .pipe(catchError(this.handleError));
  }

  // ─── POST: create a resource ───────────────────────────────────────────────
  createUser(payload: Omit<User, 'id'>): Observable<User> {
    return this.http
      .post<User>(`${this.baseUrl}/users`, payload)
      .pipe(catchError(this.handleError));
  }

  // ─── PUT: full replace ─────────────────────────────────────────────────────
  updateUser(id: number, payload: User): Observable<User> {
    return this.http
      .put<User>(`${this.baseUrl}/users/${id}`, payload)
      .pipe(catchError(this.handleError));
  }

  // ─── PATCH: partial update ─────────────────────────────────────────────────
  patchUser(id: number, changes: Partial<User>): Observable<User> {
    return this.http
      .patch<User>(`${this.baseUrl}/users/${id}`, changes)
      .pipe(catchError(this.handleError));
  }

  // ─── DELETE ────────────────────────────────────────────────────────────────
  deleteUser(id: number): Observable<void> {
    // DELETE often returns no body — type as void
    return this.http
      .delete<void>(`${this.baseUrl}/users/${id}`)
      .pipe(catchError(this.handleError));
  }

  // ─── Centralised error handler ─────────────────────────────────────────────
  private handleError(error: HttpErrorResponse): Observable<never> {
    let userMessage = 'An unexpected error occurred';

    if (error.status === 0) {
      // Network error — the request never reached the server
      userMessage = 'Network error — please check your connection';
    } else if (error.status === 401) {
      userMessage = 'Unauthorised — please log in again';
    } else if (error.status === 404) {
      userMessage = 'Resource not found';
    } else if (error.status >= 500) {
      userMessage = 'Server error — please try again later';
    }

    console.error('HTTP Error:', error);
    // throwError re-throws as an Observable error for downstream catchError handlers
    return throwError(() => new Error(userMessage));
  }
}

Component — Consuming the service with loading and error states
typescript// users-list.component.ts
import { Component, OnInit, inject } from '@angular/core';
import { CommonModule }               from '@angular/common';
import { takeUntilDestroyed }         from '@angular/core/rxjs-interop';
import { UserService, User }          from './services/user.service';

@Component({
  selector: 'app-users-list',
  standalone: true,
  imports: [CommonModule],
  template: `
    @if (loading) {
      <p>Loading users…</p>
    } @else if (error) {
      <p class="error">{{ error }}</p>
      <button (click)="loadUsers()">Retry</button>
    } @else {
      <ul>
        @for (user of users; track user.id) {
          <li>{{ user.name }} — {{ user.email }}</li>
        }
      </ul>
    }
  `
})
export class UsersListComponent implements OnInit {
  private userService = inject(UserService);

  users:   User[]        = [];
  loading: boolean       = false;
  error:   string | null = null;

  ngOnInit(): void {
    this.loadUsers();
  }

  loadUsers(): void {
    this.loading = true;
    this.error   = null;

    this.userService.getUsers()
      .pipe(takeUntilDestroyed()) // ❌ must be in constructor — see Section 7 Bug 1
      .subscribe({
        next:     response  => { this.users = response.data; },
        error:    err       => { this.error = err.message; },
        complete: ()        => { this.loading = false; }
      });
  }
}
typescript// ✅ Correct version — takeUntilDestroyed in constructor
export class UsersListComponent implements OnInit {
  private userService  = inject(UserService);
  private destroyRef   = inject(DestroyRef);

  users:   User[]        = [];
  loading: boolean       = false;
  error:   string | null = null;

  ngOnInit(): void { this.loadUsers(); }

  loadUsers(): void {
    this.loading = true;
    this.error   = null;

    this.userService.getUsers()
      .pipe(takeUntilDestroyed(this.destroyRef)) // ✅ DestroyRef passed explicitly — works anywhere
      .subscribe({
        next:     response => {
          this.users   = response.data;
          this.loading = false;
        },
        error:    err      => {
          this.error   = err.message;
          this.loading = false;
        }
      });
  }
}

Section 4 — Before & After Refactor
❌ Before — HTTP calls directly in the component, untyped, no error handling
typescript// WRONG: everything in the component, nothing typed, no error handling

@Component({ ... })
export class BadComponent implements OnInit {
  private http = inject(HttpClient); // ❌ HttpClient in component — not reusable
  users: any[] = [];                 // ❌ typed as any — loses all type safety

  ngOnInit() {
    // ❌ No error handling — a 404 or 500 silently kills the Observable
    // ❌ No loading state — UI shows stale/empty content with no feedback
    // ❌ No cleanup — if component destroys before response, callback runs on dead component
    this.http.get('https://api.example.com/users').subscribe((data: any) => {
      this.users = data; // ❌ assumes the response is directly an array — fragile
    });
  }
}
What breaks:

API errors crash the component silently — the user sees nothing
No loading state — blank screen until data arrives
Memory leak potential if the component is destroyed mid-flight
The HTTP logic can't be reused in another component — it's locked here
any types mean TypeScript can't catch property name typos or shape mismatches


✅ After — Typed service, error handling, loading state, cleanup
typescript// ✅ HttpClient lives in a service
// ✅ Typed with an interface
// ✅ Error handling via catchError in the service
// ✅ Loading + error state in the component
// ✅ takeUntilDestroyed for cleanup

@Component({ ... })
export class GoodComponent implements OnInit {
  private userService = inject(UserService); // ✅ consume the service

  users:   User[]        = [];
  loading              = false;
  error:   string | null = null;

  ngOnInit() { this.loadUsers(); }

  loadUsers() {
    this.loading = true;
    this.userService.getUsers()
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next:  res => { this.users = res.data; this.loading = false; },
        error: err => { this.error = err.message; this.loading = false; }
      });
  }
}
Why this matters in Angular: The service is the boundary between HTTP concerns and UI concerns. Components shouldn't know about URLs, HTTP verbs, or error codes — they should only know "I asked for users and got them (or got an error)."

Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Not subscribing and wondering why nothing happens
What the mistake is:
typescript// ❌ Observable is created but never subscribed — no HTTP request fires
saveUser() {
  this.userService.createUser(this.formData); // forgot .subscribe()
}
Why developers make it: Coming from Promises, where calling fetch(...) immediately fires the request. With Observables, the call is lazy — it only fires on subscription.
How to avoid it: Always subscribe to HttpClient Observables (or use async pipe / toSignal() to subscribe automatically). If you genuinely want fire-and-forget, you still need .subscribe() — just with an empty observer or error handler.
Angular-specific consequence: The API call silently never happens. No error, no feedback. This is the most common "my form submission does nothing" bug.

Mistake 2 — Putting HttpClient calls directly in components
What the mistake is: Injecting HttpClient into a component and calling this.http.get(...) directly inside it.
Why developers make it: It's faster — fewer files, fewer injections. Tutorials often do this to keep examples short.
How to avoid it: Always create a dedicated service for each API domain (e.g. UserService, ProductService). Inject HttpClient only in services.
Angular-specific consequence: The HTTP logic is locked to one component — you can't reuse it, can't mock it in tests with HttpClientTestingModule, and can't add interceptors cleanly. At scale, you end up with duplicated API logic across multiple components.

Mistake 3 — Ignoring the error callback in .subscribe()
What the mistake is:
typescript// ❌ No error handler — Observable errors go unhandled
this.userService.getUsers().subscribe(data => {
  this.users = data.users;
});
// If the API returns 404/500, nothing happens — the Observable just dies
Why developers make it: The happy path works in development where APIs are stable. Error handling feels optional.
How to avoid it: Always provide an error callback in .subscribe({ next, error }) or add .pipe(catchError(...)) in the service. At minimum, log the error and set a user-facing error state.
Angular-specific consequence: In production, API failures leave the component in a permanent loading or empty state. The user has no way to know what happened or retry.

Section 7 — Debugging Tips
Bug 1 — takeUntilDestroyed() called outside injection context
Symptom: Error: takeUntilDestroyed() can only be used within an injection context thrown when loadUsers() is called from ngOnInit.
Plain English cause: takeUntilDestroyed() without an argument relies on Angular's injection context to grab DestroyRef automatically. That context only exists during construction. Calling it inside ngOnInit or a method is outside that window.
Fix:
typescript// ✅ Inject DestroyRef explicitly — then use it anywhere
private destroyRef = inject(DestroyRef);

loadUsers() {
  this.userService.getUsers()
    .pipe(takeUntilDestroyed(this.destroyRef)) // works in any method
    .subscribe(...);
}
Angular-specific note: The explicit DestroyRef injection pattern is the correct solution for HTTP calls triggered from methods, event handlers, or ngOnInit. Reserve the no-argument form for constructor-level or field-initializer subscriptions.

Bug 2 — Response is undefined or missing properties at runtime
Symptom: Cannot read properties of undefined (reading 'name') — the response object exists but the shape doesn't match the interface.
Plain English cause: The <T> generic in http.get<T>() is a TypeScript compile-time cast — Angular does not validate the actual response against it at runtime. If the API returns { user: { name: 'John' } } but you typed it as User (expecting { name: 'John' } directly), TypeScript is satisfied at compile time but the runtime shape is wrong.
Fix:
typescript// ❌ API returns { user: {...} } but you typed it as User directly
http.get<User>('/api/me').subscribe(u => console.log(u.name)); // undefined

// ✅ Type the wrapper correctly and destructure
interface MeResponse { user: User; }
http.get<MeResponse>('/api/me').pipe(
  map(res => res.user) // extract the inner object
).subscribe(u => console.log(u.name)); // ✅ works
Angular-specific note: When the API shape and your model shape diverge, always use map() in the service to transform the response before it reaches the component — components should never know about API envelope wrappers.

Bug 3 — CORS error blocking requests in development
Symptom: Browser console shows Access to XMLHttpRequest has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header.
Plain English cause: The browser (not Angular) blocks cross-origin requests when the server doesn't include the correct CORS headers. This is a server-side or proxy configuration issue — not an Angular bug.
Fix (development): Use Angular's dev server proxy to route API calls through the same origin:
json// proxy.conf.json
{
  "/api": {
    "target": "https://api.example.com",
    "changeOrigin": true,
    "pathRewrite": { "^/api": "" }
  }
}
json// angular.json — under serve > options
"proxyConfig": "proxy.conf.json"
typescript// Now use relative URLs in development — proxy handles the routing
http.get('/api/users') // → proxied to https://api.example.com/users
Angular-specific note: The proxy fix is for development only. In production, CORS must be configured on the server or handled via an API gateway. Never ship a dev proxy config as a production fix.

Section 8 — Real-World Applications
Scenario 1 — Search with Debounce and Request Cancellation
A search box calls an API on every keystroke. Using switchMap ensures that if the user types quickly, only the most recent request completes — older in-flight requests are cancelled automatically.
typescript// search.component.ts
@Component({
  selector: 'app-search',
  standalone: true,
  imports: [ReactiveFormsModule, CommonModule],
  template: `
    <input [formControl]="searchControl" placeholder="Search users…" />
    @if (loading) { <span>Searching…</span> }
    <ul>
      @for (user of results; track user.id) {
        <li>{{ user.name }}</li>
      }
    </ul>
    @if (error) { <p class="error">{{ error }}</p> }
  `
})
export class SearchComponent {
  private userService = inject(UserService);

  searchControl = new FormControl('');
  results: User[] = [];
  loading = false;
  error: string | null = null;

  constructor() {
    this.searchControl.valueChanges.pipe(
      debounceTime(300),             // wait 300ms after last keystroke
      distinctUntilChanged(),        // skip if value hasn't changed
      filter(term => (term?.length ?? 0) >= 2), // skip short queries
      tap(() => { this.loading = true; this.error = null; }),
      switchMap(term =>              // cancel previous request, start new one
        this.userService.searchUsers(term ?? '').pipe(
          catchError(err => {
            this.error = err.message;
            return of([]);           // recover — don't kill the outer stream
          })
        )
      ),
      takeUntilDestroyed()
    ).subscribe(results => {
      this.results = results;
      this.loading = false;
    });
  }
}

Scenario 2 — Parallel API Calls with forkJoin
A dashboard page needs to load a user profile, their recent orders, and their notifications simultaneously — not sequentially. forkJoin fires all three requests in parallel and emits once when all complete.
typescript// dashboard.service.ts
import { forkJoin, Observable } from 'rxjs';
import { map } from 'rxjs/operators';

export interface DashboardData {
  user:          User;
  orders:        Order[];
  notifications: Notification[];
}

@Injectable({ providedIn: 'root' })
export class DashboardService {
  private http = inject(HttpClient);

  loadDashboard(userId: number): Observable<DashboardData> {
    // forkJoin fires all three simultaneously — completes when ALL three complete
    return forkJoin({
      user:          this.http.get<User>(`/api/users/${userId}`),
      orders:        this.http.get<Order[]>(`/api/users/${userId}/orders`),
      notifications: this.http.get<Notification[]>(`/api/users/${userId}/notifications`)
    }).pipe(
      map(({ user, orders, notifications }) => ({ user, orders, notifications }))
    );
    // ⚠️ forkJoin cancels all if ANY observable errors — add catchError per source
    // for resilience if some calls are non-critical
  }
}

// dashboard.component.ts
export class DashboardComponent implements OnInit {
  private dashboardService = inject(DashboardService);
  private destroyRef       = inject(DestroyRef);

  data:    DashboardData | null = null;
  loading = true;
  error:   string | null        = null;

  ngOnInit() {
    this.dashboardService.loadDashboard(42)
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next:  data => { this.data = data; this.loading = false; },
        error: err  => { this.error = err.message; this.loading = false; }
      });
  }
}

Section 10 — Key Takeaways
Core concepts in plain English:

HttpClient is an injectable service that returns cold Observables — no request fires until subscription
Each subscription to an HttpClient Observable fires one independent HTTP request
http.get<T>() — the <T> is a compile-time type hint, not a runtime validator
Always put HttpClient in services, never in components
HttpParams builds query strings immutably — never concatenate query strings manually
catchError in the service handles HTTP errors before they reach the component
takeUntilDestroyed(destroyRef) cleans up component subscriptions when the component destroys

Section 11 — Thought-Provoking Question + Answer
Question: HttpClient returns Observables, but many developers use firstValueFrom() to convert them to Promises and then use async/await. Is this a legitimate pattern, or an anti-pattern in Angular?
Answer:
Conceptual explanation: It's a legitimate pattern in specific contexts — but it trades away Observable superpowers for syntactic convenience. The trade-offs are real:
firstValueFrom(http.get<T>(url)) converts the Observable to a Promise that resolves with the first emitted value. You can then await it. This is clean, readable, and familiar to developers coming from a Promise background.
What you lose:

Cancellation. Promises can't be cancelled. If the component destroys mid-await, the request completes and the .then() / await continuation still runs — potentially on a destroyed component. Observables can be cancelled by unsubscribing (e.g. via takeUntilDestroyed).
Composability. You can't pipe debounceTime, switchMap, or retry onto a Promise.
Multiple emissions. Not relevant for HTTP (which emits once), but matters if you ever switch to a WebSocket or SSE stream.

Angular-specific implication: firstValueFrom is fine in two specific situations:

Services resolving data for Route Resolvers — where the resolver expects a Promise
One-shot operations in non-reactive contexts — e.g. an async method in a CanActivate guard

It is an anti-pattern when used as a wholesale replacement for the Observable pattern in components, because it gives up cancellation — the single most important property of HTTP Observables in Angular.
Practical rule: Default to Observables with takeUntilDestroyed. Reach for firstValueFrom only when the calling context genuinely expects a Promise (resolvers, guards) or when the operation is truly fire-and-forget with no cancellation concern.

Section 14 — Common Interview Questions
Question 1:

"Why does Angular's HttpClient return an Observable instead of a Promise, and what practical advantages does that give you?"
Strong answer covers:

Observables are lazy — no request fires until subscription; Promises execute immediately on creation
Observables are cancellable — unsubscribing cancels the in-flight request; Promises cannot be cancelled
Observables are composable — pipe(debounceTime, switchMap, retry, catchError) chains are impossible with Promises
switchMap enables automatic cancellation of previous requests when new ones arrive — critical for search
One Observable can emit multiple times (WebSockets, SSE) — Promises only resolve once
takeUntilDestroyed can clean up HTTP subscriptions automatically when a component destroys

Weak answer misses: The cancellation point — most candidates mention composability but miss that unsubscribing from an HttpClient Observable actually cancels the XHR request in the browser, not just ignores the response.
Difficulty: Mid

Question 2:

"In a search input that calls an API on every keystroke, how would you prevent excessive API calls and handle out-of-order responses?"
Strong answer covers:

debounceTime(300) — waits 300ms after the last keystroke before emitting
distinctUntilChanged() — skips emission if the value hasn't changed
switchMap — cancels the previous in-flight request when a new value arrives; only the latest request's response reaches the subscriber
filter — skips very short queries (e.g. less than 2 characters)
Why mergeMap would be wrong here — it doesn't cancel, so out-of-order responses cause race conditions

Weak answer misses: The distinction between switchMap and mergeMap — and specifically that switchMap cancels the previous Observable, which is what prevents stale responses from rendering.
Difficulty: Mid–Senior

Question 3:

"How do you handle HTTP errors in Angular, and where in the architecture should error handling live?"
Strong answer covers:

Two layers: catchError in the service (translates HTTP errors to domain errors), error callback in the component (updates UI state)
HttpErrorResponse has status (numeric code), message, error (body), and status === 0 for network errors
throwError(() => new Error(message)) re-throws as an Observable error for downstream handlers
The service should never expose raw HttpErrorResponse to the component — translate to user-facing messages
Global errors can be caught in an HTTP Interceptor (Topic 37) for cross-cutting concerns like 401 redirect to login

Weak answer misses: The two-layer architecture — service translates, component displays. Candidates who only mention one layer miss the separation of concerns that makes Angular code maintainable.
Difficulty: Mid–Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Nested subscriptions (subscribe inside subscribe)
typescript// ❌ Anti-pattern: nested subscribes for sequential HTTP calls
this.userService.getCurrentUser().subscribe(user => {
  this.orderService.getOrders(user.id).subscribe(orders => {
    this.notificationService.getNotifications(user.id).subscribe(notifications => {
      this.data = { user, orders, notifications };
    });
  });
});
Why it seems fine: It's sequential and readable. Works on the happy path.
What breaks in production: Three nested subscriptions with three separate cleanup requirements. If any middle Observable errors, the outer subscriptions keep running. No single place to handle errors. Classic "callback hell" — except with Observables. Adding a fourth step means another level of nesting.
Correct pattern:
typescript// ✅ Use switchMap for sequential, forkJoin for parallel
this.userService.getCurrentUser().pipe(
  switchMap(user =>
    forkJoin({
      orders:        this.orderService.getOrders(user.id),
      notifications: this.notificationService.getNotifications(user.id)
    }).pipe(map(rest => ({ user, ...rest })))
  ),
  takeUntilDestroyed(this.destroyRef),
  catchError(err => { this.error = err.message; return EMPTY; })
).subscribe(data => this.data = data);

Anti-Pattern 2 — Not providing provideHttpClient() and wondering why injection fails
typescript// ❌ Anti-pattern: forgetting to provide HttpClient in standalone app config
// app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes)
    // Missing: provideHttpClient()
  ]
};

// Somewhere in a service:
private http = inject(HttpClient); // ✅ code is correct
// But at runtime: NullInjectorError: No provider for HttpClient!
Why it seems fine: The service code is correct. The error message points to the service, not the config, so developers look in the wrong place.
What breaks in production: Every service that injects HttpClient throws NullInjectorError at runtime. The entire app fails to load if HttpClient is injected at startup.
Correct pattern:
typescript// app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(              // ✅ required in standalone apps
      withInterceptorsFromDi()      // optional: enables DI-based interceptors (Topic 37)
    )
  ]
};

Anti-Pattern 3 — Using mergeMap instead of switchMap for user-triggered searches
typescript// ❌ Anti-pattern: mergeMap for search
this.searchControl.valueChanges.pipe(
  debounceTime(300),
  mergeMap(term => this.userService.search(term)) // mergeMap: keeps ALL in-flight requests
).subscribe(results => this.results = results);
Why it seems fine: mergeMap flattens Observables just like switchMap. Most developers learn them together and don't always distinguish when each applies.
What breaks in production: If the user types "ang" then "angu" quickly, two requests fire. If the "ang" response arrives after the "angu" response (slower server, network variance), the results display "ang" results even though the user typed "angu". The UI shows stale data with no indication anything is wrong. This is a race condition — subtle, intermittent, and hard to reproduce.
Correct pattern:
typescript// ✅ switchMap: cancels the previous request when a new one arrives
this.searchControl.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.userService.search(term)) // previous request cancelled automatically
).subscribe(results => this.results = results);

Section 16 — Mental Model Summary
Core concept in one sentence:

HttpClient is an injectable service that wraps every HTTP request as a cold Observable — nothing fires until subscription, everything should be typed, all errors should be caught in the service layer, and all component subscriptions need cleanup.
Key rules:

HttpClient belongs in services — never inject it directly into components.
Cold Observable = no request until .subscribe() — this is the most common beginner trap.
Always type responses: http.get<User[]>(url) — any destroys type safety.
catchError in the service translates HTTP errors; the error callback in the component updates UI.
Use switchMap for user-triggered searches — it cancels stale in-flight requests automatically.
Use takeUntilDestroyed(destroyRef) for all component HTTP subscriptions.

The single most important Angular rule:

Put HttpClient in a service, type every response with an interface, catch errors with catchError, and clean up with takeUntilDestroyed(destroyRef) — every omission of these four is a production bug waiting to happen.
