

Topic 40 — Lazy Loading & Route-Based Code Splitting

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — The configuration is concise, but understanding why it works requires grasping how JavaScript module bundling, the browser's network loading model, and Angular's dependency injection system all interact at the route boundary.
Angular Relevance: Critical — Every production Angular app with more than a handful of routes should use lazy loading; it is the single highest-impact performance optimisation available at the architectural level, and Angular's Router makes it nearly free to implement.

Section 1 — Explanation
The Library Branch Analogy
Imagine a large public library system with a central branch and several specialist branches (law, medicine, science, children's).
Without lazy loading: Every time anyone walks into the central library, staff wheel out every book from every branch and stack them in the lobby — law books, medical textbooks, children's picture books, all of it — just in case someone might ask for them. The lobby is packed, nobody can move, and the first patron to arrive waits 3 minutes before they can even ask a question.
With lazy loading: The central library keeps only its own books in the lobby. The specialist branches stay at their own locations. When a patron specifically asks for a law book, a courier is dispatched to the law branch, retrieves just what's needed, and brings it back. First patrons arrive instantly. People who never need the law section never pay the cost of fetching those books.
In Angular terms:

The central library is your initial JavaScript bundle — everything loaded on first visit
Each specialist branch is a feature area (admin panel, settings, reports)
The courier dispatch is loadComponent / loadChildren in your route config
The books arriving are JavaScript chunk files downloaded on demand from your server


Technical Explanation
When you build an Angular app, the compiler bundles your TypeScript into JavaScript files. Without lazy loading, everything goes into one main.js bundle — every component, every service, every dependency. The browser must download and parse all of it before the app becomes interactive.
Lazy loading tells the bundler (Webpack or esbuild): "This component/module is only needed when the user navigates to this route — put it in a separate chunk file." The browser downloads that chunk only when the route is first visited.
Two modern approaches in Angular 17+:
loadComponent  →  lazily loads a single standalone component
loadChildren   →  lazily loads an entire routes file (feature routes)
Both use the dynamic import() syntax — a standard JavaScript feature that tells the bundler to split at that boundary.
What happens at runtime:

User visits / — browser downloads main.js only
User navigates to /admin — Router sees loadComponent, triggers dynamic import()
Browser downloads admin-dashboard-HASH.js chunk
Router instantiates AdminDashboardComponent inside <router-outlet>
All subsequent /admin/* navigations use the already-cached chunk

The chunk is downloaded once then cached — second visit to /admin is instant.

Section 3 — Code Example
Plain JS — Dynamic import in isolation (the underlying mechanism)
javascript// Static import — loaded immediately, part of the main bundle
import { AdminDashboard } from './admin-dashboard';

// Dynamic import — returns a Promise, loaded on demand
// This is standard JavaScript (ES2020) — Angular's lazy loading is built on this
async function loadAdminWhenNeeded() {
  // import() is only called when this function runs
  const module = await import('./admin-dashboard');
  // module.AdminDashboard is now available
  return module.AdminDashboard;
}

// The bundler sees the dynamic import() and creates a separate chunk file
// That chunk is only downloaded when loadAdminWhenNeeded() is called

Real Angular — loadComponent (single standalone component)
typescript// app.routes.ts
import { Routes } from '@angular/router';
import { HomeComponent } from './home/home.component'; // eager — in main bundle
import { authGuard } from './guards/auth.guard';

export const APP_ROUTES: Routes = [
  // Eager route — HomeComponent included in main.js (fast first load)
  { path: 'home', component: HomeComponent },

  // Lazy route — AdminDashboardComponent in its own chunk
  // The () => import(...) is NOT called until the user navigates here
  {
    path: 'admin',
    loadComponent: () =>
      import('./admin/admin-dashboard.component')
        .then(m => m.AdminDashboardComponent),
    canActivate: [authGuard], // guard runs BEFORE the chunk is downloaded
  },

  // Lazy route with inline default export (simpler .then())
  {
    path: 'settings',
    loadComponent: () => import('./settings/settings.component'),
    // Works when the component is the default export of the file
  },

  { path: '', redirectTo: 'home', pathMatch: 'full' },
  { path: '**', loadComponent: () => import('./not-found.component') },
];

Real Angular — loadChildren (entire feature section)
typescript// app.routes.ts — root routes
export const APP_ROUTES: Routes = [
  { path: 'home', component: HomeComponent },

  // Entire /users feature section is lazy
  // users.routes.ts and ALL its components are in a separate chunk
  {
    path: 'users',
    loadChildren: () =>
      import('./users/users.routes')
        .then(m => m.USERS_ROUTES),
    canActivate: [authGuard],
  },

  { path: '', redirectTo: 'home', pathMatch: 'full' },
];
typescript// users/users.routes.ts — feature routes file
import { Routes } from '@angular/router';

// This entire file (and everything it imports) becomes a separate JS chunk
export const USERS_ROUTES: Routes = [
  {
    path: '',                           // matches /users exactly
    loadComponent: () =>
      import('./user-list.component').then(m => m.UserListComponent),
  },
  {
    path: ':id',                        // matches /users/42
    loadComponent: () =>
      import('./user-detail.component').then(m => m.UserDetailComponent),
  },
  {
    path: ':id/edit',                   // matches /users/42/edit
    loadComponent: () =>
      import('./user-edit.component').then(m => m.UserEditComponent),
    canDeactivate: [unsavedChangesGuard],
  },
];
typescript// app.config.ts — registering routes
import { ApplicationConfig } from '@angular/core';
import { provideRouter, withPreloading, PreloadAllModules } from '@angular/router';
import { APP_ROUTES } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(
      APP_ROUTES,
      // Optional: silently preload lazy chunks after initial load completes
      // User gets instant navigation to lazy routes after ~2s
      withPreloading(PreloadAllModules),
    ),
  ],
};

Real Angular — Lazy-loaded service scoping
typescript// users/users.routes.ts
import { Routes } from '@angular/router';
import { UserStateService } from './user-state.service';

export const USERS_ROUTES: Routes = [
  {
    path: '',
    // providers array on a route creates a SCOPED DI context
    // UserStateService here is a different instance from any root-level service
    providers: [UserStateService],
    children: [
      { path: '', loadComponent: () => import('./user-list.component').then(m => m.UserListComponent) },
      { path: ':id', loadComponent: () => import('./user-detail.component').then(m => m.UserDetailComponent) },
    ],
  },
];

Section 4 — Before & After Refactor
❌ Before — Everything eager, one giant bundle
typescript// app.routes.ts — all components imported statically at the top
import { HomeComponent } from './home/home.component';
import { AdminDashboardComponent } from './admin/admin-dashboard.component';
import { AdminUsersComponent } from './admin/admin-users.component';
import { AdminReportsComponent } from './admin/admin-reports.component';
import { SettingsComponent } from './settings/settings.component';
import { UserListComponent } from './users/user-list.component';
import { UserDetailComponent } from './users/user-detail.component';
// ...20 more imports

export const APP_ROUTES: Routes = [
  { path: 'home', component: HomeComponent },
  { path: 'admin', component: AdminDashboardComponent },
  { path: 'admin/users', component: AdminUsersComponent },
  { path: 'admin/reports', component: AdminReportsComponent },
  { path: 'settings', component: SettingsComponent },
  { path: 'users', component: UserListComponent },
  { path: 'users/:id', component: UserDetailComponent },
];
What breaks: Every component is statically imported at the top of app.routes.ts. The bundler sees these imports and includes all component code in main.js. A user visiting only the home page downloads the entire admin panel — all its templates, logic, and dependencies — immediately. On a slow 3G connection, this adds seconds to first load.

✅ After — Feature sections lazy-loaded
typescript// app.routes.ts — no static imports of feature components
// Only shell/home components are imported eagerly
import { HomeComponent } from './home/home.component';

export const APP_ROUTES: Routes = [
  { path: 'home', component: HomeComponent }, // eagerly loaded — small, needed immediately

  {
    path: 'admin',
    canActivate: [authGuard],
    loadChildren: () =>
      import('./admin/admin.routes').then(m => m.ADMIN_ROUTES),
    // admin bundle: ~0kb in main.js, downloaded only if user navigates to /admin
  },

  {
    path: 'users',
    loadChildren: () =>
      import('./users/users.routes').then(m => m.USERS_ROUTES),
  },

  {
    path: 'settings',
    loadComponent: () => import('./settings/settings.component'),
  },
];
Why this refactor matters in Angular: The Angular compiler uses static import analysis to build the bundle. Replacing import { X } from './x' at the top of the file with () => import('./x') inside a route config is the signal that tells the bundler to split at that boundary. The change is minimal — but the impact on initial load time in large apps is significant. Angular's build output will show separate chunk files for each lazy route.

Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Statically importing the component AND using loadComponent
The mistakeimport { AdminComponent } from './admin.component' at the top of the file, then loadComponent: () => import('./admin.component').then(m => m.AdminComponent) in the routeWhy developers make itIDE auto-import adds the static import; the developer doesn't notice and also adds the lazy routeHow to avoid itIf you use loadComponent or loadChildren, there must be NO static import of those components at the top of app.routes.ts. Remove any auto-added imports immediatelyAngular consequenceThe static import causes the bundler to include the component in main.js anyway — the loadComponent call still works but the lazy split never happens. Zero performance benefit, no error, no warning

Mistake 2 — Providing a service in both root and a lazy route's providers array
The mistake@Injectable({ providedIn: 'root' }) on a service that is also listed in a lazy route's providers: [MyService]Why developers make itDevelopers add providers to the route for scoping without removing providedIn: 'root' from the service decoratorHow to avoid itChoose one: either providedIn: 'root' (one singleton for the whole app) or providers: [MyService] on the route (scoped instance). Never bothAngular consequenceTwo instances of the service exist simultaneously — the root instance and the route-scoped instance. Components in the lazy route get the scoped instance; components outside it get the root instance. State updates in one are invisible to the other — extremely hard to debug

Mistake 3 — Assuming lazy-loaded components are re-downloaded on every navigation
The mistakeAdding artificial caching logic or worrying about performance on repeated visits to a lazy routeWhy developers make it"Lazy" sounds like "slow every time" — developers assume the chunk is re-fetched each visitHow to avoid itUnderstand that dynamic import() is cached by the browser (and the JavaScript module registry) after the first download. Second navigation to a lazy route is as fast as an eager routeAngular consequenceUnnecessary complexity — cache-busting logic, service workers configured to avoid lazy chunks, manual preloading of already-cached chunks. Wasted dev time and potential bugs

Section 7 — Debugging Tips
Bug 1 — Lazy route navigates but shows a blank <router-outlet> with no error
Symptom: Navigation to /admin changes the URL, no console errors, but the outlet is empty.
Plain English cause: The loadChildren path resolves correctly but the exported Routes constant name in the .then(m => m.X_ROUTES) call doesn't match the actual export name in the routes file.
Fix:
typescript// users.routes.ts — check the actual export name
export const USERS_ROUTES: Routes = [...]; // ← what is it actually called?

// app.routes.ts — .then() must use the exact same name
loadChildren: () =>
  import('./users/users.routes').then(m => m.USERS_ROUTES) // ← must match
Angular-specific note: TypeScript will catch this if you have strict type checking enabled and use .then(m => m.USERS_ROUTES) — m.USERS_ROUTES will be undefined (not a type error by default since module exports are typed as any). Add // @ts-check or use satisfies Routes on the export to surface this at compile time.

Bug 2 — Lazy chunk is included in main.js instead of a separate file
Symptom: Angular build output shows no separate chunk files. main.js size is the same as before adding lazy routes.
Plain English cause: A static import of the component exists somewhere in a file that is part of the eager bundle — most commonly an auto-added import at the top of app.routes.ts added by the IDE.
Fix:
typescript// ❌ This static import pulls AdminDashboardComponent into main.js
import { AdminDashboardComponent } from './admin/admin-dashboard.component';

// ✅ Remove the static import — loadComponent handles it
// No import statement for AdminDashboardComponent at the top of this file
{
  path: 'admin',
  loadComponent: () =>
    import('./admin/admin-dashboard.component')
      .then(m => m.AdminDashboardComponent),
}
Angular-specific note: Run ng build --stats-json and open the output with webpack-bundle-analyzer (or use source-map-explorer) to visually confirm which components are in which chunks. This is the definitive way to verify lazy splitting is actually working.

Bug 3 — NullInjectorError for a service inside a lazy-loaded component
Symptom: NullInjectorError: No provider for UserStateService appears when navigating to a lazy route, even though the service exists.
Plain English cause: The service is provided in the lazy route's providers array but the component is accessing it via a parent injector that doesn't have it (e.g., the component is in a different lazy module than where the service is provided).
Fix:
typescript// Option 1: provide the service at root level if it's needed broadly
@Injectable({ providedIn: 'root' })
export class UserStateService { ... }

// Option 2: ensure the component consuming the service is inside the
// route subtree that provides it
export const USERS_ROUTES: Routes = [{
  path: '',
  providers: [UserStateService], // provided here
  children: [
    // UserStateService is available to ALL children in this subtree
    { path: '', loadComponent: () => import('./user-list.component')... },
    { path: ':id', loadComponent: () => import('./user-detail.component')... },
  ]
}];
Angular-specific note: Angular's DI walks the injector tree upward — if the service isn't found in the component's route injector or any parent, it throws. Route-level providers create an environment injector scoped to that route subtree. Components outside that subtree cannot access it.

Section 8 — Real-World Applications
Scenario 1 — Admin portal with auth-gated lazy loading (Angular-specific)
A SaaS platform with a public marketing section and a protected admin portal. 95% of visitors are unauthenticated users who never need admin code. The admin panel is large (reports, user management, billing, settings) and its JavaScript should never be downloaded by non-admin users.
typescript// app.routes.ts
export const APP_ROUTES: Routes = [
  // Eagerly loaded — needed by everyone immediately
  { path: '', component: LandingPageComponent },
  { path: 'login', component: LoginComponent },
  { path: 'pricing', component: PricingComponent },

  // Admin section — gated by auth, entire bundle deferred
  {
    path: 'app',
    canActivate: [authGuard],          // 1. Check auth FIRST — if blocked,
    loadChildren: () =>                //    chunk is never downloaded
      import('./portal/portal.routes')
        .then(m => m.PORTAL_ROUTES),   // 2. THEN download the portal chunk
  },

  { path: '**', loadComponent: () => import('./not-found.component') },
];
typescript// portal/portal.routes.ts — entire portal is one lazy chunk boundary
export const PORTAL_ROUTES: Routes = [
  {
    path: '',
    component: PortalShellComponent,   // shell is eager within the portal chunk
    children: [
      { path: 'dashboard', loadComponent: () => import('./dashboard/dashboard.component')... },
      { path: 'users', loadChildren: () => import('./users/users.routes').then(m => m.USERS_ROUTES) },
      { path: 'billing', loadChildren: () => import('./billing/billing.routes').then(m => m.BILLING_ROUTES) },
      { path: 'reports', loadChildren: () => import('./reports/reports.routes').then(m => m.REPORTS_ROUTES) },
      { path: '', redirectTo: 'dashboard', pathMatch: 'full' },
    ],
  },
];
Result: Unauthenticated users download main.js + landing page assets only. The entire portal JS is never fetched. Authenticated users download the portal shell on first login, then individual section chunks on demand.

Scenario 2 — Preloading strategy for a content site (Angular-specific)
A news website where the home page loads fast and the article pages are lazy-loaded. Articles are the most-visited pages so we want them preloaded silently after the home page finishes loading — ensuring instant navigation when a user clicks a headline.
typescript// app.config.ts — custom preloading strategy
import {
  provideRouter,
  withPreloading,
  PreloadingStrategy,
  Route,
} from '@angular/router';
import { Injectable } from '@angular/core';
import { Observable, of, timer } from 'rxjs';
import { switchMap } from 'rxjs/operators';

// Custom strategy: only preload routes marked with data.preload = true
@Injectable({ providedIn: 'root' })
export class SelectivePreloadingStrategy implements PreloadingStrategy {
  preload(route: Route, load: () => Observable<unknown>): Observable<unknown> {
    if (route.data?.['preload'] === true) {
      // Delay preloading by 2s so it doesn't compete with initial render
      return timer(2000).pipe(switchMap(() => load()));
    }
    return of(null); // don't preload this route
  }
}

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(
      APP_ROUTES,
      withPreloading(SelectivePreloadingStrategy), // use custom strategy
    ),
  ],
};
typescript// app.routes.ts — mark high-traffic routes for preloading
export const APP_ROUTES: Routes = [
  { path: 'home', component: HomeComponent },

  {
    path: 'articles',
    loadChildren: () => import('./articles/articles.routes').then(m => m.ARTICLES_ROUTES),
    data: { preload: true }, // ← flagged for preloading after initial load
  },

  {
    path: 'admin',
    loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES),
    data: { preload: false }, // ← admin only visited by small % — don't preload
    canActivate: [authGuard],
  },
];

Section 10 — Key Takeaways
Core concepts in plain English:

Lazy loading splits your app into separate JS chunk files that are downloaded only when needed
loadComponent lazily loads one component; loadChildren lazily loads an entire routes file
The mechanism is standard JavaScript dynamic import() — Angular's Router exploits module boundaries
Guards run before chunks are downloaded — unauthorized users never download protected code
Preloading silently fetches lazy chunks after initial load — combining fast first load with instant subsequent navigation
A static import at the top of your routes file defeats lazy splitting entirely

Section 11 — Thought-Provoking Question + Answer
Question: If lazy loading improves initial load time by deferring chunks, but preloading fetches those chunks shortly after anyway — are they not just achieving the same result with extra steps? What is the actual user experience difference?
Answer:
Conceptual explanation: They achieve the same final state (all chunks downloaded) but at completely different times relative to user interaction. The distinction is the critical path — what must complete before the user can interact with the app.
Without lazy loading: download main.js (large) → parse → render → interactive

With lazy loading + preloading: download main.js (small) → parse → render → interactive → (background) download other chunks
The user reaches "interactive" in the first scenario only after the full large bundle parses. In the second, they reach "interactive" after the small bundle, and the other chunks arrive silently in the background — they're ready before the user navigates to them.
The Angular-specific implication: On a modern broadband connection the difference may be 200ms — imperceptible. On a 3G mobile connection with 800ms latency, the difference between a 2MB main.js and a 200KB main.js is 5-6 seconds of blank screen versus a functional app. This is why lazy loading matters: not for developers on fast connections, but for users on slow ones.
The nuance of preloading timing: The preloading strategy fires after the initial navigation completes and the browser is idle. The lazy chunk downloads happen in the background during idle time, competing minimally with the user's current activity. By the time the user clicks a link to a lazy route, the chunk is already cached — navigation is instant.
Practical rule: Always lazy-load large feature sections. Always add withPreloading(PreloadAllModules) or a selective strategy. The combination gives you the best of both: fast initial load AND instant subsequent navigation. They are complementary, not redundant.

Section 14 — Common Interview Questions
Question 1
"What is lazy loading in Angular and how does it affect the build output?"
Strong answer covers:

Lazy loading defers downloading JavaScript for a route until the user navigates to it
Implemented via loadComponent or loadChildren with dynamic import() syntax
The Angular bundler (webpack/esbuild) creates separate chunk files for each lazy boundary
main.js only contains eagerly-loaded code — everything behind loadComponent/loadChildren is in named chunks
First visit to a lazy route downloads its chunk; subsequent visits use the browser cache
Practical impact: smaller initial bundle → faster Time to Interactive (TTI)

Weak answer misses: Explaining how the bundler knows to split — the static vs dynamic import() distinction — and confirming they understand it's about build output, not just runtime behavior.
Difficulty: Junior-Mid

Question 2
"How do route guards interact with lazy-loaded routes? Does the guard prevent the chunk from being downloaded?"
Strong answer covers:

Guards in canActivate run before loadChildren/loadComponent is called
A guard returning false or a UrlTree means the dynamic import() is never triggered — the chunk is not downloaded
This is a security benefit: unauthorized users never download admin/protected code
The correct order in the route config: canActivate then loadChildren (Angular handles the ordering automatically based on the navigation pipeline)
Contrast with putting auth logic inside the component: the component bundle would already be downloaded before the check runs

Weak answer misses: Explicitly confirming the chunk is not downloaded on guard failure — many candidates say "the guard blocks navigation" without addressing the network request.
Difficulty: Mid-Senior

Question 3
"What is a preloading strategy and when would you use a custom one over PreloadAllModules?"
Strong answer covers:

Preloading silently downloads lazy chunks after the initial app load, during browser idle time
PreloadAllModules downloads all lazy chunks — good for small apps where bandwidth is not a concern
Custom strategies (implementing PreloadingStrategy) allow selective preloading based on route data flags, user role, network conditions (navigator.connection), or time delays
Example: preload only routes marked data: { preload: true }, or only preload if navigator.connection.effectiveType === '4g'
withPreloading() in provideRouter() registers the strategy
Trade-off: PreloadAllModules on a large app with many chunks can cause unnecessary bandwidth consumption on mobile

Weak answer misses: The custom strategy use case — just saying "PreloadAllModules downloads everything" without discussing when you'd choose a selective approach.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Lazy-loading every route including small, always-visited components
typescript// ❌ Anti-pattern — lazy-loading tiny, always-needed components
export const APP_ROUTES: Routes = [
  {
    path: 'home',
    loadComponent: () => import('./home/home.component'), // 3KB component
  },
  {
    path: 'login',
    loadComponent: () => import('./login/login.component'), // always needed
  },
  {
    path: 'nav',
    loadComponent: () => import('./nav/nav.component'), // shown on every page
  },
];
Why it seems fine: "Lazy = good, so more lazy = more good" — a logical but wrong extrapolation.
What breaks at scale: Each lazy route requires an HTTP request for its chunk file. A 3KB component in its own chunk means an HTTP round-trip (potentially 50-200ms on mobile) to download 3KB. That is strictly worse than including it in main.js. Additionally, components needed on the first page load (login, nav) now require a chunk fetch before they can render — adding to Time to Interactive instead of reducing it.
typescript// ✅ Correct pattern — eager for small/always-needed, lazy for large/conditional
import { HomeComponent } from './home/home.component';
import { LoginComponent } from './login/login.component';

export const APP_ROUTES: Routes = [
  { path: 'home', component: HomeComponent },   // eagerly loaded — small, needed immediately
  { path: 'login', component: LoginComponent }, // eagerly loaded — needed on first visit
  {
    path: 'admin',
    loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES),
    // large, rarely visited by most users — worth the lazy split
  },
];

Anti-Pattern 2 — Forgetting that a static import defeats the lazy split
typescript// ❌ Anti-pattern — static import present alongside loadComponent
import { AdminDashboardComponent } from './admin/admin-dashboard.component'; // ← added by IDE

export const APP_ROUTES: Routes = [
  {
    path: 'admin',
    loadComponent: () =>
      import('./admin/admin-dashboard.component')
        .then(m => m.AdminDashboardComponent), // ← dynamic import also present
  },
];
// Result: AdminDashboardComponent is in main.js AND referenced by a chunk
// The "lazy" chunk exists but the component code is already in main.js
// Zero lazy loading benefit — with extra chunk overhead
Why it seems fine: The app works perfectly. No errors, no warnings — navigation to /admin functions correctly because the dynamic import resolves fine even though the static import already loaded it.
What breaks at scale: The entire admin bundle remains in main.js forever. The "lazy chunk" that gets generated either duplicates the code or references main.js — both outcomes waste bandwidth. In large teams, IDEs silently re-add static imports constantly, making this a recurring regression.
typescript// ✅ Correct pattern — zero static imports of lazy components at the top of routes files
// (no import statement for AdminDashboardComponent anywhere in app.routes.ts)
export const APP_ROUTES: Routes = [
  {
    path: 'admin',
    loadComponent: () =>
      import('./admin/admin-dashboard.component')
        .then(m => m.AdminDashboardComponent),
  },
];

Anti-Pattern 3 — Using loadChildren pointing to a component instead of a routes file
typescript// ❌ Anti-pattern — loadChildren pointing to a component file
export const APP_ROUTES: Routes = [
  {
    path: 'users',
    loadChildren: () =>
      import('./users/user-list.component') // ← this is a COMPONENT, not a routes file
        .then(m => m.UserListComponent),    // ← UserListComponent is not a Routes array
  },
];
// Angular expects loadChildren to resolve to a Routes array
// This produces a runtime error or renders nothing
Why it seems fine: Both loadComponent and loadChildren use () => import(...) syntax — they look identical. Developers confuse them.
What breaks: loadChildren expects the resolved value to be a Routes array (or an NgModule with routing — legacy). Passing a component class causes the Router to fail silently or throw Error: Invalid configuration of route 'users'.
typescript// ✅ Correct pattern — use the right tool for the job
// loadComponent → resolves to a Component class
{
  path: 'users',
  loadComponent: () =>
    import('./users/user-list.component').then(m => m.UserListComponent),
}

// loadChildren → resolves to a Routes array
{
  path: 'users',
  loadChildren: () =>
    import('./users/users.routes').then(m => m.USERS_ROUTES),
}

Section 16 — Mental Model Summary
Core concept in one sentence:

Lazy loading replaces static imports with dynamic import() calls in route config, telling the bundler to split feature code into separate chunks that the browser downloads only when the user first navigates there.
Key rules:

loadComponent for one standalone component; loadChildren for an entire feature routes file
No static import of the component at the top of the routes file — it defeats the split
Guards run before the chunk is downloaded — blocked guards prevent the network request
Chunks are cached after the first download — second visit to a lazy route is as fast as eager
Route-level providers create a DI scope scoped to that route subtree
Verify lazy splitting actually happened by checking ng build chunk output — the compiler gives no warning when it silently fails

The single most important Angular rule:

A static import of a lazy component in your routes file silently defeats the entire lazy split — always remove auto-added imports from app.routes.ts and verify chunks appear in the build output.
