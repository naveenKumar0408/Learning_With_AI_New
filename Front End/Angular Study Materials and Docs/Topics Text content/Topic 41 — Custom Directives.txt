Topic 41 — Custom Directives

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — The decorator and class structure are straightforward, but understanding when to build a directive versus a component, and how to correctly interact with the host element without breaking Angular's rendering model, requires deliberate practice.
Angular Relevance: High — Custom directives are the correct tool for reusable DOM behaviour that doesn't need its own template — click-outside detection, auto-focus, permission-based visibility, tooltip anchoring, and input formatting all belong in directives, not components.

Section 1 — Explanation
The Sticker Sheet Analogy
Imagine you're decorating notebooks. A component is like printing a completely new page and inserting it — it brings its own content, its own layout, its own structure.
A directive is like a sticker you apply to an existing page — it adds behaviour, changes appearance, or reacts to interaction, but the page itself already exists. The sticker doesn't replace the page; it enhances it.

A tooltip sticker — hover over the page, a bubble appears
A highlight sticker — the text underneath turns yellow
A lock sticker — you can't write on this section unless you have a key

You can put multiple stickers on the same page. Each sticker does one focused job. The page (host element) doesn't know or care how many stickers it has — it just behaves according to all of them.
In Angular terms:

The host element is the notebook page — it already exists in the template
Your directive class is the sticker — it attaches to that element via a CSS selector
@HostListener is the sticker reacting to what happens on the page (hover, click, keypress)
@HostBinding is the sticker changing something about the page's appearance or attributes


Technical Explanation
A directive is an Angular class decorated with @Directive that attaches to a DOM element matched by a CSS selector. Unlike components, directives have no template of their own — they operate on the host element they are placed on.
Three types of directives:
TypePurposeExamplesAttribute directiveChanges appearance or behaviour of an existing elementngClass, ngStyle, your custom appHighlightStructural directiveChanges the DOM structure by adding/removing elements@if, @for, *ngIf, *ngForComponentA directive with a templateEvery @Component is technically a directive
Custom directives you write are almost always attribute directives — structural directives are rare and complex (covered separately if needed).
Core building blocks:
@Directive({ selector: '[appMyDirective]' })  ← attaches to elements with this attribute
class MyDirective {
  @HostBinding('class.active')    ← binds to a property of the host element
  @HostListener('click')          ← listens to an event on the host element
  @Input()                        ← receives configuration from the template
  ElementRef                      ← direct reference to the host DOM element
  Renderer2                       ← safe, platform-agnostic DOM manipulation
}

Section 3 — Code Example
Plain TS — The core pattern in isolation
typescript// A directive is a class that:
// 1. Knows which element it is attached to (ElementRef)
// 2. Can react to events on that element (@HostListener)
// 3. Can change properties of that element (@HostBinding)
// 4. Can accept configuration from the template (@Input)

class HighlightBehaviour {
  private element: HTMLElement;
  private color: string = 'yellow';

  constructor(el: HTMLElement, color: string) {
    this.element = el;
    this.color = color;
  }

  onMouseEnter() {
    this.element.style.backgroundColor = this.color; // change appearance
  }

  onMouseLeave() {
    this.element.style.backgroundColor = ''; // restore
  }
}
// Angular's @Directive does this wiring automatically
// @HostListener replaces manual addEventListener
// @HostBinding replaces manual style assignment

Real Angular — Highlight directive (attribute directive fundamentals)
typescript// directives/highlight.directive.ts
import {
  Directive,
  HostBinding,
  HostListener,
  Input,
  OnInit,
} from '@angular/core';

@Directive({
  selector: '[appHighlight]', // applied to any element with this attribute
  standalone: true,
})
export class HighlightDirective implements OnInit {
  // @Input with same name as selector — allows [appHighlight]="'yellow'" syntax
  @Input() appHighlight: string = 'yellow';

  // Secondary input for the default (non-hovered) background
  @Input() defaultColor: string = 'transparent';

  // @HostBinding binds to a property of the host element
  // Angular keeps this in sync — no manual DOM manipulation needed
  @HostBinding('style.backgroundColor') backgroundColor = '';

  ngOnInit(): void {
    // Set initial state when directive first attaches
    this.backgroundColor = this.defaultColor;
  }

  // @HostListener subscribes to host element DOM events
  // Angular automatically removes the listener when the directive is destroyed
  @HostListener('mouseenter')
  onMouseEnter(): void {
    this.backgroundColor = this.appHighlight;
  }

  @HostListener('mouseleave')
  onMouseLeave(): void {
    this.backgroundColor = this.defaultColor;
  }
}
typescript// Using the directive in a template
// Must import HighlightDirective in the component's imports array
@Component({
  selector: 'app-product-card',
  standalone: true,
  imports: [HighlightDirective],
  template: `
    <!-- appHighlight input = the selector attribute itself -->
    <div appHighlight="lightblue">Hover over me</div>

    <!-- binding a dynamic color -->
    <div [appHighlight]="selectedColor" defaultColor="lightyellow">
      Dynamic highlight
    </div>

    <!-- directive with no value — uses default color -->
    <p appHighlight>Default yellow highlight</p>
  `,
})
export class ProductCardComponent {
  selectedColor = 'lightgreen';
}

Real Angular — Permission directive using Renderer2 and a service
typescript// directives/has-permission.directive.ts
import {
  Directive,
  Input,
  OnInit,
  ElementRef,
  Renderer2,
  inject,
} from '@angular/core';
import { AuthService } from '../services/auth.service';

@Directive({
  selector: '[appHasPermission]',
  standalone: true,
})
export class HasPermissionDirective implements OnInit {
  @Input() appHasPermission!: string; // required permission string e.g. 'admin:write'

  // ElementRef gives access to the underlying DOM element
  // Use Renderer2 for DOM manipulation — NOT direct element.style = ...
  // Renderer2 is platform-safe (works in SSR, Web Workers)
  private el = inject(ElementRef);
  private renderer = inject(Renderer2);
  private auth = inject(AuthService);

  ngOnInit(): void {
    if (!this.auth.hasPermission(this.appHasPermission)) {
      // Renderer2.setStyle is the Angular-safe way to change host element styles
      this.renderer.setStyle(this.el.nativeElement, 'display', 'none');
      // Alternative: this.renderer.setAttribute(this.el.nativeElement, 'disabled', 'true');
    }
  }
}
html<!-- template usage — button hidden if user lacks 'admin:write' permission -->
<button appHasPermission="admin:write" (click)="deleteUser()">
  Delete User
</button>

<input appHasPermission="editor:write" [(ngModel)]="content" />

Real Angular — Click-outside directive (practical real-world pattern)
typescript// directives/click-outside.directive.ts
import {
  Directive,
  Output,
  EventEmitter,
  HostListener,
  inject,
  ElementRef,
} from '@angular/core';

@Directive({
  selector: '[appClickOutside]',
  standalone: true,
})
export class ClickOutsideDirective {
  @Output() clickOutside = new EventEmitter<void>();

  private el = inject(ElementRef);

  // Listen on the DOCUMENT, not the host element
  // 'document:click' syntax — Angular supports global event listeners
  @HostListener('document:click', ['$event.target'])
  onDocumentClick(target: HTMLElement): void {
    // Check if the click was inside or outside this directive's host element
    const isInside = this.el.nativeElement.contains(target);
    if (!isInside) {
      this.clickOutside.emit();
    }
  }
}
html<!-- dropdown that closes when clicking outside -->
<div appClickOutside (clickOutside)="closeDropdown()">
  <button (click)="toggleDropdown()">Menu</button>
  @if (isOpen) {
    <ul class="dropdown">
      <li>Option 1</li>
      <li>Option 2</li>
    </ul>
  }
</div>

Section 4 — Before & After Refactor
❌ Before — DOM behaviour duplicated in every component
typescript// product-card.component.ts
@Component({ ... })
export class ProductCardComponent {
  private el = inject(ElementRef);

  @HostListener('mouseenter')
  onEnter() {
    this.el.nativeElement.style.backgroundColor = 'lightyellow';
  }

  @HostListener('mouseleave')
  onLeave() {
    this.el.nativeElement.style.backgroundColor = '';
  }
}

// user-card.component.ts — SAME code duplicated
@Component({ ... })
export class UserCardComponent {
  private el = inject(ElementRef);

  @HostListener('mouseenter')
  onEnter() {
    this.el.nativeElement.style.backgroundColor = 'lightyellow';
  }
  // ...identical code again
}
What breaks: Highlight behaviour is coupled to specific components. To add it to a third component, copy-paste again. To change the hover colour, update every component individually. To add keyboard support, update every component. This violates the single responsibility principle — a card component's job is to display card data, not manage hover state.

✅ After — Behaviour extracted into a reusable directive
typescript// One directive handles the behaviour for ALL elements
@Directive({ selector: '[appHighlight]', standalone: true })
export class HighlightDirective {
  @Input() appHighlight = 'lightyellow';

  @HostBinding('style.backgroundColor') bg = '';

  @HostListener('mouseenter') onEnter() { this.bg = this.appHighlight; }
  @HostListener('mouseleave') onLeave() { this.bg = ''; }
}
html<!-- Apply to any element in any component — zero duplication -->
<app-product-card appHighlight="lightyellow" />
<app-user-card appHighlight="lightblue" />
<tr appHighlight="lightyellow" *ngFor="let row of rows">...</tr>
<button appHighlight>Hover me</button>
Why this refactor matters in Angular: Directives are Angular's mechanism for behaviour composition without inheritance. Any element in any component gains the behaviour by adding the attribute. Change the directive once — every element using it updates. This is the open/closed principle applied to Angular templates.

Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Manipulating the DOM directly via ElementRef.nativeElement instead of Renderer2
The mistakethis.el.nativeElement.style.color = 'red' directly in a directiveWhy developers make itIt's shorter, familiar from vanilla JS, and works correctly in a browserHow to avoid itAlways use Renderer2: this.renderer.setStyle(this.el.nativeElement, 'color', 'red')Angular consequenceDirect DOM manipulation breaks Angular Universal (SSR — Topic 50), Web Worker rendering, and test environments where nativeElement may not be a real DOM node. Renderer2 is platform-agnostic — Angular swaps in the correct implementation per environment

Mistake 2 — Forgetting to add the directive to the component's imports array
The mistakeCreating a standalone directive but not importing it in the component that uses itWhy developers make itComponents are in declarations in NgModule apps — muscle memory carries over. Standalone directives require explicit importsHow to avoid itTreat standalone directives exactly like standalone components: they must be in imports: [MyDirective] in every component that uses themAngular consequenceAngular silently ignores the attribute in the template — no error, no warning. The directive never instantiates. The element looks and behaves as if the directive was never applied

Mistake 3 — Using @HostBinding to bind to innerHTML or textContent for content projection
The mistake@HostBinding('innerHTML') content = '<strong>Hello</strong>'Why developers make itLooks like a quick way to add content to the host element from a directiveHow to avoid itIf you need to add a template, you need a component (with ng-content) not a directive. Section 7 — Debugging Tips
Bug 1 — Directive not working; element behaves as if directive was never applied
Symptom: No visual change, no console errors, @HostListener never fires — directive appears completely ignored.
Plain English cause: The directive is not imported in the consuming component's imports array (standalone component pattern). Angular treats the attribute as an unknown HTML attribute and silently ignores it.
Fix:
typescript// consuming-component.ts
@Component({
  standalone: true,
  imports: [
    HighlightDirective, // ← directive MUST be here
  ],
  template: `<div appHighlight>Hello</div>`,
})
export class ConsumingComponent {}
Angular-specific note: Enable strictTemplates in tsconfig.json — with this flag on, Angular will emit a compile-time error for unknown attributes, surfacing missing directive imports before the app runs.

Bug 2 — @HostListener('document:click') fires immediately on the same click that opened a dropdown
Symptom: User clicks a button to open a dropdown. The clickOutside event fires on the same click, immediately closing the dropdown that was just opened.
Plain English cause: The document:click listener fires for all clicks — including the one on the toggle button itself. The click event bubbles up to the document, the listener sees it, checks contains(target) — but the button is outside the dropdown div, so it emits clickOutside.
Fix: Delay the listener attachment until after the current event cycle:
typescript// Option 1: Use stopPropagation on the toggle button
<button (click)="toggleDropdown(); $event.stopPropagation()">Menu</button>

// Option 2: Skip the first emission using a flag
@HostListener('document:click', ['$event.target'])
onDocumentClick(target: HTMLElement): void {
  if (this.justOpened) { this.justOpened = false; return; }
  if (!this.el.nativeElement.contains(target)) {
    this.clickOutside.emit();
  }
}
Angular-specific note: This is a DOM event timing issue, not Angular-specific, but it surfaces constantly with document:click directives. The stopPropagation approach is cleaner — it prevents the toggle click from reaching the document listener entirely.

Bug 3 — @HostBinding value not updating after @Input changes
Symptom: Directive applies correctly on first render, but when the bound @Input value changes (e.g. user changes a color picker), the @HostBinding doesn't update.
Plain English cause: The @HostBinding is set to the initial input value in ngOnInit and never updated — @Input changes fire ngOnChanges, but the directive has no ngOnChanges handler to propagate the new value to the binding.
Fix:
typescript@Directive({ selector: '[appHighlight]', standalone: true })
export class HighlightDirective implements OnChanges {
  @Input() appHighlight = 'yellow';
  @HostBinding('style.backgroundColor') bg = '';

  ngOnChanges(): void {
    // Called every time @Input value changes — keep HostBinding in sync
    this.bg = this.appHighlight;
  }
}
Angular-specific note: @HostBinding is reactive to its own property changes (Angular's change detection tracks it), but it doesn't automatically watch @Input properties. You must explicitly propagate input changes to the binding property via ngOnChanges or a setter.

Section 8 — Real-World Applications
Scenario 1 — Auto-focus directive for accessible modals (Angular-specific)
When a modal opens, focus must move to the first focusable element inside it for keyboard accessibility. Implementing this in every modal component creates duplication. A directive applied to the modal container handles it universally.
typescript// directives/auto-focus.directive.ts
import { Directive, ElementRef, Input, OnInit, inject } from '@angular/core';

@Directive({
  selector: '[appAutoFocus]',
  standalone: true,
})
export class AutoFocusDirective implements OnInit {
  // Optional: CSS selector for which element to focus within the host
  @Input() appAutoFocus: string = ''; // empty = focus the host itself

  private el = inject(ElementRef);

  ngOnInit(): void {
    // setTimeout pushes focus call after Angular has finished rendering
    // the host element's content — without this, child elements don't exist yet
    setTimeout(() => {
      const target = this.appAutoFocus
        ? this.el.nativeElement.querySelector(this.appAutoFocus)
        : this.el.nativeElement;

      (target as HTMLElement)?.focus();
    });
  }
}
html<!-- Modal component template -->
<div class="modal" appAutoFocus="input, button, [tabindex]">
  <h2>Confirm Delete</h2>
  <p>Are you sure?</p>
  <button>Cancel</button>
  <button>Delete</button>
  <!-- Focus moves to first button automatically when modal opens -->
</div>

<!-- Or focus the container itself -->
<div class="modal" tabindex="-1" appAutoFocus>
  <!-- Container itself receives focus -->
</div>

Scenario 2 — Tooltip directive (real-world compound directive pattern)
A tooltip that appears on hover, positions itself relative to the host element, and cleans up properly — without requiring a tooltip component wrapper on every element.
typescript// directives/tooltip.directive.ts
import {
  Directive,
  Input,
  HostListener,
  ElementRef,
  Renderer2,
  OnDestroy,
  inject,
} from '@angular/core';

@Directive({
  selector: '[appTooltip]',
  standalone: true,
})
export class TooltipDirective implements OnDestroy {
  @Input() appTooltip = ''; // tooltip text

  private el = inject(ElementRef);
  private renderer = inject(Renderer2);
  private tooltipElement: HTMLElement | null = null;

  @HostListener('mouseenter')
  onMouseEnter(): void {
    this.createTooltip();
  }

  @HostListener('mouseleave')
  onMouseLeave(): void {
    this.removeTooltip();
  }

  private createTooltip(): void {
    // Use Renderer2 — not innerHTML or document.createElement directly
    this.tooltipElement = this.renderer.createElement('div') as HTMLElement;
    this.renderer.addClass(this.tooltipElement, 'tooltip');
    const text = this.renderer.createText(this.appTooltip);
    this.renderer.appendChild(this.tooltipElement, text);

    // Position tooltip above host element
    const hostRect = this.el.nativeElement.getBoundingClientRect();
    this.renderer.setStyle(this.tooltipElement, 'position', 'fixed');
    this.renderer.setStyle(this.tooltipElement, 'top', `${hostRect.top - 36}px`);
    this.renderer.setStyle(this.tooltipElement, 'left', `${hostRect.left}px`);

    this.renderer.appendChild(document.body, this.tooltipElement);
  }

  private removeTooltip(): void {
    if (this.tooltipElement) {
      this.renderer.removeChild(document.body, this.tooltipElement);
      this.tooltipElement = null;
    }
  }

  // Critical: remove tooltip if component is destroyed while hovering
  ngOnDestroy(): void {
    this.removeTooltip();
  }
}
html<button appTooltip="Save your changes">Save</button>
<span appTooltip="This field is required">*</span>
<img src="user.jpg" appTooltip="Profile picture" alt="user" />

Section 10 — Key Takeaways
Core concepts in plain English:

A directive attaches behaviour to an existing host element — it has no template of its own
@HostBinding binds a directive property to a host element property — Angular keeps it in sync
@HostListener subscribes to a host element event — Angular removes the listener on destroy
@Input() on a directive works identically to @Input() on a component — same binding syntax
Renderer2 is the platform-safe way to manipulate DOM — never use nativeElement directly
Directives must be imported in every consuming component's imports array (standalone)

Quick Reference Table:

Angular-specific rules:

selector: '[appCamelCase]' (attribute selector) is the convention for attribute directives
Always prefix directive selectors with your app prefix (app) to avoid conflicts with native HTML attributes
@HostListener('document:click') and @HostListener('window:resize') work for global listeners
ngOnChanges is needed to react to @Input changes — @HostBinding alone won't update automatically
Standalone directives must be imported in every component that uses them — no global registration

One-Line Memory Aid:

A directive is a sticker on an existing element — @HostBinding changes how it looks, @HostListener reacts to what happens to it, and @Input configures what the sticker does.


Section 11 — Thought-Provoking Question + Answer
Question: When should you build a custom directive versus a custom component? Is there a clear architectural rule, or is it a judgment call?
Answer:
Conceptual explanation: There is a clear rule, though it requires understanding what each tool is fundamentally for:

A component owns its own template — it defines what is rendered inside it
A directive owns its own behaviour — it changes what an existing element does or looks like

The test is: does this feature need its own HTML structure, or is it modifying an existing element?
Needs own HTML structure→ ComponentModifies an existing element→ Directive
Examples that clarify the boundary:
A tooltip component wraps a trigger element: <app-tooltip text="Save">Save Button</app-tooltip> — it controls the template structure around the trigger. A tooltip directive is applied to any element: <button appTooltip="Save">Save</button> — the button already exists; the directive adds behaviour to it. Both work; the directive is more composable because it can be applied to any element type without restructuring the template.
A modal component has its own overlay, header, footer, content slots — clearly it needs a template. An auto-focus directive doesn't need any template; it just calls .focus() after the host renders. Clear directive.
The Angular-specific implication: When the same behaviour needs to work on multiple element types (buttons, inputs, divs, table rows), a directive is almost always the correct choice. A component would require wrapping every element type differently. The directive applies uniformly to any host element its selector matches.
Practical rule: If you catch yourself writing a component that has only <ng-content></ng-content> in its template and exists purely to attach behaviour — stop, delete it, and write a directive instead.

Section 14 — Common Interview Questions
Question 1
"What is the difference between a component and a directive in Angular?"
Strong answer covers:

Components have a template; directives do not
Both are technically directives — @Component extends @Directive
Attribute directives add behaviour/appearance to existing elements; structural directives change DOM structure
When to choose each: own HTML structure → component; modify existing element → directive
Both participate in DI, both have lifecycle hooks, both use @Input()

Weak answer misses: That @Component is a directive with a template — treating them as completely different concepts rather than a specialisation relationship.
Difficulty: Junior

Question 2
"What is Renderer2 and why should you use it instead of accessing nativeElement directly?"
Strong answer covers:

Renderer2 is Angular's platform-agnostic DOM abstraction layer
Direct nativeElement access couples code to the browser DOM — breaks in Angular Universal (SSR), Web Workers, and test environments
Renderer2 methods: setStyle, removeStyle, addClass, removeClass, setAttribute, removeAttribute, createElement, appendChild
Angular swaps the Renderer2 implementation based on the rendering environment — browser gets DOM renderer, SSR gets server renderer
Security benefit: Renderer2 routes through Angular's sanitisation pipeline; raw innerHTML does not

Weak answer misses: The SSR/platform-agnostic angle — just saying "it's the Angular way" without explaining why.
Difficulty: Mid

Question 3
"How would you build a directive that listens to clicks anywhere on the document to close a dropdown, while ensuring it doesn't close on the click that opened it?"
Strong answer covers:

@HostListener('document:click', ['$event.target']) for the global listener
ElementRef.nativeElement.contains(target) to distinguish inside vs outside clicks
The timing problem: the open-click event bubbles to document and immediately triggers the close listener
Solution options: stopPropagation on the trigger button, or a one-tick delay using setTimeout
@Output() clickOutside = new EventEmitter<void>() to communicate the event to the parent
Cleanup is automatic — @HostListener on document is removed when the directive destroys

Weak answer misses: The timing/same-click problem — describing the basic pattern without addressing why it immediately closes on open.
Difficulty: Mid-Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Putting business logic inside a directive
typescript// ❌ Anti-pattern — directive doing HTTP calls and business logic
@Directive({ selector: '[appUserStatus]' })
export class UserStatusDirective implements OnInit {
  @Input() userId!: string;

  private http = inject(HttpClient);

  ngOnInit(): void {
    // HTTP call directly in directive — wrong layer
    this.http.get<User>(`/api/users/${this.userId}`).subscribe(user => {
      if (user.isActive) {
        this.renderer.addClass(this.el.nativeElement, 'active');
      }
    });
  }
}
Why it seems fine: It works, it's self-contained, and it's easy to apply to any element.
What breaks at scale: Directives become untestable black boxes. The same user data is fetched once per element that uses the directive — five appUserStatus elements on the same page trigger five separate HTTP requests. Business rules (what "active" means) are buried in a DOM layer class that nobody looks for them in.
typescript// ✅ Correct pattern — directive receives resolved data via @Input, applies only DOM behaviour
@Directive({ selector: '[appUserStatus]' })
export class UserStatusDirective implements OnChanges {
  @Input() isActive = false; // component fetches data, passes result in

  @HostBinding('class.active') get activeClass() { return this.isActive; }
}

// Component handles the data concern
user$ = this.userService.getUser(this.userId); // one HTTP call, shared

Anti-Pattern 2 — Using ElementRef.nativeElement for DOM manipulation
typescript// ❌ Anti-pattern — direct DOM manipulation
@Directive({ selector: '[appHighlight]' })
export class HighlightDirective {
  private el = inject(ElementRef);

  @HostListener('mouseenter')
  onEnter(): void {
    this.el.nativeElement.style.backgroundColor = 'yellow'; // direct DOM access
    this.el.nativeElement.classList.add('highlighted');      // direct classList
  }
}
Why it seems fine: Works perfectly in every browser-based test and development scenario.
What breaks in production: Angular Universal (SSR — Topic 50) runs Angular on Node.js where there is no DOM. nativeElement.style throws TypeError: Cannot set property 'backgroundColor' of undefined. Apps with SSR enabled for SEO will crash on server-side rendering of any route that uses this directive.
typescript// ✅ Correct pattern — Renderer2 for all DOM operations
@Directive({ selector: '[appHighlight]' })
export class HighlightDirective {
  private el = inject(ElementRef);
  private renderer = inject(Renderer2);

  @HostListener('mouseenter')
  onEnter(): void {
    this.renderer.setStyle(this.el.nativeElement, 'backgroundColor', 'yellow');
    this.renderer.addClass(this.el.nativeElement, 'highlighted');
  }
}

Anti-Pattern 3 — Creating a directive when a component is the right tool
typescript// ❌ Anti-pattern — directive trying to add its own HTML structure
@Directive({ selector: '[appCard]' })
export class CardDirective implements OnInit {
  private el = inject(ElementRef);
  private renderer = inject(Renderer2);

  ngOnInit(): void {
    // Trying to add wrapper divs, headers, footers via DOM manipulation
    const header = this.renderer.createElement('div');
    this.renderer.addClass(header, 'card-header');
    this.renderer.insertBefore(
      this.el.nativeElement.parentNode,
      header,
      this.el.nativeElement
    );
    // ...more DOM surgery to build a card layout
  }
}
Why it seems fine: The developer wants card styling to be reusable without wrapping every element in a component — the directive feels like a lighter-weight solution.
What breaks at scale: Imperatively building HTML structure via Renderer2 bypasses Angular's template compiler entirely. Change detection doesn't track these elements. Angular expressions don't work in them. Event bindings fail. The "card" HTML is invisible to Angular's debugging tools. Structural complexity grows rapidly as the directive tries to replicate what a template does naturally.
typescript// ✅ Correct pattern — component with content projection for reusable structure
@Component({
  selector: 'app-card',
  standalone: true,
  template: `
    <div class="card">
      <div class="card-header"><ng-content select="[header]" /></div>
      <div class="card-body"><ng-content /></div>
    </div>
  `,
})
export class CardComponent {}

  <span header>Card Title</span>
  <p>Card content goes here</p>
</app-card>

Section 16 — Mental Model Summary
Core concept in one sentence:

A custom directive is a behaviour class that attaches to an existing host element via a CSS selector, reacting to its events with @HostListener and modifying its properties with @HostBinding — with no template of its own.
Key rules:

Directives have no template — they enhance an existing element, not replace it
Use @HostBinding to declaratively sync directive state → host element properties
Use @HostListener to react to host element events — Angular handles listener cleanup
Always use Renderer2 for DOM manipulation — never nativeElement directly
Import standalone directives in every consuming component's imports array
If the feature needs its own HTML structure, build a component — not a directive

The single most important Angular rule:

Use Renderer2 for all DOM manipulation inside directives — direct nativeElement access breaks Angular Universal (SSR) and test environments with no error in the browser.

Section 8 — Real-World Applications (both examples rewritten)
Scenario 1 — Auto-focus directive for accessible modals:
typescript@Directive({ selector: '[appAutoFocus]' })
export class AutoFocusDirective {
  appAutoFocus = input<string>(''); // CSS selector for which element to focus
  private el = inject(ElementRef);

  constructor() {
    afterNextRender(() => {
      // afterNextRender replaces ngOnInit + setTimeout for post-render DOM work
      const target = this.appAutoFocus()
        ? this.el.nativeElement.querySelector(this.appAutoFocus())
        : this.el.nativeElement;

      (target as HTMLElement)?.focus();
    });
  }
}

// Template usage:
// <div class="modal" appAutoFocus="input, button, [tabindex]">
Note: afterNextRender() is the modern replacement for the ngOnInit + setTimeout() pattern — it guarantees the call runs after Angular finishes rendering, without an arbitrary timeout.
Scenario 2 — Tooltip directive:
typescript@Directive({ selector: '[appTooltip]' })
export class TooltipDirective {
  appTooltip = input(''); // input() signal
  private el = inject(ElementRef);
  private renderer = inject(Renderer2);
  private tooltipElement: HTMLElement | null = null;

  @HostListener('mouseenter') onMouseEnter(): void { this.createTooltip(); }
  @HostListener('mouseleave') onMouseLeave(): void { this.removeTooltip(); }

  private createTooltip(): void {
    this.tooltipElement = this.renderer.createElement('div') as HTMLElement;
    this.renderer.addClass(this.tooltipElement, 'tooltip');
    const text = this.renderer.createText(this.appTooltip()); // call signal as function
    this.renderer.appendChild(this.tooltipElement, text);
    const hostRect = this.el.nativeElement.getBoundingClientRect();
    this.renderer.setStyle(this.tooltipElement, 'position', 'fixed');
    this.renderer.setStyle(this.tooltipElement, 'top', `${hostRect.top - 36}px`);
    this.renderer.appendChild(document.body, this.tooltipElement);
  }

  private removeTooltip(): void {
    if (this.tooltipElement) {
      this.renderer.removeChild(document.body, this.tooltipElement);
      this.tooltipElement = null;
    }
  }

  ngOnDestroy(): void { this.removeTooltip(); } // OnDestroy interface still current
}
