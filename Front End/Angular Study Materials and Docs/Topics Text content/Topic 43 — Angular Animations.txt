Topic 43 — Angular Animations

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — The API surface is large and the mental model (states, transitions, triggers) requires a deliberate shift from thinking in CSS to thinking in Angular's declarative animation DSL; the mechanics are learnable but the layering of concepts trips up most developers on first contact.
Angular Relevance: High — Angular Animations is the production-correct way to animate components in an Angular app; it integrates with change detection, works with OnPush components, survives SSR, and avoids the brittle CSS-class-toggling patterns that break under Angular's rendering model.

Section 1 — Explanation
The Traffic Light Analogy
Imagine a traffic light. It has a fixed set of states (red, amber, green). At any moment it is always in exactly one state. When conditions change, it transitions from one state to another — and during that transition it does something visible (the light changes). The transition itself has a duration and a curve (instant, or a brief fade).
Angular Animations work exactly like this:

A state is a named snapshot of CSS properties (red = { backgroundColor: 'red' })
A transition is the rule for moving between two states ('red => green') and how long it takes
A trigger is the named container that groups states and transitions together and is attached to a host element in the template

The template binds the trigger like a property: [@trafficLight]="currentState". Whenever currentState changes in the component, Angular looks up the matching transition, calculates the interpolated CSS values between the two states, and plays the animation — all without you writing a single requestAnimationFrame or CSS keyframe.
Technical Explanation:
Angular Animations are powered by the Web Animations API (with a CSS fallback) and are provided through @angular/animations. The engine lives outside the core rendering pipeline, which is why you must explicitly provide it with provideAnimations() in app.config.ts.
The building blocks:
FunctionPurposeWhere it livestrigger(name, [...])Names and groups states + transitionsanimations: [] metadatastate(name, style({}))Defines CSS properties for a named stateInside trigger()transition('a => b', [...])Defines what happens when moving from state a to bInside trigger()animate('duration easing', style({}))Defines timing and optional end-style for a transitionInside transition()keyframes([...])Multi-step animation with explicit percentage checkpointsInside animate()query(selector, [...])Targets child elements inside a parent animationInside transition()stagger(delay, [...])Adds sequential delay between a list of animated childrenInside query()group([...])Runs multiple animations in parallelInside transition()sequence([...])Runs multiple animations one after anotherInside transition()
The two special wildcard states:

* — matches any state (including void)
void — the state of an element that is not in the DOM (before it enters or after it leaves)

This gives you the two most common patterns:

'void => *' = element enters the DOM (aliased as :enter)
'* => void' = element leaves the DOM (aliased as :leave)

Real Angular Example 1 — Fade In / Fade Out with @if
typescript// app.config.ts — animations must be explicitly provided
import { provideAnimations } from '@angular/platform-browser/animations';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideAnimations()   // ← required once at the root level
  ]
};
typescript// notification.component.ts
import { Component, signal } from '@angular/core';
import {
  trigger,
  state,
  style,
  transition,
  animate
} from '@angular/animations';

@Component({
  selector: 'app-notification',
  standalone: true,
  animations: [
    trigger('fadeInOut', [
      // Define what 'visible' looks like
      state('visible', style({
        opacity: 1,
        transform: 'translateY(0)'
      })),
      // Define what 'hidden' looks like
      state('hidden', style({
        opacity: 0,
        transform: 'translateY(-10px)'
      })),
      // Transition in either direction: 300ms ease-in-out
      transition('visible <=> hidden', [
        animate('300ms ease-in-out')
      ])
    ])
  ],
  template: `
    <div [@fadeInOut]="panelState()" class="notification">
      Saved successfully!
    </div>
    <button (click)="toggle()">Toggle</button>
  `
})
export class NotificationComponent {
  panelState = signal<'visible' | 'hidden'>('hidden');

  toggle() {
    // Changing the signal value triggers the transition
    this.panelState.set(this.panelState() === 'visible' ? 'hidden' : 'visible');
  }
}

Real Angular Example 2 — Enter / Leave Animation with @if
typescript// alert-banner.component.ts
import { Component, signal } from '@angular/core';
import { trigger, transition, style, animate } from '@angular/animations';

@Component({
  selector: 'app-alert-banner',
  standalone: true,
  animations: [
    trigger('slideFade', [
      // :enter fires when @if adds this element to the DOM
      transition(':enter', [
        style({ opacity: 0, transform: 'translateX(-20px)' }), // starting style
        animate('250ms ease-out', style({ opacity: 1, transform: 'translateX(0)' }))
      ]),
      // :leave fires when @if removes this element from the DOM
      transition(':leave', [
        animate('200ms ease-in', style({ opacity: 0, transform: 'translateX(20px)' }))
      ])
    ])
  ],
  template: `
    @if (showAlert()) {
      <!-- Angular holds the element in the DOM until the leave animation completes -->
      <div @slideFade class="alert">
        ⚠ Connection lost. Retrying…
      </div>
    }
    <button (click)="showAlert.set(!showAlert())">Toggle Alert</button>
  `
})
export class AlertBannerComponent {
  showAlert = signal(true);
}

Real Angular Example 3 — Staggered List Animation
typescript// task-list.component.ts
import { trigger, transition, style, animate, query, stagger } from '@angular/animations';

@Component({
  standalone: true,
  animations: [
    trigger('listAnimation', [
      transition('* => *', [  // fires on any state change (any list update)
        query(':enter', [     // target all newly added child elements
          style({ opacity: 0, transform: 'translateY(10px)' }),
          stagger(60, [       // each item starts 60ms after the previous
            animate('300ms ease-out', style({ opacity: 1, transform: 'translateY(0)' }))
          ])
        ], { optional: true })  // optional: true — no error if no items are entering
      ])
    ])
  ],
  template: `
    <!-- The trigger goes on the PARENT container, not individual items -->
    <ul [@listAnimation]="tasks().length">
      @for (task of tasks(); track task.id) {
        <li>{{ task.title }}</li>
      }
    </ul>
  `
})
export class TaskListComponent {
  tasks = signal<Task[]>([]);
}

Section 4 — Before & After Refactor
❌ Before — CSS Class Toggle Animation
typescript// WRONG: manually toggling a CSS class to drive animation
@Component({
  template: `
    <div [class.visible]="isVisible" class="panel">Content</div>
    <button (click)="toggle()">Toggle</button>
  `,
  styles: [`
    .panel { opacity: 0; transition: opacity 300ms; }
    .panel.visible { opacity: 1; }
  `]
})
export class PanelComponent {
  isVisible = false;

  toggle() {
    this.isVisible = !this.isVisible;
    // When combined with @if — this completely breaks.
    // If you use @if(isVisible), the element is removed from the DOM
    // before the CSS transition can play. The user sees an instant removal.
  }
}
What breaks:

The CSS transition on :leave never plays because @if removes the element from the DOM instantly — before the browser has a chance to run the CSS transition
OnPush components may not detect the class change if isVisible is mutated inside a non-signal, non-observable context
Completely untestable via Angular's testing utilities — no animation state to assert


✅ After — Angular Animation Trigger
typescript@Component({
  standalone: true,
  animations: [
    trigger('fade', [
      transition(':enter', [
        style({ opacity: 0 }),
        animate('300ms ease-out', style({ opacity: 1 }))
      ]),
      transition(':leave', [
        animate('200ms ease-in', style({ opacity: 0 }))
      ])
    ])
  ],
  template: `
    @if (isVisible()) {
      <!-- Angular's animation engine holds the element in the DOM
           until the :leave animation finishes, then removes it -->
      <div @fade class="panel">Content</div>
    }
    <button (click)="isVisible.set(!isVisible())">Toggle</button>
  `
})
export class PanelComponent {
  isVisible = signal(false);
}
Why this refactor matters:

Angular's animation engine delays DOM removal until the :leave animation completes — CSS transitions can never do this
Works correctly with @if, @for, OnPush, and Angular Universal (SSR) — all of which break the CSS class toggle approach
The animation is declared in the component metadata, co-located with the template, and testable via fakeAsync in TestBed


Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Forgetting provideAnimations() in app.config.ts
What the mistake looks like: Animations are defined correctly in the component but nothing animates. No error is thrown.
Why developers make it: In older Angular (NgModule-based), you imported BrowserAnimationsModule in AppModule. In standalone Angular, you call provideAnimations() in app.config.ts. Developers porting code or following old tutorials miss this entirely.
How to avoid it: When you add animations: [...] to your first component, immediately check app.config.ts for provideAnimations(). If you want to disable animations in tests, use provideNoopAnimations() instead.
Angular-specific consequence: Animations silently do nothing — the element still shows/hides, but all transitions are skipped. The bug looks identical to an animation timing issue, wasting debugging time.

Mistake 2 — Using [hidden] Instead of @if for Enter/Leave Animations
What the mistake looks like:
html<!-- WRONG: [hidden] keeps the element in the DOM — :leave never fires -->
<div @fade [hidden]="!isVisible">Content</div>
Why developers make it: [hidden] feels like toggling visibility. Developers assume Angular's animation engine watches visibility, not DOM presence.
How to avoid it: :enter and :leave are triggered exclusively by elements being added to or removed from the DOM. Only @if (or *ngIf) actually removes the element. Use @if for any component that needs enter/leave animations.
Angular-specific consequence: The element appears and disappears instantly with no animation despite a correctly written trigger — the :leave animation never fires because the element never leaves the DOM.

Mistake 3 — Putting the query() Trigger on the Child Instead of the Parent
What the mistake looks like:
html<!-- WRONG: trigger on each list item — stagger won't work -->
@for (task of tasks(); track task.id) {
  <li [@listAnimation]="...">{{ task.title }}</li>
}
Why developers make it: It seems logical to animate each item individually.
How to avoid it: The query() and stagger() functions work by querying child elements from a parent trigger. The trigger must go on the container element; query(':enter', ...) then finds all entering children within that container.
Angular-specific consequence: The stagger never applies — each item animates independently and simultaneously, defeating the cascading effect entirely.

Section 7 — Debugging Tips
Bug 1 — Animations Defined but Nothing Animates
Symptom: Component renders and elements show/hide correctly but no animation plays. No console errors.
Plain English Cause: Either provideAnimations() is missing from app.config.ts, or provideNoopAnimations() has been added (which silently disables all animations — often left in from test configuration).
Fix:
typescript// app.config.ts
import { provideAnimations } from '@angular/platform-browser/animations';

export const appConfig: ApplicationConfig = {
  providers: [
    provideAnimations()  // ← ensure this is present, not provideNoopAnimations()
  ]
};
Angular-specific note: If you migrated from NgModule, check that BrowserAnimationsModule in AppModule was replaced with provideAnimations() — not just removed.

Bug 2 — query(':enter', ...) threw error: No elements found
Symptom: Runtime error in the console: ANIMATION: Could not find elements matching selector or similar when the list is rendered empty initially.
Plain English Cause: query() throws by default if the CSS selector matches zero elements. When a list first renders empty, query(':enter', ...) finds nothing.
Fix:
typescriptquery(':enter', [
  style({ opacity: 0 }),
  stagger(60, [animate('300ms', style({ opacity: 1 }))])
], { optional: true })  // ← this one flag prevents the error
Angular-specific note: Always add { optional: true } to any query() that targets :enter or :leave on dynamically loaded lists that could be empty on initialisation.

Bug 3 — Leave Animation Skipped, Element Disappears Instantly
Symptom: The enter animation plays correctly but elements disappear with no transition when removed.
Plain English Cause: The element is being hidden with [hidden], display: none, or a CSS class toggle rather than being removed from the DOM via @if. Angular's :leave trigger only fires on actual DOM removal.
Fix:
html<!-- REPLACE THIS: -->
<div @myTrigger [hidden]="!show">Content</div>

<!-- WITH THIS: -->
@if (show) {
  <div @myTrigger>Content</div>
}
Angular-specific note: The distinction between "hidden in the DOM" and "removed from the DOM" is one of the most fundamental Angular animation concepts. :leave = DOM removal, always.

Section 8 — Real-World Applications
Scenario 1 — Animated Modal / Dialog Overlay
A UX requirement on a SaaS dashboard: modals must slide up from the bottom on open and fade down on close. The modal is managed by a signal in a layout component.
typescript// modal.component.ts
import { trigger, transition, style, animate, group } from '@angular/animations';

@Component({
  selector: 'app-modal',
  standalone: true,
  animations: [
    trigger('modalAnimation', [
      transition(':enter', [
        group([
          // Backdrop fades in
          query('.backdrop', [
            style({ opacity: 0 }),
            animate('200ms ease-out', style({ opacity: 1 }))
          ]),
          // Panel slides up
          query('.panel', [
            style({ opacity: 0, transform: 'translateY(40px)' }),
            animate('250ms 50ms ease-out',  // 50ms delay lets backdrop appear first
              style({ opacity: 1, transform: 'translateY(0)' }))
          ])
        ])
      ]),
      transition(':leave', [
        group([
          query('.backdrop', [animate('200ms ease-in', style({ opacity: 0 }))]),
          query('.panel', [animate('150ms ease-in',
            style({ opacity: 0, transform: 'translateY(20px)' }))])
        ])
      ])
    ])
  ],
  template: `
    @if (isOpen()) {
      <div @modalAnimation class="modal-host">
        <div class="backdrop" (click)="close()"></div>
        <div class="panel">
          <ng-content />
        </div>
      </div>
    }
  `
})
export class ModalComponent {
  isOpen = input.required<boolean>();
  closed = output<void>();

  close() { this.closed.emit(); }
}
Why Angular Animations and not CSS: The backdrop and panel must animate in a coordinated sequence. CSS cannot express "animate child A then child B with a 50ms delay" declaratively. group() + query() handles this exactly.

Scenario 2 — Route Transition Animations
When navigating between routes, pages slide in from the right. This is wired at the router-outlet level.
typescript// app.component.ts
import { trigger, transition, style, animate, query, group } from '@angular/animations';
import { RouterOutlet } from '@angular/router';

export const routeTransitionAnimation = trigger('routeAnimation', [
  transition('* <=> *', [
    // Capture the outgoing and incoming pages
    query(':enter, :leave', [
      style({ position: 'absolute', width: '100%' })
    ], { optional: true }),
    group([
      query(':leave', [
        animate('200ms ease-in', style({ opacity: 0, transform: 'translateX(-20px)' }))
      ], { optional: true }),
      query(':enter', [
        style({ opacity: 0, transform: 'translateX(20px)' }),
        animate('250ms 100ms ease-out', style({ opacity: 1, transform: 'translateX(0)' }))
      ], { optional: true })
    ])
  ])
]);

@Component({
  standalone: true,
  imports: [RouterOutlet],
  animations: [routeTransitionAnimation],
  template: `
    <!-- prepareRoute() returns a unique key per route, triggering the animation -->
    <div [@routeAnimation]="prepareRoute(outlet)">
      <router-outlet #outlet="outlet" />
    </div>
  `
})
export class AppComponent {
  prepareRoute(outlet: RouterOutlet) {
    // Returns the route's animation data or a fallback key
    return outlet?.activatedRouteData?.['animation'] ?? outlet?.isActivated;
  }
}
typescript// app.routes.ts — give each route a unique animation key
export const routes: Routes = [
  { path: 'home',    component: HomeComponent,    data: { animation: 'home' } },
  { path: 'profile', component: ProfileComponent, data: { animation: 'profile' } },
];

Section 11 — Thought-Provoking Question + Answer
Question: Angular's animation engine delays DOM removal until a :leave animation finishes. But Angular's change detection has already processed @if (false) and decided the element should be gone. How does Angular hold the element in the DOM without contradicting its own rendering output?
Answer:
This is one of the more elegant pieces of Angular's internals, and understanding it changes how you think about the relationship between the template engine and the animation engine.
The conceptual explanation: When Angular's change detection processes @if (false) on an element that has an active animation trigger, it does not immediately destroy the element's view. Instead, the animation engine intercepts the "remove view" instruction and places the element in a leave animation queue. The element's DOM node is kept alive — but marked as leaving — while the transition plays. Only when the animation's onDone callback fires does the animation engine release the element and allow Angular to fully destroy the view and remove the node.
The Angular-specific implication: This means that for a brief window during a :leave animation, the DOM contains elements that Angular's component tree considers "destroyed". The element's component is in a destroyed state — lifecycle hooks will not fire, subscriptions should already be cleaned up. The DOM node is just being visually held by the animation engine as a courtesy to the user experience.
Practical rule to take away: Never rely on a component being accessible in code after @if evaluates to false, even if you can visually see it on screen during a leave animation. From Angular's perspective, that component is already gone. The animation engine is showing a ghost — a visual echo — of the destroyed view. This is also why you must ensure your subscription cleanup (via takeUntilDestroyed) happens correctly: the component's DestroyRef fires at logical destruction time, not at visual removal time.

Section 14 — Common Interview Questions
Question 1
"What is the difference between :enter and :leave animations, and what must be true in the template for them to fire?"
Strong answer covers:

:enter = void => * transition — fires when an element is added to the DOM
:leave = * => void transition — fires when an element is removed from the DOM
The element must be added/removed via @if (or *ngIf) — [hidden] keeps the element in the DOM and neither transition fires
Angular's animation engine holds the element in the DOM until the :leave animation completes before destroying the view
provideAnimations() must be registered for any of this to work

Weak answers typically miss: The critical @if requirement — many candidates know the :enter/:leave syntax but don't know it requires actual DOM addition/removal, not just visibility toggling.
Difficulty: Mid

Question 2
"How would you animate a list so that new items stagger in one after another with a 60ms delay between each?"
Strong answer covers:

The query() + stagger() pattern — trigger on the parent container, not individual items
The trigger value on the parent must change (e.g. bind to tasks.length) to fire * => *
query(':enter', [...]) targets only newly added child elements within the transition
stagger(60, [animate(...)]) applies a cumulative 60ms delay per child
{ optional: true } prevents a runtime error when the list is empty

Weak answers typically miss: That the trigger goes on the parent and that { optional: true } is required — most candidates know stagger exists but fumble the placement and the error handling.
Difficulty: Mid/Senior

Question 3
"In a production Angular app, a leave animation was working in development but disappeared in the production build. What would you investigate?"
Strong answer covers:

Check whether provideAnimations() is in the production app.config.ts (vs. provideNoopAnimations() accidentally left in a shared config)
Check whether @if is being used — [hidden] silently skips :leave
Check for any OnPush change detection issues: if the signal/input driving the @if isn't updating correctly in production (e.g. due to a missing signal() wrapper on a mutated object)
Check for SSR/Universal: if the app is server-rendered, animations require provideNoopAnimations() on the server and provideAnimations() only on the client
Check the animation module import in lazy-loaded feature routes — lazy chunks don't inherit the root provideAnimations() automatically in older patterns

Weak answers typically miss: The SSR angle and the provideNoopAnimations() accidental override — these are the two most common "works in dev, broken in prod" animation bugs.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Animating with [hidden] Instead of @if
typescript// ANTI-PATTERN
@Component({
  animations: [
    trigger('fade', [
      transition(':enter', [style({ opacity: 0 }), animate('300ms', style({ opacity: 1 }))]),
      transition(':leave', [animate('300ms', style({ opacity: 0 }))])
    ])
  ],
  template: `<div @fade [hidden]="!isVisible">Content</div>`  // ← broken
})
Why it seems fine: [hidden] does visually hide the element. The :enter animation even plays once (on component initialisation) making it appear to work.
What breaks in production: :leave never fires. The element snaps invisible instantly when isVisible becomes false. Additionally, a permanently hidden element stays in the DOM consuming memory and change detection cycles for the lifetime of the parent component — in large lists this is a measurable performance problem.
Correct pattern:
html@if (isVisible) {
  <div @fade>Content</div>

Section 16 — Mental Model Summary
30-Second Cheat Sheet — Angular Animations
Core concept in one sentence:

Angular Animations are a declarative state machine — you define named CSS states, declare how to transition between them with timing, bind a trigger to a signal or expression in the template, and Angular plays the correct animation automatically during change detection.
Key rules:

Register provideAnimations() once in app.config.ts — without it, all animations silently do nothing
:enter/:leave only fire on actual DOM addition/removal — use @if, never [hidden]
query() + stagger() triggers go on the parent container element, not on individual children
Always add { optional: true } to query(':enter', ...) on lists that may be empty
Extract reusable animation triggers into a shared animations.ts file — never copy-paste across components
Use provideNoopAnimations() in all unit test environments — real animations make DOM-state assertions unreliable

The single most important Angular rule:

:leave animations require @if — [hidden] keeps the element in the DOM and the leave animation will never fire.

Section 1 — Explanation (unchanged — verbatim, no DI or setup code in this section)
The Traffic Light Analogy
Imagine a traffic light. It has a fixed set of states (red, amber, green). At any moment it is always in exactly one state. When conditions change, it transitions from one state to another — and during that transition it does something visible (the light changes). The transition itself has a duration and a curve (instant, or a brief fade).
Angular Animations work exactly like this:

A state is a named snapshot of CSS properties (red = { backgroundColor: 'red' })
A transition is the rule for moving between two states ('red => green') and how long it takes
A trigger is the named container that groups states and transitions together and is attached to a host element in the template

The template binds the trigger like a property: [@trafficLight]="currentState". Whenever currentState changes in the component, Angular looks up the matching transition, calculates the interpolated CSS values between the two states, and plays the animation — all without you writing a single requestAnimationFrame or CSS keyframe.
Technical Explanation:
Angular Animations are powered by the Web Animations API (with a CSS fallback) and are provided through @angular/animations. The engine lives outside the core rendering pipeline, which is why you must explicitly register it as a provider in app.config.ts — and as of modern Angular, this registration should be done asynchronously via provideAnimationsAsync() rather than the older eager provideAnimations(), so the animations engine code is not pulled into the initial bundle for apps that only animate conditionally or later in the user journey.
The building blocks:
FunctionPurposeWhere it livestrigger(name, [...])Names and groups states + transitionsanimations: [] metadatastate(name, style({}))Defines CSS properties for a named stateInside trigger()transition('a => b', [...])Defines what happens when moving from state a to bInside trigger()animate('duration easing', style({}))Defines timing and optional end-style for a transitionInside transition()keyframes([...])Multi-step animation with explicit percentage checkpointsInside animate()query(selector, [...])Targets child elements inside a parent animationInside transition()stagger(delay, [...])Adds sequential delay between a list of animated childrenInside query()group([...])Runs multiple animations in parallelInside transition()sequence([...])Runs multiple animations one after anotherInside transition()
The two special wildcard states:

* — matches any state (including void)
void — the state of an element that is not in the DOM (before it enters or after it leaves)

This gives you the two most common patterns:

'void => *' = element enters the DOM (aliased as :enter)
'* => void' = element leaves the DOM (aliased as :leave)

Section 5 — Common Mistakes & Misconceptions (REWRITTEN — Mistake 1 updated to reflect provideAnimationsAsync())
Mistake 1 — Forgetting provideAnimationsAsync() in app.config.ts
What the mistake looks like: Animations are defined correctly in the component but nothing animates. No error is thrown.
Why developers make it: In older Angular (NgModule-based), you imported BrowserAnimationsModule in AppModule. In standalone Angular, you call provideAnimationsAsync() in app.config.ts. Developers porting code or following old tutorials still reach for BrowserAnimationsModule, or use the older eager provideAnimations(), neither of which reflects current best practice for bundle size.
How to avoid it: When you add animations: [...] to your first component, immediately check app.config.ts for provideAnimationsAsync(). If you want to disable animations in tests, use provideNoopAnimations() instead.
Angular-specific consequence: Animations silently do nothing — the element still shows/hides, but all transitions are skipped. The bug looks identical to an animation timing issue, wasting debugging time. Using the older BrowserAnimationsModule additionally pulls NgModule machinery into an otherwise fully standalone app for no functional benefit, and using eager provideAnimations() instead of the async variant unnecessarily inflates the initial bundle.

Mistake 2 — Using [hidden] Instead of @if for Enter/Leave Animations (unchanged — verbatim)
What the mistake looks like:
html<!-- WRONG: [hidden] keeps the element in the DOM — :leave never fires -->
<div @fade [hidden]="!isVisible">Content</div>
Why developers make it: [hidden] feels like toggling visibility. Developers assume Angular's animation engine watches visibility, not DOM presence.
How to avoid it: :enter and :leave are triggered exclusively by elements being added to or removed from the DOM. Only @if (or *ngIf) actually removes the element. Use @if for any component that needs enter/leave animations.
Angular-specific consequence: The element appears and disappears instantly with no animation despite a correctly written trigger — the :leave animation never fires because the element never leaves the DOM.

Mistake 3 — Putting the query() Trigger on the Child Instead of the Parent (unchanged — verbatim)
What the mistake looks like:
html<!-- WRONG: trigger on each list item — stagger won't work -->
@for (task of tasks(); track task.id) {
  <li [@listAnimation]="...">{{ task.title }}</li>
}
Why developers make it: It seems logical to animate each item individually.
How to avoid it: The query() and stagger() functions work by querying child elements from a parent trigger. The trigger must go on the container element; query(':enter', ...) then finds all entering children within that container.
Angular-specific consequence: The stagger never applies — each item animates independently and simultaneously, defeating the cascading effect entirely.

Section 7 — Debugging Tips (REWRITTEN — Bug 1 updated)
Bug 1 — Animations Defined but Nothing Animates
Symptom: Component renders and elements show/hide correctly but no animation plays. No console errors.
Plain English Cause: Either provideAnimationsAsync() is missing from app.config.ts, the deprecated BrowserAnimationsModule is still being imported instead, or provideNoopAnimations() has been added (which silently disables all animations — often left in from test configuration).
Fix:
typescript// app.config.ts
import { provideAnimationsAsync } from '@angular/platform-browser/animations/async';

export const appConfig: ApplicationConfig = {
  providers: [
    provideAnimationsAsync()  // ← ensure this is present, not provideNoopAnimations()
                               //   and not the legacy eager provideAnimations()
  ]
};
Angular-specific note: If you migrated from NgModule, check that BrowserAnimationsModule in AppModule was replaced with provideAnimationsAsync() — not just removed, and not replaced with the older synchronous provideAnimations(), which forgoes the lazy-loading benefit.

Bug 2 — query(':enter', ...) threw error: No elements found (unchanged — verbatim)
Symptom: Runtime error in the console: ANIMATION: Could not find elements matching selector or similar when the list is rendered empty initially.
Plain English Cause: query() throws by default if the CSS selector matches zero elements. When a list first renders empty, query(':enter', ...) finds nothing.
Fix:
typescriptquery(':enter', [
  style({ opacity: 0 }),
  stagger(60, [animate('300ms', style({ opacity: 1 }))])
], { optional: true })  // ← this one flag prevents the error
Angular-specific note: Always add { optional: true } to any query() that targets :enter or :leave on dynamically loaded lists that could be empty on initialisation.

Bug 3 — Leave Animation Skipped, Element Disappears Instantly (unchanged — verbatim)
Symptom: The enter animation plays correctly but elements disappear with no transition when removed.
Plain English Cause: The element is being hidden with [hidden], display: none, or a CSS class toggle rather than being removed from the DOM via @if. Angular's :leave trigger only fires on actual DOM removal.
Fix:
html<!-- REPLACE THIS: -->
<div @myTrigger [hidden]="!show">Content</div>

<!-- WITH THIS: -->
@if (show) {
  <div @myTrigger>Content</div>
}
Angular-specific note: The distinction between "hidden in the DOM" and "removed from the DOM" is one of the most fundamental Angular animation concepts. :leave = DOM removal, always.

Scenario 1 — Animated Modal / Dialog Overlay
A UX requirement on a SaaS dashboard: modals must slide up from the bottom on open and fade down on close. The modal is managed by a signal in a layout component.
typescript// modal.component.ts
import { trigger, transition, style, animate, group } from '@angular/animations';

@Component({
  selector: 'app-modal',
  standalone: true,
  animations: [
    trigger('modalAnimation', [
      transition(':enter', [
        group([
          // Backdrop fades in
          query('.backdrop', [
            style({ opacity: 0 }),
            animate('200ms ease-out', style({ opacity: 1 }))
          ]),
          // Panel slides up
          query('.panel', [
            style({ opacity: 0, transform: 'translateY(40px)' }),
            animate('250ms 50ms ease-out',  // 50ms delay lets backdrop appear first
              style({ opacity: 1, transform: 'translateY(0)' }))
          ])
        ])
      ]),
      transition(':leave', [
        group([
          query('.backdrop', [animate('200ms ease-in', style({ opacity: 0 }))]),
          query('.panel', [animate('150ms ease-in',
            style({ opacity: 0, transform: 'translateY(20px)' }))])
        ])
      ])
    ])
  ],
  template: `
    @if (isOpen()) {
      <div @modalAnimation class="modal-host">
        <div class="backdrop" (click)="close()"></div>
        <div class="panel">
          <ng-content />
        </div>
      </div>
    }
  `
})
export class ModalComponent {
  isOpen = input.required<boolean>();
  closed = output<void>();

  close() { this.closed.emit(); }
}
Why Angular Animations and not CSS: The backdrop and panel must animate in a coordinated sequence. CSS cannot express "animate child A then child B with a 50ms delay" declaratively. group() + query() handles this exactly.
