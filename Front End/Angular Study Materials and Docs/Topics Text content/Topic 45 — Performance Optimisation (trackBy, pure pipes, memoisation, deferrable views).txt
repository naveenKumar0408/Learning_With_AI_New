Topic 45 — Performance Optimisation (trackBy, pure pipes, memoisation, deferrable views)

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — Each individual technique is approachable, but the skill is knowing which problem each technique solves and when applying one without the others leaves performance on the table; the interactions between OnPush, signals, pure pipes, and deferrable views require a unified mental model.
Angular Relevance: Critical — Performance problems in Angular almost always trace back to a small set of well-known patterns; knowing these techniques separates developers who build fast apps from those who build apps that feel sluggish at scale, and every senior Angular interview touches this topic directly.

Section 1 — Explanation
The Restaurant Kitchen Analogy
Imagine a restaurant kitchen during a busy service. An inefficient kitchen re-cooks every dish from scratch every time the head chef walks through — even if the dish hasn't been ordered again. A well-run kitchen:

Only re-cooks dishes that were actually ordered (OnPush change detection — Topic 24)
Remembers the recipe result so identical orders skip the cooking step (pure pipes + memoisation)
Doesn't start cooking the dessert menu until a table actually orders dessert (deferrable views)
Knows which specific dish changed on a tray instead of replacing the whole tray (trackBy)

Angular's default behaviour is the inefficient kitchen — it re-checks everything on every event. Each technique in this topic is one discipline that makes the kitchen run efficiently.
The Four Techniques — Overview:
TechniqueProblem it solvesWhere it appliestrackBy / trackDOM thrashing when lists re-render@for loops with dynamic dataPure pipesRedundant transform recalculationTemplate expressions that transform dataMemoisationExpensive function re-executionComponent methods called in templatesDeferrable views (@defer)Blocking render with off-screen contentBelow-the-fold or conditionally shown components
These four techniques address different layers of the rendering pipeline. In a real app you apply all four — they are complementary, not alternatives.

Bridging Note:

In Topic 24 you learned that OnPush skips a component's re-render unless its inputs change by reference. The techniques in this topic extend that discipline further down the rendering stack: trackBy prevents unnecessary DOM node recreation inside a list that OnPush is already protecting at the component level; pure pipes prevent unnecessary transform recalculation inside the template expressions that OnPush is already limiting to changed inputs; @defer prevents the component from entering the rendering pipeline at all until it's needed.
Most directly extends: Topic 24 — OnPush Change Detection (all four techniques are downstream optimisations of the same reference-equality mental model).

Section 3 — Code Example
Technique 1 — track in @for (replaces trackBy)
typescript// Without track — Angular destroys and recreates every DOM node on every list update
// Even if only one item changed, all 100 <li> elements are torn down and rebuilt

// With track — Angular matches existing DOM nodes to new data by identity
// Only the changed/added/removed items touch the DOM

@Component({
  standalone: true,
  template: `
    <!-- BAD: no track — full DOM rebuild on every change -->
    @for (item of items(); ) {
      <app-item [data]="item" />
    }

    <!-- GOOD: track by stable unique ID — only changed nodes are touched -->
    @for (item of items(); track item.id) {
      <app-item [data]="item" />
    }
  `
})
export class ListComponent {
  items = signal<Item[]>([]);
}
typescript// When track by index is acceptable vs. when it breaks things:

// ACCEPTABLE: static list that never reorders and items have no internal state
@for (label of ['Home', 'About', 'Contact']; track $index) {
  <li>{{ label }}</li>
}

// BREAKS: dynamic list where items reorder or have child components with state
// If items reorder, $index changes but the DOM node stays — child component
// receives wrong @Input() data while retaining its previous internal state
@for (user of sortedUsers(); track $index) {  // ← dangerous with reordering
  <app-user-card [user]="user" />             // card may show wrong user data
}

// ALWAYS CORRECT: stable unique ID from the data
@for (user of sortedUsers(); track user.id) {
  <app-user-card [user]="user" />
}

Technique 2 — Pure Pipes as a Performance Tool
typescript// The problem: method calls in templates run on EVERY change detection cycle
@Component({
  template: `
    <!-- BAD: getFilteredItems() runs on every mousemove, keydown, timer tick -->
    @for (item of getFilteredItems(); track item.id) {
      <app-item [data]="item" />
    }
  `
})
export class ListComponent {
  items = signal<Item[]>([]);
  filter = signal('');

  getFilteredItems(): Item[] {              // called every CD cycle
    return this.items().filter(i =>
      i.name.includes(this.filter())
    );
  }
}
typescript// The fix: pure pipe — Angular memoises the result, only recalculates
// when items() reference or filter() value changes

@Pipe({ name: 'filterItems', standalone: true, pure: true })
export class FilterItemsPipe implements PipeTransform {
  transform(items: Item[] | null, query: string): Item[] {
    if (!items) return [];
    if (!query) return items;
    return items.filter(i => i.name.toLowerCase().includes(query.toLowerCase()));
  }
}

@Component({
  standalone: true,
  imports: [FilterItemsPipe],
  template: `
    <!-- GOOD: transform() only called when items signal or filter signal changes -->
    @for (item of (items() | filterItems : filter()); track item.id) {
      <app-item [data]="item" />
    }
  `
})
export class ListComponent {
  items = signal<Item[]>([]);
  filter = signal('');
}

Technique 3 — Memoisation for Expensive Computations
typescript// When a pure pipe isn't applicable (e.g. in TypeScript logic, not templates),
// use computed() for signal-based memoisation

@Injectable({ providedIn: 'root' })
export class ReportStore {
  readonly #transactions = signal<Transaction[]>([]);
  readonly transactions = this.#transactions.asReadonly();

  // computed() memoises — only recalculates when #transactions signal changes
  // Without computed(), this runs every time any signal in the app changes
  readonly monthlyTotals = computed(() => {
    console.log('Recalculating monthly totals...');  // should log rarely
    return this.#transactions().reduce((acc, t) => {
      const month = t.date.slice(0, 7);  // 'YYYY-MM'
      acc[month] = (acc[month] ?? 0) + t.amount;
      return acc;
    }, {} as Record<string, number>);
  });

  readonly topCategory = computed(() => {
    // This expensive calculation also only runs when transactions change
    const counts = this.#transactions().reduce((acc, t) => {
      acc[t.category] = (acc[t.category] ?? 0) + 1;
      return acc;
    }, {} as Record<string, number>);
    return Object.entries(counts).sort((a, b) => b[1] - a[1])[0]?.[0] ?? 'none';
  });
}

Technique 4 — Deferrable Views (@defer)
typescript// @defer — the most powerful performance tool in modern Angular
// Splits the component from the main bundle AND delays rendering

@Component({
  standalone: true,
  template: `
    <!-- Above the fold: renders immediately, in the main bundle -->
    <app-hero-banner />
    <app-featured-products />

    <!-- Below the fold: deferred until the user scrolls to this area -->
    @defer (on viewport) {
      <!-- HeavyAnalyticsComponent and its entire dependency tree are:
           1. Split into a separate lazy chunk (automatic code splitting)
           2. Not downloaded until the user scrolls here
           3. Not rendered until downloaded -->
      <app-heavy-analytics-dashboard />

      @placeholder {
        <!-- Shown BEFORE the deferred block loads — must be lightweight -->
        <div class="skeleton" style="height: 400px;"></div>
      }

      @loading (minimum 300ms) {
        <!-- Shown WHILE the chunk is downloading -->
        <!-- minimum 300ms prevents flash if download is fast -->
        <app-spinner />
      }

      @error {
        <!-- Shown if the chunk fails to download -->
        <p>Failed to load analytics. <button (click)="retry()">Retry</button></p>
      }
    }

    <!-- Defer with multiple triggers -->
    @defer (on idle; on viewport; prefetch on hover) {
      <!-- on idle: loads when browser is idle (requestIdleCallback) -->
      <!-- on viewport: also triggers on scroll into view -->
      <!-- prefetch on hover: pre-downloads chunk when user hovers nearby -->
      <app-recommendations />
      @placeholder { <div class="skeleton"></div> }
    }
  `
})
export class HomePageComponent {}
typescript// @defer with interaction trigger and manual control

@Component({
  standalone: true,
  template: `
    <button (click)="showComments.set(true)">Show Comments</button>

    <!-- on interaction — loads when the user clicks/focuses the placeholder -->
    @defer (when showComments()) {
      <app-comment-thread [postId]="postId()" />
      @placeholder {
        <div class="comments-placeholder">Click to load comments</div>
      }
    }
  `
})
export class ArticleComponent {
  postId = input.required<number>();
  showComments = signal(false);
}

Section 4 — Before & After Refactor
❌ Before — A Typical Unoptimised List Component
typescript@Component({
  changeDetection: ChangeDetectionStrategy.Default,  // re-checks everything always
  template: `
    <!-- No track: full DOM rebuild on every data change -->
    @for (product of getFilteredProducts(); ) {
      <!-- getFilteredProducts() is a method — runs every CD cycle -->
      <app-product-card [product]="product" />
    }

    <!-- Heavy chart component always rendered, always in the bundle -->
    <app-sales-chart [data]="salesData" />
  `
})
export class ProductListComponent {
  products: Product[] = [];
  searchQuery = '';
  salesData: SalesData[] = [];

  getFilteredProducts(): Product[] {
    // Runs on every mousemove, every keypress anywhere in the app
    // With 1,000 products, this is 1,000 filter evaluations per event
    return this.products.filter(p =>
      p.name.toLowerCase().includes(this.searchQuery.toLowerCase())
    );
  }
}
What breaks at scale: 1,000 products × every CD cycle = the filter() runs hundreds of times per second during typing. No track means 1,000 DOM nodes are destroyed and recreated on every keystroke. app-sales-chart is always in the main bundle and always rendered even if the user never scrolls to it. With Default change detection, the component re-checks on every event in the entire app.

✅ After — All Four Optimisations Applied
typescript@Pipe({ name: 'filterProducts', standalone: true, pure: true })
export class FilterProductsPipe implements PipeTransform {
  transform(products: Product[], query: string): Product[] {
    if (!products) return [];
    if (!query) return products;
    const lower = query.toLowerCase();
    return products.filter(p => p.name.toLowerCase().includes(lower));
  }
}

@Component({
  standalone: true,
  imports: [FilterProductsPipe],
  changeDetection: ChangeDetectionStrategy.OnPush,  // only re-checks on input changes
  template: `
    <!-- Pure pipe: transform() only runs when products or searchQuery changes -->
    <!-- track item.id: only changed DOM nodes are updated -->
    @for (product of (products() | filterProducts : searchQuery()); track product.id) {
      <app-product-card [product]="product" />
    }

    <!-- @defer: chart is lazy-loaded and only rendered when scrolled into view -->
    @defer (on viewport) {
      <app-sales-chart [data]="salesData()" />
      @placeholder { <div class="chart-skeleton"></div> }
      @loading { <app-spinner /> }
    }
  `
})
export class ProductListComponent {
  products  = input.required<Product[]>();
  salesData = input.required<SalesData[]>();
  searchQuery = signal('');
}
Why this refactor matters:

OnPush → component only re-checks when products or salesData inputs change by reference
Pure pipe → filter() only runs when the products array reference or searchQuery string changes
track product.id → only the specific DOM nodes that changed are updated, not all 1,000
@defer (on viewport) → the chart component is excluded from the initial bundle and not rendered until the user scrolls to it; first meaningful paint is dramatically faster


Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Using track $index on Dynamic Lists
What the mistake looks like:
html@for (user of sortedUsers(); track $index) {
  <app-user-card [user]="user" />
}
Why developers make it: $index is available automatically and feels like a natural unique identifier. It also silences any linting warnings about missing track.
How to avoid it: track $index is only safe when the list never reorders and items have no internal component state. For any list that sorts, filters, or reorders, use track item.id (or another stable identity from the data).
Angular-specific consequence: When the list reorders, index 0 might now point to a different item. Angular keeps the DOM node for index 0 alive and passes the new item as @Input() to the existing component instance — but that component instance still holds the previous item's internal state (form values, expansion state, selection). The visible data and the component state silently diverge.

Mistake 2 — Treating @defer as a Substitute for All Performance Work
What the mistake looks like:
typescript// Developer wraps everything in @defer, skips OnPush, skips track, skips pure pipes
@defer (on viewport) {
  <!-- Still no track, no OnPush, no pure pipes inside -->
  <app-slow-list [items]="items" />
}
Why developers make it: @defer is visually dramatic — it clearly splits the bundle and defers loading. It feels like "doing performance work." The other techniques are invisible.
How to avoid it: @defer delays initial load — it has no effect once the component is rendered. After the deferred block loads, all the same OnPush / track / pure pipe rules apply inside it. All four techniques are complementary and address different phases: @defer = load time; OnPush + signals = render time; track = DOM update time; pure pipes = computation time.
Angular-specific consequence: The app loads fast (thanks to @defer) but becomes sluggish as soon as the deferred component renders, because all the runtime performance problems still exist inside it.

Mistake 3 — Calling Expensive Methods in Templates Instead of Using computed() or Pure Pipes
What the mistake looks like:
html<!-- BAD: formatReport() is called on every change detection cycle -->
<div>{{ formatReport(reportData) }}</div>
<span>{{ calculateTotal(items) }}</span>
Why developers make it: Method calls in templates are convenient and feel like the natural Angular way, especially for simple transformations. Developers don't realise that Angular treats template method calls as volatile expressions — it cannot memoize them.
How to avoid it: Any template expression that transforms data should be a pure pipe (for reusability) or a computed() signal (for TypeScript logic). Reserve template method calls for event handlers only — never for value derivation.
Angular-specific consequence: With Default change detection, formatReport() runs on every mouse movement anywhere in the app. With OnPush, it still runs on every input change to this component. With 50 rows each calling two methods, that's 100 function calls per CD cycle — measurable frame drops during scrolling or typing in any nearby input.

Section 7 — Debugging Tips
Bug 1 — List Items Show Wrong Data After Reordering
Symptom: After sorting or filtering a list, some items display data from the wrong item, or child components show a previous item's expanded/selected state despite the data changing correctly.
Plain English Cause: track $index is being used on a list that reorders. Angular matches DOM nodes to new data by index, so when the sort order changes, existing component instances receive new @Input() data but retain their previous internal state.
Fix:
html<!-- Replace: -->
@for (item of sortedItems(); track $index) { ... }

<!-- With: -->
@for (item of sortedItems(); track item.id) { ... }
Angular-specific note: This bug is invisible in development with short lists but becomes obvious with longer lists or complex child components. Always audit track usage when implementing sort or filter functionality.

Bug 2 — @defer Block Never Loads / Stays on @placeholder Forever
Symptom: The deferred component never appears. The @placeholder is always visible even after the trigger condition is met.
Plain English Cause (most common): The trigger is on viewport but the @placeholder has zero height (height: 0 or no content). The Intersection Observer sees a zero-height element as "in viewport" immediately, but subsequent Angular rendering skips the load because the element has no visible area to observe.
Plain English Cause (second common): provideNoopAnimations() was accidentally applied in a way that also disabled the browser APIs that @defer relies on in the test environment, and the test configuration leaked into development.
Fix:
html@defer (on viewport) {
  <app-heavy-component />
  @placeholder {
    <!-- Give the placeholder real dimensions matching the deferred content -->
    <div style="height: 400px; width: 100%;"></div>
  }
}
Angular-specific note: Always give @placeholder meaningful dimensions. It serves double duty: triggering the Intersection Observer correctly AND preventing cumulative layout shift (CLS) when the real component loads.

Bug 3 — Pure Pipe Not Updating After Store Data Changes
Symptom: A filtered list stops updating after new items are added via a store write method.
Plain English Cause: The store's array is being mutated in place (this.#items().push(item) or a direct mutation inside update()), so the signal's reference doesn't change, and the pure pipe's memoisation cache returns the stale result.
Fix:
typescript// WRONG — mutates in place, pure pipe doesn't see a new reference:
addItem(item: Item) {
  this.#items.update(curr => {
    curr.push(item);   // ← mutates the existing array
    return curr;       // ← returns the same reference
  });
}

// CORRECT — new reference on every update:
addItem(item: Item) {
  this.#items.update(curr => [...curr, item]);  // new array reference
}
Angular-specific note: This is the same bug from Topic 42 (pure pipe + mutation), now appearing at the store layer. The fix is always at the mutation site — enforce immutable updates in every store write method.

Section 8 — Real-World Applications
Scenario 1 — High-Performance Data Table with 10,000 Rows
A CRM application renders a paginated, sortable, filterable table of contacts. Initial implementation was sluggish during sort and filter operations.
typescript@Pipe({ name: 'sortAndFilter', standalone: true, pure: true })
export class SortAndFilterPipe implements PipeTransform {
  transform(contacts: Contact[], query: string, sortField: keyof Contact, sortDir: 'asc' | 'desc'): Contact[] {
    if (!contacts) return [];

    let result = query
      ? contacts.filter(c =>
          c.name.toLowerCase().includes(query.toLowerCase()) ||
          c.email.toLowerCase().includes(query.toLowerCase())
        )
      : contacts;

    return [...result].sort((a, b) => {
      const comparison = String(a[sortField]).localeCompare(String(b[sortField]));
      return sortDir === 'asc' ? comparison : -comparison;
    });
  }
}

@Component({
  standalone: true,
  imports: [SortAndFilterPipe],
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <input [value]="query()" (input)="query.set($any($event.target).value)" />

    <!-- Pure pipe: sort+filter only recalculates when contacts, query, or sort changes -->
    <!-- track contact.id: only changed rows touch the DOM -->
    @for (
      contact of (contacts() | sortAndFilter : query() : sortField() : sortDir());
      track contact.id
    ) {
      <app-contact-row [contact]="contact" />
    }
  `
})
export class ContactTableComponent {
  contacts  = input.required<Contact[]>();
  query     = signal('');
  sortField = signal<keyof Contact>('name');
  sortDir   = signal<'asc' | 'desc'>('asc');
}
Result: Sort and filter operations go from re-running on every CD cycle to running only when contacts, query, sortField, or sortDir change. DOM updates touch only the rows that actually changed position.

Section 10 — Key Takeaways
Core concepts in plain English:

track tells Angular how to match existing DOM nodes to updated data — without it, the entire list is torn down and rebuilt on every change
Pure pipes cache their last result and only recalculate when input references change — method calls in templates have no such cache
computed() is Angular's built-in memoisation for signal-derived values — it recalculates only when its signal dependencies change
@defer splits a component into a separate lazy chunk AND delays its rendering until a trigger fires — it addresses both bundle size and render cost
These four techniques operate at different phases: load time (@defer), component render time (OnPush + signals), DOM update time (track), computation time (pure pipes + computed())

Angular-specific rules:

track is required syntax in @for — always use a stable entity ID, not $index for dynamic lists

@defer automatically code-splits the deferred component — no extra loadComponent() call needed
@placeholder must have realistic dimensions to prevent CLS and to correctly trigger on viewport
@loading (minimum Xms) prevents loading-state flicker for fast connections — always set a minimum

One-Line Memory Aid:

Load less (@defer), render less (OnPush + signals), compute less (pure pipes + computed()), patch less (track) — apply all four, in every list-heavy component.


Section 11 — Thought-Provoking Question + Answer
Question: @defer automatically code-splits the deferred component into a separate chunk. But Angular's lazy loading via loadComponent() in the router (Topic 40) also code-splits. What is the actual difference, and when should you use one versus the other?
Answer:
This question reveals that code splitting has two different axes: when to split and what triggers the load. Understanding both axes clarifies why Angular has two different mechanisms.
The conceptual explanation:
loadComponent() in the router is route-driven splitting. The split boundary is a navigation event — the user navigates to a URL, the router downloads the component, and the component renders. The unit of splitting is a page. The trigger is always a route change.
@defer is render-driven splitting. The split boundary is a template condition — a viewport intersection, a user interaction, a signal turning true, or the browser going idle. The unit of splitting is any component or component tree, regardless of routing. The trigger is configurable.
The Angular-specific implication:
Use loadComponent() / loadChildren() when the split maps to a route boundary — a whole page that the user navigates to. This is the right tool for splitting a /dashboard page from a /settings page because the user can only see one at a time.
Use @defer when the split is within a single page/route — content that is on the same page but not immediately visible or needed. Heavy charts below the fold, comment sections, recommendation engines, rich text editors that only open on interaction — these live on the same route but don't need to be in the initial render.
Practical rule: Router lazy loading and @defer are complementary. A production app uses both: loadChildren() to split routes into separate chunks, and @defer within those route components to split heavy sub-components within each page. The @defer block inside a lazy-loaded route component produces its own further-nested chunk — the two mechanisms compose naturally.
The key question to ask: "Is this a separate page, or is this heavy content within a page?" Page → router lazy loading. Content within a page → @defer.

Section 14 — Common Interview Questions
Question 1
"Why can using track $index in an @for loop cause bugs, and when is it actually safe?"
Strong answer covers:

track $index uses the array position as the DOM node identity
When the list reorders (sort, filter, reverse), the index of each item changes but the DOM node stays in place — Angular updates @Input() on the existing component but the component's internal state (form values, expanded state, selection) belongs to the previous item
Safe only for: static lists that never reorder, primitive value lists with no child component state, lists where items have no internal state at all
Always prefer track item.id or another stable server-assigned identifier

Weak answers typically miss: The internal component state problem — most candidates know $index is "bad" but can't explain exactly what breaks and why.
Difficulty: Mid

Question 2
"What is the difference between @defer (on viewport) and route-based lazy loading, and when do you use each?"
Strong answer covers:

Route lazy loading splits at page/route boundaries — triggered by navigation
@defer splits at component boundaries within a page — triggered by viewport, idle, interaction, or a signal condition
They are complementary — a lazy-loaded route can contain @defer blocks for further within-page splitting
@defer also handles the render lifecycle (placeholder, loading, error states) which route lazy loading does not
Use route splitting for separate pages; use @defer for heavy content within a page

Weak answers typically miss: That the two mechanisms compose — candidates often treat them as alternatives rather than complementary tools.
Difficulty: Mid/Senior

Question 3
"A developer reports that their Angular app is slow during user input in a search box. The component uses OnPush. What would you investigate and what fixes would you apply?"
Strong answer covers:

Check for template method calls that return filtered/sorted arrays — these run every CD cycle even with OnPush, because the input that triggers OnPush is the search query itself
Replace method calls with a pure pipe — the pipe's memoisation skips recalculation if the query string hasn't changed between CD cycles
Check track on any @for loops in the search results — without it, every keystroke rebuilds the entire DOM
Check whether any child components inside the results list also lack OnPush
Mention debounceTime on the search input observable/signal to reduce how often the filter runs at all
Mention @defer for any heavy components in the results that aren't immediately visible

Weak answers typically miss: The pure pipe fix — most candidates jump to debounceTime or virtual scrolling without identifying the root cause (method calls in templates).
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Template Method Calls for Data Transformation
typescript// ANTI-PATTERN
@Component({
  template: `
    @for (item of getProcessedItems(); track item.id) {
      <app-item [data]="item" />
    }
    <span>Total: {{ calculateTotal() }}</span>
  `
})
export class DashboardComponent {
  items = input.required<Item[]>();

  getProcessedItems(): Item[] {
    return this.items()
      .filter(i => i.active)
      .sort((a, b) => b.priority - a.priority);
  }

  calculateTotal(): number {
    return this.items().reduce((sum, i) => sum + i.value, 0);
  }
}
Why it seems fine: Method calls in templates are natural, readable, and work correctly.
What breaks at scale: With Default CD, getProcessedItems() and calculateTotal() run on every mouse move. With OnPush, they run on every input change. With 500 items, this is 500 filter evaluations + 500 reduce evaluations per CD cycle — measurable CPU usage during any interaction.
Correct pattern:
typescript// Use computed() for signal-based derivation:
processedItems = computed(() =>
  this.items().filter(i => i.active).sort((a, b) => b.priority - a.priority)
);
total = computed(() => this.items().reduce((sum, i) => sum + i.value, 0));

// Template:
// @for (item of processedItems(); track item.id) { ... }
// <span>Total: {{ total() }}</span>

Anti-Pattern 2 — @defer Without Placeholder Dimensions
typescript// ANTI-PATTERN
@Component({
  template: `
    <app-header />
    <app-main-content />

    @defer (on viewport) {
      <app-analytics-widget />
      @placeholder { }  <!-- empty placeholder -->
    }
  `
})
Why it seems fine: The deferred component loads correctly. Everything looks fine in development on a fast connection.
What breaks in production: An empty placeholder has zero height. The Intersection Observer triggers immediately (a zero-height element at the bottom of the DOM is technically "in viewport"). More critically, when the analytics widget loads and takes 400px of height, the entire page content below it shifts down — a Cumulative Layout Shift (CLS) score penalty that degrades Core Web Vitals and hurts SEO rankings. On slow connections, the page visually "jumps" as each widget loads.
Correct pattern:
html@defer (on viewport) {
  <app-analytics-widget />
  @placeholder {
    <!-- Match the expected dimensions of the deferred component -->
    <div style="height: 400px; width: 100%; background: #f5f5f5; border-radius: 8px;"></div>
  }
  @loading (minimum 300ms) {
    <app-skeleton height="400" />
  }
}

Anti-Pattern 3 — Applying @defer to Components That Are Already Lazy-Loaded via the Router
typescript// ANTI-PATTERN: unnecessary double-deferral
// This route is already lazy-loaded via loadComponent() in the router
// app.routes.ts: { path: 'settings', loadComponent: () => import('./settings.component') }

// Inside SettingsComponent (already lazy):
@Component({
  template: `
    <!-- This form is already in a lazy chunk — @defer adds nothing here -->
    @defer (on viewport) {
      <app-settings-form />   <!-- small, simple form — not worth deferring -->
      @placeholder { <div style="height: 50px"></div> }
    }
  `
})
export class SettingsComponent { }
Why it seems fine: More deferral seems like more performance. @defer is always beneficial.
What breaks at scale: @defer adds a placeholder → loading state → component swap lifecycle. For small, fast-rendering components (a settings form, a simple card), this lifecycle adds a visible flash of placeholder/loading that is worse UX than just rendering eagerly. @defer is only beneficial when the deferred component is genuinely heavy (large JS dependencies, complex rendering) and not immediately visible.
Correct pattern: Apply @defer only to components that are: (a) not immediately visible on page load, AND (b) heavy enough that the split is worth the placeholder/loading lifecycle. Rule of thumb: if the component renders in under 50ms and has no large dependencies, render it eagerly.

Section 16 — Mental Model Summary
30-Second Cheat Sheet — Performance Optimisation
Core concept in one sentence:

Angular performance is about doing less work at every phase — less to load (@defer), less to render (OnPush + signals), less to compute (pure pipes + computed()), and less DOM to patch (track) — and each technique is targeting a different phase of the rendering pipeline.
Key rules:

Always use track item.id (stable entity ID) on dynamic lists — never track $index on sortable/filterable data
Replace template method calls that return transformed data with pure pipes or computed() signals
Apply @defer (on viewport) to every heavy component that starts below the fold
Always give @placeholder real dimensions matching the deferred content — prevents layout shift
@defer addresses load time only — OnPush, track, and pure pipes are still required inside deferred blocks
All four techniques are complementary — applying only one leaves the other three phases unoptimised

The single most important Angular rule:

Template method calls that transform data are never memoised — replace them with pure pipes or computed() signals; this is the single most common source of Angular performance problems in production.

Core concepts in plain English:

Section 11 — Thought-Provoking Question + Answer (REWRITTEN — new question replacing the original, since the audit specifically calls out that zoneless was entirely absent from this topic's deep-dive content)
Question: This topic treats OnPush as a performance technique alongside track, pure pipes, and @defer. But under provideExperimentalZonelessChangeDetection(), is OnPush still just a performance technique — or has its role fundamentally changed?
Answer:
This question matters because the original framing of OnPush as "one optimisation among several" is accurate under Zone.js but becomes misleading under zoneless Angular.
The conceptual explanation: Under Zone.js, every component — OnPush or not — eventually gets checked, because Zone.js patches async browser APIs broadly and schedules a full tree check after virtually anything happens. OnPush's job in that world is purely to let Angular skip components whose inputs haven't changed by reference, saving work during that broad sweep. The component will always eventually be considered for a check; OnPush just makes that check a fast no-op.
Under provideExperimentalZonelessChangeDetection(), there is no broad sweep. Angular instead relies on explicit signals: a write to a signal(), a markForCheck() call, or specific framework-internal notifications (like an @Input() binding update or an event handler firing) are what schedule a check at all. A component that mutates a plain class property — this.count++ instead of this.count.update(c => c + 1) — and is not otherwise notified through one of these channels may never be re-checked, because nothing told Angular a check was needed. There is no fallback sweep coming along five seconds later to catch the inconsistency.
The Angular-specific implication: This means OnPush plus signal-driven state isn't really "a performance technique" under zoneless — it's closer to "the API contract for how the view stays in sync with the model at all." A component using ChangeDetectionStrategy.Default and mutating plain properties might happen to render correctly under zoneless if change happens to occur inside a context Angular is already tracking (an event handler it's currently dispatching, for instance), but this is fragile and implementation-dependent rather than guaranteed.
Practical rule: Treat every technique in this topic — but especially OnPush and signal-driven @for/pure-pipe inputs — as the baseline architecture for any component you write today, regardless of whether your app currently runs Zone.js or zoneless. Components built this way port to zoneless with zero changes. Components that rely on Zone.js's broad sweep to "eventually" pick up a mutated plain property will need to be rewritten the day the app flips provideExperimentalZonelessChangeDetection() on — and that rewrite is exactly the OnPush + signals discipline this topic already teaches. Building it correctly now is strictly cheaper than retrofitting it later.
