Topic 52 — NgRx Effects

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate-Advanced — The concept is straightforward (listen to actions, do async work, dispatch new actions), but the operator choice (switchMap vs concatMap vs exhaustMap) has silent, destructive consequences in production that are non-obvious until you know exactly what each one cancels.
Angular Relevance: Critical — Every real NgRx app has HTTP calls, navigation, analytics, and error handling that must live outside reducers; Effects are the only correct place for all of it, and getting the operator choice wrong is the most common source of data loss bugs in production NgRx applications.

Section 1 — Explanation
The Personal Assistant Analogy
Imagine your NgRx Store is a CEO. The CEO only does one thing: makes decisions based on information (reducers computing state). The CEO never picks up the phone, never emails clients, never fetches documents — that's beneath the role and would distract from decision-making.
So the CEO has a personal assistant (an Effect). The assistant listens in on all meetings (listens to dispatched actions), and whenever a relevant topic comes up — say, "we need the Q3 report" — the assistant quietly leaves the room, makes the phone calls, fetches the document, and returns with either "here's the report" (loadReportsSuccess) or "the server was down" (loadReportsFailure). The CEO (reducer) then makes a decision based on that new information.
The assistant never changes the CEO's calendar directly. They always bring back a formal memo (dispatch a new action). This is the Effects contract.
Technical Explanation
An Effect is a class decorated with @Injectable that uses Actions — an Observable stream of every action dispatched in the app — combined with ofType() to filter for specific actions, followed by an RxJS operator chain that performs the side effect, and ends by dispatching a new action (or using { dispatch: false } for fire-and-forget effects like analytics).
The critical decision in every Effect is which flattening operator to use after ofType():

switchMap — cancels the previous inner Observable when a new action arrives. Right for searches, navigation, any "latest wins" scenario. Catastrophic for writes — cancels in-flight POST/PUT/DELETE on double-click.
concatMap — queues actions, processes one at a time in strict order. Right for sequential writes where order matters.
exhaustMap — ignores new actions while one is already in flight. Right for login — ignores double-clicks entirely until the current request completes.
mergeMap — runs all concurrently with no cancellation. Right for independent parallel operations where order doesn't matter.

Section 3 — Code Example
Plain TS — Core concept in isolation
typescript// Understanding Effects mental model without Angular:
// An Effect is just: stream of events → filter → async work → new event

import { Subject, of } from 'rxjs';
import { filter, switchMap, catchError, map } from 'rxjs/operators';

const actions$ = new Subject<{ type: string; query?: string }>();

// A "manual effect" — listen, filter, do async work, emit result
actions$.pipe(
  filter(action => action.type === '[Search] Query Changed'),
  switchMap(action =>
    fakeHttpSearch(action.query!).pipe(
      map(results => ({ type: '[Search API] Results Loaded', results })),
      catchError(err => of({ type: '[Search API] Load Failed', error: err.message }))
    )
  )
).subscribe(newAction => {
  console.log('Dispatching:', newAction);
  actions$.next(newAction); // dispatch back into the stream
});

Real Angular NgRx Effects

Step 1 — Create the Effects class:
typescript// users/store/users.effects.ts
import { Injectable, inject } from '@angular/core';
import { Actions, createEffect, ofType } from '@ngrx/effects';
import { Router } from '@angular/router';
import { of } from 'rxjs';
import {
  switchMap, map, catchError,
  exhaustMap, tap, concatMap
} from 'rxjs/operators';
import * as UsersActions from './users.actions';
import { UsersApiService } from '../services/users-api.service';

@Injectable()
export class UsersEffects {
  // Inject Actions stream — emits every action dispatched in the app
  readonly #actions$ = inject(Actions);
  readonly #usersApi = inject(UsersApiService);
  readonly #router = inject(Router);

  // ── Effect 1: Load users on page open ─────────────────────────────
  // switchMap: if the page opens twice fast (unlikely but possible),
  // cancel the first request and use the latest
  loadUsers$ = createEffect(() =>
    this.#actions$.pipe(
      ofType(UsersActions.loadUsersPageOpened), // filter for this action
      switchMap(() =>                           // cancel previous, use latest
        this.#usersApi.getUsers().pipe(
          map(users =>
            // Success: dispatch success action with payload
            UsersActions.loadUsersSuccess({ users })
          ),
          catchError(error =>
            // CRITICAL: catchError must be INSIDE switchMap's inner Observable
            // If it's outside, one error kills the entire Effect permanently
            of(UsersActions.loadUsersFailure({ error: error.message }))
          )
        )
      )
    )
  );

  // ── Effect 2: Search users — switchMap (latest wins) ─────────────
  // User types fast — only the last search query matters
  searchUsers$ = createEffect(() =>
    this.#actions$.pipe(
      ofType(UsersActions.userSearched),
      switchMap(({ query }) =>               // ✅ switchMap: cancel stale searches
        this.#usersApi.searchUsers(query).pipe(
          map(users => UsersActions.loadUsersSuccess({ users })),
          catchError(error =>
            of(UsersActions.loadUsersFailure({ error: error.message }))
          )
        )
      )
    )
  );

  // ── Effect 3: Create user — concatMap (preserve order) ───────────
  // If the user creates multiple users rapidly, process them in order
  // concatMap queues — never drops a write request
  createUser$ = createEffect(() =>
    this.#actions$.pipe(
      ofType(UsersActions.createUserRequested),
      concatMap(({ user }) =>                // ✅ concatMap: queue writes
        this.#usersApi.createUser(user).pipe(
          map(created => UsersActions.createUserSuccess({ user: created })),
          catchError(error =>
            of(UsersActions.createUserFailure({ error: error.message }))
          )
        )
      )
    )
  );

  // ── Effect 4: Login — exhaustMap (ignore double-clicks) ──────────
  // While a login request is in flight, ignore all further login attempts
  login$ = createEffect(() =>
    this.#actions$.pipe(
      ofType(UsersActions.loginSubmitted),
      exhaustMap(({ credentials }) =>         // ✅ exhaustMap: ignore while busy
        this.#usersApi.login(credentials).pipe(
          map(user => UsersActions.loginSuccess({ user })),
          catchError(error =>
            of(UsersActions.loginFailure({ error: error.message }))
          )
        )
      )
    )
  );

  // ── Effect 5: Navigate after login — dispatch: false ─────────────
  // This Effect has a side effect (navigation) but dispatches NO action
  // { dispatch: false } tells NgRx not to expect an action back
  navigateAfterLogin$ = createEffect(
    () =>
      this.#actions$.pipe(
        ofType(UsersActions.loginSuccess),
        tap(() => this.#router.navigate(['/dashboard']))
        // tap: perform side effect without transforming the stream
        // No map() here — we're not creating a new action
      ),
    { dispatch: false } // REQUIRED when the effect doesn't dispatch
  );

  // ── Effect 6: Analytics — dispatch: false ────────────────────────
  trackUserCreated$ = createEffect(
    () =>
      this.#actions$.pipe(
        ofType(UsersActions.createUserSuccess),
        tap(({ user }) => {
          // Fire analytics event — no action needed back
          console.log('Analytics: user created', user.id);
        })
      ),
    { dispatch: false }
  );
}

Step 3 — The API service called by Effects:
typescript// users/services/users-api.service.ts
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { User } from '../models/user.model';

@Injectable({ providedIn: 'root' })
export class UsersApiService {
  readonly #http = inject(HttpClient);
  readonly #base = '/api';

  getUsers(): Observable<User[]> {
    return this.#http.get<User[]>(`${this.#base}/users`);
  }

  searchUsers(query: string): Observable<User[]> {
    return this.#http.get<User[]>(`${this.#base}/users`, {
      params: { q: query }
    });
  }

  createUser(user: Omit<User, 'id'>): Observable<User> {
    return this.#http.post<User>(`${this.#base}/users`, user);
  }

  login(credentials: { email: string; password: string }): Observable<User> {
    return this.#http.post<User>(`${this.#base}/auth/login`, credentials);
  }
}

Section 4 — Before & After Refactor
❌ Before — HTTP calls inside a component
typescript// WRONG: Async logic in the component
@Component({})
export class UsersPageComponent implements OnInit {
  readonly #http = inject(HttpClient);
  readonly #store = inject(Store);

  ngOnInit(): void {
    // HTTP call directly in component — bypasses NgRx entirely
    this.#http.get<User[]>('/api/users').subscribe(users => {
      // Dispatching success directly — no loading state, no error handling
      this.#store.dispatch(UsersActions.loadUsersSuccess({ users }));
    });
    // No error handling — a failed request leaves loading = true forever
    // No cleanup — component destroyed, subscription still active
  }
}
What breaks: No loading state management, no error handling, no subscription cleanup, no DevTools visibility into the async operation, no reusability. Every component that needs users duplicates this code.
✅ After — HTTP call in an Effect
typescript// CORRECT: Component is purely declarative
@Component({})
export class UsersPageComponent implements OnInit {
  readonly #store = inject(Store);

  loading$ = this.#store.select(selectUsersLoading);
  users$   = this.#store.select(selectAllUsers);
  error$   = this.#store.select(selectUsersError);

  ngOnInit(): void {
    // One line — describes what happened, Effect handles everything else
    this.#store.dispatch(UsersActions.loadUsersPageOpened());
  }
}

// Effect handles: HTTP call, loading state (via reducer),
// error handling, DevTools visibility, reusability across components
Why this matters in Angular: The component becomes a pure view layer — it dispatches events and renders state. All async complexity lives in the Effect where it is independently testable, visible in DevTools, and reusable across any component that dispatches the same action.

Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Placing catchError outside the inner Observable
What it looks like:
typescript// ❌ WRONG: catchError outside switchMap's inner Observable
loadUsers$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(UsersActions.loadUsersPageOpened),
    switchMap(() => this.#usersApi.getUsers().pipe(
      map(users => UsersActions.loadUsersSuccess({ users }))
    )),
    // catchError here catches errors from the OUTER stream
    // One HTTP error kills the entire Effect Observable permanently
    catchError(error => of(UsersActions.loadUsersFailure({ error: error.message })))
  )
);
Why developers make it: It looks cleaner — one catchError at the end rather than nested inside every switchMap. The RxJS chain reads more linearly.
How to avoid it: Always place catchError inside the inner Observable — inside the switchMap/concatMap/etc. callback, after the HTTP call.
Angular-specific consequence: The first HTTP error (a 404, a 500, a network blip) permanently kills the Effect. Every subsequent action of that type is dispatched, hits the dead Effect, and silently does nothing. No error is thrown — the app just stops working for that feature. Users must refresh to recover. This is the most dangerous Effects bug in production.

Mistake 2 — Using switchMap for write operations (POST/PUT/DELETE)
What it looks like:
typescript// ❌ WRONG: switchMap for a write operation
deleteUser$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(UsersActions.deleteUserRequested),
    switchMap(({ userId }) =>              // switchMap CANCELS previous
      this.#usersApi.deleteUser(userId).pipe(
        map(() => UsersActions.deleteUserSuccess({ userId })),
        catchError(error => of(UsersActions.deleteUserFailure({ error: error.message })))
      )
    )
  )
);
Why developers make it: switchMap is the first flattening operator most Angular developers learn (from search/autocomplete examples). They apply it everywhere without thinking about cancellation semantics.
How to avoid it: For any write operation (POST, PUT, PATCH, DELETE), use concatMap (preserve order) or exhaustMap (ignore duplicates). Reserve switchMap exclusively for reads where "latest wins" is the correct behaviour.
Angular-specific consequence: A user double-clicks "Delete". Two deleteUserRequested actions are dispatched. switchMap cancels the first DELETE request mid-flight and starts the second. The server may or may not have processed the first request before cancellation — the user thinks the item was deleted but the server state is undefined. Data integrity is corrupted silently.

Mistake 3 — Forgetting { dispatch: false } on non-dispatching Effects
What it looks like:
typescript// ❌ WRONG: Missing { dispatch: false }
navigateAfterLogin$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(UsersActions.loginSuccess),
    tap(() => this.#router.navigate(['/dashboard']))
    // tap returns the original action — NgRx tries to dispatch it again
    // loginSuccess dispatches loginSuccess dispatches loginSuccess...
  )
  // Missing: { dispatch: false }
);
Why developers make it: They add tap() for side effects and forget that createEffect defaults to dispatch: true — it expects the Observable to emit an action to dispatch.
How to avoid it: Any Effect that uses tap() instead of map() as its terminal operator needs { dispatch: false }. A quick rule: if your Effect chain ends with tap, add { dispatch: false }.
Angular-specific consequence: NgRx dispatches the original action that flowed through tap() back into the store. This triggers the Effect again. An infinite dispatch loop floods the Redux DevTools with hundreds of identical actions per second, causes console errors about maximum action dispatches, and may freeze or crash the browser tab.

Section 7 — Debugging Tips
Bug 1 — Effect stops working after the first error
Symptom: The first HTTP call succeeds. After any subsequent error (e.g. a 404), the Effect never fires again even though actions are still being dispatched. Redux DevTools shows actions dispatching but no HTTP calls appear in the Network panel.
Plain English cause: catchError is on the outer Observable. The first unhandled error completes the outer stream. The Effect is permanently dead.
Fix: Move catchError inside the switchMap/concatMap inner Observable:
typescriptswitchMap(action =>
  this.#service.call(action).pipe(
    map(result => successAction({ result })),
    catchError(err => of(failureAction({ error: err.message }))) // ← HERE
  )
)
Angular-specific note: Add a tap({ error: e => console.error('Effect error:', e) }) temporarily before catchError to confirm where the error is occurring. Redux DevTools won't show you the error — it only shows dispatched actions.

Bug 2 — Infinite action dispatch loop
Symptom: Redux DevTools shows the same action repeating hundreds of times per second. Console shows Error: Maximum action dispatch limit reached. Browser tab may freeze.
Plain English cause: An Effect without { dispatch: false } is using tap() as its terminal operator. The original action flows through tap() unchanged and NgRx dispatches it again, triggering the Effect again.
Fix: Add { dispatch: false } as the second argument to createEffect():
typescriptmyEffect$ = createEffect(
  () => this.#actions$.pipe(
    ofType(SomeAction.happened),
    tap(() => doSomething())
  ),
  { dispatch: false } // ← add this
);
Angular-specific note: Redux DevTools will clearly show the loop — you'll see the same action type repeating with incrementing sequence numbers. This is one of the easiest bugs to identify with DevTools.

Bug 3 — Effect never fires at all
Symptom: You dispatch an action, the DevTools shows it, but the Effect never triggers and no HTTP call appears in the Network panel.
Plain English cause (three possibilities):

The Effects class was never registered with provideEffects()
The ofType() references a different action creator than what was dispatched — type string mismatch
The Effect is registered in a feature route that hasn't loaded yet

Fix checklist:

Confirm provideEffects([YourEffects]) is in the route's providers array
In DevTools, check the exact type string of the dispatched action. In your Effect, console.log inside ofType() with a tap before it to confirm the filter is matching
Navigate to the feature route and confirm provideEffects is in that route, not a parent route

Angular-specific note: A common subtle cause — you import the action creator from the wrong path (two files export an action with the same name but different type strings). NgRx matches by type string, not by object reference. Always check the raw type string in DevTools.

Section 8 — Real-World Applications
Scenario 1 — Optimistic update with rollback
A todo app updates the UI instantly on toggle (optimistic) but rolls back if the server rejects it:
typescript// actions
export const todoToggled = createAction(
  '[Todo List] Todo Toggled',
  props<{ id: number; completed: boolean }>()
);
export const todoToggleConfirmed = createAction(
  '[Todos API] Toggle Confirmed',
  props<{ id: number }>()
);
export const todoToggleRolledBack = createAction(
  '[Todos API] Toggle Rolled Back',
  props<{ id: number; completed: boolean }>() // original value to restore
);

// reducer handles todoToggled immediately — no waiting for server
on(todoToggled, (state, { id, completed }) => ({
  ...state,
  todos: state.todos.map(t =>
    t.id === id ? { ...t, completed } : t // update instantly
  )
}))

// Effect confirms or rolls back
toggleTodo$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(todoToggled),
    concatMap(({ id, completed }) =>        // concatMap: queue toggles in order
      this.#todoApi.updateTodo(id, { completed }).pipe(
        map(() => todoToggleConfirmed({ id })),
        catchError(() =>
          // Roll back: dispatch with the OPPOSITE completed value
          of(todoToggleRolledBack({ id, completed: !completed }))
        )
      )
    )
  )
);

Scenario 2 — Polling with automatic stop
A dashboard polls a live metrics endpoint every 5 seconds but stops when the user navigates away:
typescriptimport { interval, EMPTY } from 'rxjs';
import { switchMap, takeUntil } from 'rxjs/operators';

pollMetrics$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(MetricsActions.dashboardOpened),
    // switchMap: if dashboard is opened twice, cancel the first poll
    switchMap(() =>
      interval(5000).pipe(
        // Stop polling when the dashboard closes
        takeUntil(
          this.#actions$.pipe(ofType(MetricsActions.dashboardClosed))
        ),
        switchMap(() =>
          this.#metricsApi.getLatest().pipe(
            map(metrics => MetricsActions.metricsLoaded({ metrics })),

          )
        )
      )
    )
  )
);

Section 10 — Key Takeaways
Core concepts in plain English:

Effects are the async middleware layer of NgRx — they listen to actions, perform side effects (HTTP, navigation, analytics), and dispatch new actions back into the store
The flattening operator choice is the most consequential decision in every Effect — wrong operator = silent data loss
catchError must always be inside the inner Observable — outside = one error kills the Effect permanently
{ dispatch: false } is required for any Effect that doesn't dispatch a new action
Effects register alongside their feature state — lazy with provideEffects() in route providers

Quick Reference Table — Operator Decision:
ScenarioOperatorWhyLoad data on page openswitchMapLatest request wins, old ones irrelevantSearch / autocompleteswitchMapCancel stale searchesCreate / update / deleteconcatMapPreserve order, never cancel writesLogin / form submitexhaustMapIgnore duplicates while in flightIndependent parallel uploadsmergeMapAll must complete, none cancel others
Angular-specific rules:

Always put catchError inside the inner Observable — this is the single most important Effects rule
switchMap is for reads; concatMap/exhaustMap are for writes — never cross this line
Every Effect ending with tap() needs { dispatch: false }
Register Effects lazily in route providers with provideEffects() alongside provideState()

One-Line Memory Aid:

Effects are the personal assistant who takes action descriptions, makes the phone calls, and brings back results — they live outside the state machine and the operator they use decides whether they hang up on old calls or wait patiently in queue.


Section 11 — Thought-Provoking Question + Answer
Question: If catchError inside the inner Observable returns of(failureAction(...)), the Effect stream continues — but what happens to the component that dispatched the original action if the user retries the same operation that previously failed? Is there anything in the reducer or selector layer that needs to reset for the retry to work correctly?
Answer:
This is a subtle but production-critical state management problem called the stale error state problem.
When an Effect catches an error and dispatches loadUsersFailure({ error: 'Server error' }), the reducer sets error: 'Server error' and loading: false. The component shows the error message. The user reads it, understands the problem, and clicks "Retry". The component dispatches loadUsersPageOpened() again.
The Effect fires correctly. But here's what breaks silently: the reducer for loadUsersPageOpened sets loading: true and — if you weren't careful — leaves error: 'Server error' in state. The component now shows both a loading spinner and the old error message simultaneously. If the retry succeeds, loadUsersSuccess sets error: null — fine. But if you never clear the error on the retry action, the UI is in an inconsistent state during the loading phase.
The fix is in the reducer:
typescripton(UsersActions.loadUsersPageOpened, state => ({
  ...state,
  loading: true,
  error: null  // ← always clear error when retrying
}))
The deeper implication is that every action that represents "starting over" must explicitly reset all the state that a previous failure may have set. This is not automatic — NgRx reducers only change what you tell them to change. Forgetting to clear error on retry is one of the most common UX bugs in NgRx apps — the user retries successfully but still sees the old error message because no action ever cleared it.
Practical rule: For every action that initiates an async operation, ensure its on() handler in the reducer sets loading: true AND clears error: null — even if the previous state had no error. Treat it as a reset gate, not just a loading flag.

Section 14 — Common Interview Questions
Question 1
"Where should you place catchError in an NgRx Effect and why does placement matter?"
Strong answer covers:

Must be inside the inner Observable (inside the switchMap/concatMap callback), not on the outer stream
Outer placement: one HTTP error completes the outer Observable permanently, the Effect dies silently for the rest of the session
Inner placement: the error is caught per-request, the outer stream continues, the Effect remains alive for future actions
The fix returns of(failureAction(...)) — of() creates a completing Observable so the inner stream ends cleanly and the outer stream continues listening

Weak answers miss: Why the outer stream dying is silent — no console error, no thrown exception, the app just stops responding to that action type.
Difficulty: Mid

Question 2
"When would you use exhaustMap vs concatMap vs switchMap in an NgRx Effect?"
Strong answer covers:

switchMap: reads where latest-wins (search, page load on navigation) — cancels previous
concatMap: writes that must preserve order (sequential create/update/delete operations)
exhaustMap: operations where duplicates must be ignored while one is in flight (login, form submit, payment)
mergeMap: independent parallel operations that all must complete (file uploads, batch operations)
The cardinal rule: never switchMap for writes — it silently cancels in-flight mutations

Weak answers miss: The specific production consequence of switchMap on a DELETE — the request may be partially processed server-side when cancelled, leaving data in an undefined state.
Difficulty: Mid-Senior

Question 3
"A developer reports that clicking 'Save' on a form sometimes saves the data and sometimes doesn't, but only when clicking quickly. The Effect uses switchMap. What's happening and how do you fix it?"
Strong answer covers:

switchMap cancels the previous inner Observable when a new action arrives
Double-clicking dispatches two save actions rapidly; the first HTTP request is cancelled by the second
If the second request also completes before the next click, it appears to work — intermittent because timing-dependent
Fix: replace switchMap with concatMap (queue saves in order) or exhaustMap (ignore second click while first is in flight)
Choice between concatMap and exhaustMap depends on whether both saves should eventually complete or only the first

Weak answers miss: The intermittent nature explanation — why it sometimes works (timing) and why that makes it harder to reproduce in testing than in production.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Effects that dispatch actions that trigger other Effects in a chain
typescript// ❌ Anti-pattern: Effect A dispatches → Effect B dispatches → Effect C
loadDashboard$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(DashboardActions.opened),
    switchMap(() => this.#api.getDashboard().pipe(
      map(data => DashboardActions.loaded({ data }))
    ))
  )
);

// Effect B triggers on loadedSuccess
loadUserProfile$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(DashboardActions.loaded),      // reacts to Effect A's output
    switchMap(({ data }) => this.#api.getUserProfile(data.userId).pipe(
      map(profile => UserActions.profileLoaded({ profile }))
    ))
  )
);

// Effect C triggers on profileLoaded
loadUserPermissions$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(UserActions.profileLoaded),    // reacts to Effect B's output
    switchMap(({ profile }) => this.#api.getPermissions(profile.id).pipe(
      map(perms => UserActions.permissionsLoaded({ perms }))
    ))
  )
);
Why it seems fine: Each Effect is simple and focused. The chain reads like a clear sequential workflow.
What actually breaks at scale: Three sequential HTTP requests where one parallel forkJoin would do. The chain creates hidden coupling — changing Effect A's output action breaks Effect B silently. In DevTools, tracing a bug requires following a chain of 6+ actions. Error handling is duplicated across three Effects.
Correct pattern: Use forkJoin or combineLatest in a single Effect when data can be fetched in parallel. When sequence is genuinely required, use concatMap with switchMap nested inside a single Effect.

Anti-Pattern 2 — Dispatching actions from Effects based on current state read inside the Effect
typescript// ❌ Anti-pattern: reading state with a one-time subscription inside an Effect
saveDocument$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(DocumentActions.saveRequested),
    switchMap(() => {
      // One-time store subscription inside the Effect — not reactive
      let currentDoc: Document | undefined;
      this.#store.select(selectCurrentDocument)
        .pipe(take(1))
        .subscribe(doc => currentDoc = doc);

      return this.#api.save(currentDoc!).pipe(
        map(() => DocumentActions.saveSuccess()),
        catchError(err => of(DocumentActions.saveFailure({ error: err.message })))
      );
    })
  )
);
Why it seems fine: It works — take(1) gets the current value and the save proceeds. Clean and readable.
What actually breaks: The subscribe inside switchMap is a nested subscription — an anti-pattern (Topic 20). The selector subscription and the HTTP subscription have separate lifecycles. If the component is destroyed between the subscribe and the HTTP response, you have a memory leak. The correct NgRx pattern for reading state in an Effect is withLatestFrom:
typescriptsaveDocument$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(DocumentActions.saveRequested),
    withLatestFrom(this.#store.select(selectCurrentDocument)),
    switchMap(([action, currentDoc]) =>   // both action and state in one tuple
      this.#api.save(currentDoc).pipe(
        map(() => DocumentActions.saveSuccess()),
        catchError(err => of(DocumentActions.saveFailure({ error: err.message })))
      )
    )
  )
);

Anti-Pattern 3 — Using a single catch-all Effect for multiple action types with complex branching
typescript// ❌ Anti-pattern: one Effect handles too many action types
handleAllApiCalls$ = createEffect(() =>
  this.#actions$.pipe(
    ofType(
      UsersActions.load,
      ProductsActions.load,
      OrdersActions.load,
      CartActions.load
    ),
    switchMap(action => {
      // Complex branching inside the Effect
      if (action.type === UsersActions.load.type) {
        return this.#usersApi.getAll().pipe(
          map(users => UsersActions.loadSuccess({ users })),
          catchError(err => of(UsersActions.loadFailure({ error: err.message })))
        );
      } else if (action.type === ProductsActions.load.type) {
        return this.#productsApi.getAll().pipe(/* ... */);
      }
      // ... more branches
    })
  )
);
Why it seems fine: Reduces the number of Effect properties. Feels DRY.
What actually breaks: switchMap now cancels ANY load when ANY other load fires — loading users cancels in-flight product loads. The branching makes the Effect impossible to unit test cleanly. Adding a new API call requires modifying a shared Effect, creating merge conflicts in teams. Error handling for one branch can accidentally affect another.
Correct pattern: One Effect per action type per concern. The verbosity is deliberate — each Effect is independently testable, independently replaceable, and independently debuggable. Use mergeMap if you genuinely need a single Effect to handle independent parallel loads without cancellation.

Section 16 — Mental Model Summary
Core concept in one sentence: Effects are NgRx's dedicated async layer — they listen to the action stream, perform side effects (HTTP, navigation, analytics) outside the pure reducer, and dispatch new actions back into the store to complete the cycle.
Key rules:

catchError always inside the inner Observable — outside = Effect dies on first error, silently, permanently
switchMap for reads (latest wins), concatMap for ordered writes, exhaustMap for deduplicated submissions, mergeMap for independent parallel operations
Any Effect ending with tap() must have { dispatch: false } — omitting it creates an infinite dispatch loop
Register Effects lazily with provideEffects([EffectsClass]) in route providers, not in app.config.ts
Read current state in Effects with withLatestFrom(store.select(...)) — never nest a subscribe inside an Effect
Never use switchMap for POST, PUT, PATCH, or DELETE — it silently cancels in-flight write requests on any new emission

The single most important Angular rule:

catchError must be inside the switchMap/concatMap inner Observable — one misplaced catchError on the outer stream silently kills the entire Effect after the first error, with no console warning and no way to recover without a page refresh.
