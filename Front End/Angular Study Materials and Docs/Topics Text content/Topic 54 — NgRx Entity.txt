Topic 54 — NgRx Entity

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — NgRx Entity introduces a new abstraction layer (the EntityAdapter) on top of the NgRx reducer pattern you already know, requiring you to learn a new API rather than new programming concepts.
Angular Relevance: High — Any Angular app managing lists of records (users, products, orders, messages) benefits directly from NgRx Entity, which eliminates hundreds of lines of hand-written CRUD reducer boilerplate while enforcing a consistent, performant data structure.

Section 1 — Explanation
The Filing Cabinet Analogy
Imagine you're managing paper records for a company. Without a system, you pile every employee file in a heap — to find one, you rifle through the whole stack. To update one record, you pull out the stack, find it, swap it, and put everything back. Slow and error-prone.
A professional filing cabinet solves this: every file gets a unique tab ID, files are stored alphabetically by ID, and you have a master index listing all IDs in order. To find, update, or delete any record, you go straight to the tab. Done.
NgRx Entity is that filing cabinet for your NgRx store.
Technically:
NgRx Entity (@ngrx/entity) provides an EntityAdapter that manages a normalized data structure called an EntityState:
tsinterface EntityState<T> {
  ids: string[] | number[];   // ordered list of all entity IDs
  entities: Record<string, T>; // dictionary: id → entity object
}
Instead of writing your own find, filter, map, and splice logic in reducers, the adapter gives you ready-made CRUD operations. These are pure functions that return new state objects, compatible with NgRx's immutability requirements.

The single topic it extends most directly: Topic 51 — NgRx Core Concepts.
NgRx Entity is essentially a pre-written, battle-tested reducer library for collections. Everything in Topic 51 still applies — Entity just eliminates the hand-written CRUD code inside your on() handlers.
Bridging note: In Topic 51 you wrote reducers like state.users.filter(u => u.id !== action.id) for every CRUD operation. NgRx Entity replaces every one of those array operations with a single adapter method call, while the normalized { ids, entities } structure makes selector lookups O(1) instead of O(n) array scans.

Section 3 — Code Example
Plain TS — What EntityAdapter does under the hood
ts// Without Entity — hand-written, error-prone
function removeUser(state: UsersState, id: string): UsersState {
  return {
    ...state,
    users: state.users.filter(u => u.id !== id) // O(n) scan every time
  };
}

// With Entity — adapter handles it
// adapter.removeOne(id, state) returns the same result, but:
// - uses the { ids, entities } normalized structure
// - is O(1) for lookup (dictionary access, not array scan)
// - is already tested by the NgRx team
Full Angular NgRx Entity Feature
ts// user.model.ts
export interface User {
  id: string;
  name: string;
  email: string;
  role: 'admin' | 'viewer';
}
ts// user.actions.ts
import { createActionGroup, emptyProps, props } from '@ngrx/store';
import { User } from './user.model';

export const UsersApiActions = createActionGroup({
  source: 'Users API',
  events: {
    // Past-tense names per Topic 51 naming rules
    'Users Loaded': props<{ users: User[] }>(),
    'User Added': props<{ user: User }>(),
    'User Updated': props<{ id: string; changes: Partial<User> }>(),
    'User Removed': props<{ id: string }>(),
    'Users Load Failed': props<{ error: string }>(),
  }
});

export const UsersPageActions = createActionGroup({
  source: 'Users Page',
  events: {
    'Page Opened': emptyProps(),
    'Add User Clicked': props<{ user: User }>(),
    'Remove User Clicked': props<{ id: string }>(),
    'Update User Submitted': props<{ id: string; changes: Partial<User> }>(),
  }
});
ts// user.reducer.ts
import { createEntityAdapter, EntityAdapter, EntityState } from '@ngrx/entity';
import { createFeature, createReducer, on } from '@ngrx/store';
import { User } from './user.model';
import { UsersApiActions } from './user.actions';

// Step 1: Create the adapter — optionally specify sort order
export const userAdapter: EntityAdapter<User> = createEntityAdapter<User>({
  // Optional: default sort by name. Omit for insertion order.
  sortComparer: (a, b) => a.name.localeCompare(b.name),

  // Optional: if your ID field isn't named 'id'
  // selectId: (user) => user.userId,
});

// Step 2: Define state — EntityState<User> gives us { ids, entities }
// We add extra slices alongside the entity collection
export interface UsersState extends EntityState<User> {
  loading: boolean;
  error: string | null;
  selectedUserId: string | null;
}

// Step 3: Get initial state — merges { ids:[], entities:{} } with our extras
const initialState: UsersState = userAdapter.getInitialState({
  loading: false,
  error: null,
  selectedUserId: null,
});

// Step 4: Write the reducer using adapter methods inside on() handlers
export const usersFeature = createFeature({
  name: 'users',
  reducer: createReducer(
    initialState,

    on(UsersApiActions.usersLoaded, (state, { users }) =>
      // setAll replaces the entire collection — used for initial load
      userAdapter.setAll(users, { ...state, loading: false, error: null })
    ),

    on(UsersApiActions.userAdded, (state, { user }) =>
      // addOne adds if ID doesn't exist; ignores if already present
      userAdapter.addOne(user, state)
    ),

    on(UsersApiActions.userUpdated, (state, { id, changes }) =>
      // updateOne merges partial changes — does not replace the whole entity
      userAdapter.updateOne({ id, changes }, state)
    ),

    on(UsersApiActions.userRemoved, (state, { id }) =>
      // removeOne deletes by ID — O(1) operation
      userAdapter.removeOne(id, state)
    ),

    on(UsersApiActions.usersLoadFailed, (state, { error }) =>
      // Non-entity state updated normally with spread
      ({ ...state, loading: false, error })
    ),
  ),
});

// Step 5: Export the feature selectors NgRx generates automatically
// usersFeature.selectUsersState, usersFeature.selectLoading, etc.
export const {
  selectUsersState,
  selectLoading,
  selectError,
  selectSelectedUserId,
} = usersFeature;
ts// user.selectors.ts
import { createSelector } from '@ngrx/store';
import { userAdapter, selectUsersState, selectSelectedUserId } from './user.reducer';

// Step 6: Get the adapter's built-in selectors
// selectAll → User[]       (respects sortComparer order)
// selectEntities → Record<string, User>  (dictionary for O(1) lookup)
// selectIds → string[]
// selectTotal → number
const {
  selectAll: selectAllUsers,
  selectEntities: selectUserEntities,
  selectIds: selectUserIds,
  selectTotal: selectUserTotal,
} = userAdapter.getSelectors(selectUsersState);

export { selectAllUsers, selectUserEntities, selectUserIds, selectUserTotal };

// Compose derived selectors — Topic 53 layered selector pattern
export const selectSelectedUser = createSelector(
  selectUserEntities,
  selectSelectedUserId,
  // O(1) dictionary lookup — no array find()
  (entities, selectedId) => selectedId ? entities[selectedId] ?? null : null
);

export const selectAdminUsers = createSelector(
  selectAllUsers,
  (users) => users.filter(u => u.role === 'admin')
);
ts// users.component.ts
import { Component, inject, OnInit } from '@angular/core';
import { Store } from '@ngrx/store';
import { ChangeDetectionStrategy } from '@angular/core';
import { UsersPageActions } from './user.actions';
import { selectAllUsers, selectLoading, selectSelectedUser } from './user.selectors';

@Component({
  selector: 'app-users',
  changeDetection: ChangeDetectionStrategy.OnPush, // Always pair with NgRx
  template: `
    @if (loading()) {
      <p>Loading...</p>
    }
    @for (user of users(); track user.id) {
      <div>
        {{ user.name }}
        <button (click)="remove(user.id)">Remove</button>
      </div>
    }
    <p>Total: {{ total() }}</p>
  `
})
export class UsersComponent implements OnInit {
  private store = inject(Store);

  // store.selectSignal — Topic 53 Signal-based selector pattern
  users = this.store.selectSignal(selectAllUsers);
  loading = this.store.selectSignal(selectLoading);
  total = this.store.selectSignal(selectUserTotal);

  ngOnInit() {
    this.store.dispatch(UsersPageActions.pageOpened());
  }

  remove(id: string) {
    this.store.dispatch(UsersPageActions.removeUserClicked({ id }));
  }
}

Section 4 — Before & After Refactor
Before — Hand-written array CRUD reducer
ts// ❌ BEFORE — writing all array operations manually
interface UsersState {
  users: User[];
  loading: boolean;
}

const reducer = createReducer(
  { users: [], loading: false },

  on(UsersApiActions.usersLoaded, (state, { users }) => ({
    ...state,
    users,         // Replace entire array — O(n) reference
    loading: false,
  })),

  on(UsersApiActions.userUpdated, (state, { id, changes }) => ({
    ...state,
    // O(n) scan + new array + new object — 3 allocations per update
    users: state.users.map(u => u.id === id ? { ...u, ...changes } : u),
  })),

  on(UsersApiActions.userRemoved, (state, { id }) => ({
    ...state,
    users: state.users.filter(u => u.id !== id), // O(n) scan
  })),

  on(UsersApiActions.userAdded, (state, { user }) => ({
    ...state,
    users: [...state.users, user], // O(n) spread copy
  })),
);
What breaks with this approach:

O(n) operations on every state change — with 10,000 users, every update, remove, or lookup scans the entire array
Selector by ID requires users.find(u => u.id === id) — another O(n) scan
Duplicate IDs are not prevented — adding the same user twice silently corrupts state
Sort order must be re-implemented manually on every operation
Boilerplate scales badly — 4 operations × 10 entity types = 40 hand-written array functions, all needing individual tests

After — NgRx Entity adapter
ts// ✅ AFTER — adapter handles all CRUD operations

on(UsersApiActions.usersLoaded, (state, { users }) =>
  userAdapter.setAll(users, { ...state, loading: false })
),

on(UsersApiActions.userUpdated, (state, { id, changes }) =>
  userAdapter.updateOne({ id, changes }, state)
  // O(1) dictionary update — single property assignment
),

on(UsersApiActions.userRemoved, (state, { id }) =>
  userAdapter.removeOne(id, state)
  // O(1) delete — removes from entities dict and splices from ids array
),

on(UsersApiActions.userAdded, (state, { user }) =>
  userAdapter.addOne(user, state)
  // addOne silently ignores duplicates — safer than push
),
Why this refactor matters in Angular:

Selector performance is O(1) via dictionary lookup — critical with OnPush and large lists
Duplicate protection is built in (addOne ignores, upsertOne merges)
Sort order is maintained automatically by sortComparer
The adapter's methods are already tested by the NgRx team — you only test your action/effect logic


Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Using addOne when you need upsertOne for API sync
What: Dispatching addOne when refreshing data from an API that returns records already in the store.
Why developers make it: addOne sounds like "add this to the collection" which is correct — but its behaviour when the ID already exists is silent ignore, not update.
How to avoid it: If the API can return records that might already be in the store (a refresh, a push notification update), use upsertOne or setAll. Use addOne only for genuinely new records created by the user.
Angular-specific consequence: Your UI silently shows stale data because the old entity was never replaced. No error, no warning — the component just keeps displaying the outdated version.

Mistake 2 — Calling getSelectors() without passing the feature selector
What:
ts// ❌ Wrong — no argument
const { selectAll } = userAdapter.getSelectors();
// This selects from root state, not the feature slice
Why developers make it: The NgRx docs show both the argument and no-argument form. The no-argument form expects you to pass the feature state slice yourself at the store.select() call site, which is easy to forget.
How to avoid it: Always pass the feature selector: userAdapter.getSelectors(selectUsersState). This produces selectors that scope themselves to the feature slice automatically.
Angular-specific consequence: selectAll returns undefined or throws a runtime error because it's trying to read ids and entities from the wrong state level.

Mistake 3 — Putting sortComparer logic in selectors instead of the adapter
What:
ts// ❌ Wrong — sorting in selector breaks memoisation (Topic 53 rule)
export const selectSortedUsers = createSelector(
  selectAllUsers,
  (users) => [...users].sort((a, b) => a.name.localeCompare(b.name))
);
Why developers make it: Sorting in a selector feels natural and flexible — and it works. But it creates a new array reference on every emission, breaking memoisation exactly as warned in Topic 53.
How to avoid it: Define sortComparer in createEntityAdapter(). The adapter then maintains sorted order in the ids array automatically, and selectAll returns users pre-sorted with no extra computation.
Angular-specific consequence: The sorted selector emits a new array reference on every action that touches the users slice (even unrelated ones), causing OnPush components to re-render unnecessarily on every store action.

Section 7 — Debugging Tips
Bug 1 — selectAll returns an empty array even after dispatching load success
Symptom: Component shows nothing; Redux DevTools shows state with entities populated but selectAll returns [].
Cause: getSelectors() was called without a feature selector argument, so it's reading from root state (state.ids, state.entities) rather than state.users.ids and state.users.entities.
Fix:
ts// ❌ Wrong
const { selectAll } = userAdapter.getSelectors();

// ✅ Correct
const { selectAll } = userAdapter.getSelectors(selectUsersState);
Angular-specific note: This is especially hard to spot because DevTools shows the correct state tree — the bug is in which slice the selector is reading from, not in the state itself.

Bug 2 — Updating an entity does nothing visible in the component
Symptom: You dispatch updateOne, DevTools shows state updated, but the component doesn't re-render.
Cause: The component is using ChangeDetectionStrategy.OnPush correctly (Topic 24), but the selector is not returning a new reference. This happens when strictStateImmutability is off and someone accidentally mutated state directly somewhere else, causing the selector to see the same reference and skip emission.
Fix: Enable strictStateImmutability: true in your NgRx runtime checks (development only):
ts// app.config.ts
provideStore({}, {
  runtimeChecks: {
    strictStateImmutability: true,
    strictActionImmutability: true,
  }
})
Angular-specific note: The adapter's updateOne always returns a new state reference when a change occurs. If your component isn't updating, the mutation happened somewhere else in the state tree — the runtime checks will surface it immediately.

Bug 3 — upsertOne is not merging — it's replacing the entire entity
Symptom: You call upsertOne with a partial entity and other fields disappear.
Cause: upsertOne adds the entity as-is if the ID doesn't exist, and merges if it does — but you're passing an incomplete object for a new entity that hasn't been added yet. Since the ID is absent, it treats it as an addOne and stores the partial object directly.
Fix: Only use upsertOne for full entity objects when the record might or might not exist. For guaranteed partial updates on existing records, use updateOne({ id, changes }).
ts// ✅ Partial update on a known-existing record
userAdapter.updateOne({ id: '123', changes: { role: 'admin' } }, state)

// ✅ Full entity — add if new, merge if exists
userAdapter.upsertOne(fullUserObject, state)
Angular-specific note: This most commonly surfaces when handling optimistic update patterns — you send a partial PATCH to the API and try to apply the same partial payload to the store with upsertOne, which works only if the entity already exists.

Section 8 — Real-World Applications
Scenario 1 — Product catalogue with real-time stock updates
An e-commerce Angular app receives WebSocket messages whenever a product's stock level changes. The store holds thousands of products already loaded from the initial API call.
ts// product.effects.ts
loadProducts$ = createEffect(() =>
  this.actions$.pipe(
    ofType(ProductsPageActions.pageOpened),
    switchMap(() =>
      this.productService.getAll().pipe(
        map(products => ProductsApiActions.productsLoaded({ products })),
        catchError(error => of(ProductsApiActions.productsLoadFailed({ error: error.message })))
      )
    )
  )
);

// WebSocket update — runs as a long-lived Effect
stockUpdates$ = createEffect(() =>
  this.wsService.stockUpdates$.pipe(
    map(({ productId, newStock }) =>
      // O(1) update — no array scan needed
      ProductsApiActions.productUpdated({
        id: productId,
        changes: { stock: newStock }
      })
    )
  )
);
ts// product.reducer.ts — handles the update
on(ProductsApiActions.productUpdated, (state, { id, changes }) =>
  productAdapter.updateOne({ id, changes }, state)
  // Dictionary update: state.entities[id] = { ...state.entities[id], ...changes }
  // O(1) regardless of catalogue size
),
The O(1) update is critical — if the WebSocket fires 50 stock updates per second across 10,000 products, an array map() approach processes 500,000 element comparisons per second. The dictionary approach processes 50.

Scenario 2 — Inbox with read/unread state and selection
A messaging app has a thread list. Users can mark threads read, star them, and click to open one. The selected thread's detail view must update in real time without re-fetching.
ts// State interface
export interface ThreadsState extends EntityState<Thread> {
  selectedThreadId: string | null;
  loading: boolean;
}

// Reducer
on(ThreadsApiActions.threadMarkedRead, (state, { id }) =>
  threadAdapter.updateOne({ id, changes: { unread: false } }, state)
),

on(ThreadsPageActions.threadSelected, (state, { id }) => ({
  ...state,
  selectedThreadId: id
})),
ts// Selectors — O(1) lookup for selected thread
export const selectSelectedThread = createSelector(
  selectThreadEntities,    // Record<string, Thread>
  selectSelectedThreadId,  // string | null
  (entities, id) => id ? entities[id] ?? null : null
  // No array.find() — direct property access
);

export const selectUnreadCount = createSelector(
  selectAllThreads,
  (threads) => threads.filter(t => t.unread).length
);
The selected thread selector is the key win — as the inbox grows to thousands of threads, selection lookup stays O(1). Without Entity, threads.find(t => t.id === selectedId) degrades linearly.

Section 10 — Key Takeaways
Core concepts:

EntityState<T> normalizes a collection into { ids: string[], entities: Record<string, T> } — a dictionary structure enabling O(1) CRUD operations
createEntityAdapter<T>() produces all the CRUD helper functions; sortComparer is optional and keeps the ids array sorted automatically
getInitialState(extras) merges the empty entity structure with your extra state slices (loading, error, selectedId)
getSelectors(featureSelector) produces four scoped selectors: selectAll, selectEntities, selectIds, selectTotal
Adapter methods (addOne, updateOne, removeOne, etc.) are pure functions returning new state — they satisfy NgRx's immutability requirement automatically

Section 11 — Thought-Provoking Question + Answer
Question: NgRx Entity's selectAll selector returns a User[] array — which is a new array reference every time it's called. Does this mean it always breaks memoisation and causes unnecessary OnPush re-renders?
Answer:
This is one of the subtlest points in NgRx Entity.
selectAll is implemented as a createSelector internally. Like all NgRx selectors (Topic 53), it uses referential equality checking on its inputs, not on its output. The selector only recomputes when state.ids or state.entities changes reference. When it does recompute, it produces a new User[] array — but this only happens when the underlying entity data actually changed.
So the behaviour is:

Action that doesn't touch the users feature slice → input references unchanged → selector short-circuits → same User[] reference returned → OnPush component does NOT re-render ✅
Action that changes entity data (add, update, remove) → new ids or entities reference → selector recomputes → new User[] reference → OnPush component re-renders ✅

The concern would be valid if selectAll ran on every action regardless of input changes — but that's exactly what createSelector's memoisation prevents.
The trap to avoid: If you compose a derived selector on top of selectAll and that selector's projector returns a new object or array literal on every call (Topic 53's central warning), then memoisation breaks there. The fix is the same as Topic 53: never return {} or [] from a projector unless the inputs changed meaningfully.
Practical rule: Trust selectAll's memoisation. Only audit derived selectors that filter, sort, or reshape the result — those are where new reference creation silently breaks OnPush.

Section 14 — Common Interview Questions
Question 1
"What problem does NgRx Entity solve, and how does its data structure improve performance over a plain array in the store?"
Strong answer covers:

Arrays require O(n) scan for find/update/delete; Entity normalizes to { ids, entities } enabling O(1) dictionary lookup
Eliminates hand-written CRUD boilerplate in reducers (map, filter, spread) with battle-tested adapter methods
The ids array preserves ordered selection while entities dictionary enables fast keyed access
Adapter methods automatically return new state references satisfying NgRx immutability requirements
sortComparer maintains order automatically without repeated sorting in selectors

Weak answers miss: The performance argument (O(1) vs O(n)) — most candidates explain the API without explaining why the normalized structure matters.
Difficulty: Mid

Question 2
"What's the difference between addOne, setOne, and upsertOne in the EntityAdapter, and when would you use each?"
Strong answer covers:

addOne: adds the entity only if the ID is absent — silently ignores if already present
setOne: unconditionally adds or replaces the entire entity
upsertOne: adds if absent, merges (shallow) if present — similar to a database UPSERT
addOne for user-created records (guaranteed new), upsertOne for API sync (may already exist), setOne when you want guaranteed full replacement
All three return new state references — they never mutate

Weak answers miss: The distinction between setOne (full replace) and upsertOne (merge) — candidates often treat them as synonyms.
Difficulty: Mid

Question 3
"A developer uses sortComparer in their EntityAdapter but also sorts the result again inside a selector. What are the consequences, and which approach is correct?"
Strong answer covers:

selectAll already returns entities in sortComparer order — the second sort is redundant computation
Sorting inside a selector's projector always returns a new array reference, even when nothing changed
A new array reference causes memoisation to fail — the selector emits on every action touching the feature slice
OnPush components re-render unnecessarily on every store action, defeating the performance benefit
Correct approach: define sort in createEntityAdapter({ sortComparer }) and trust selectAll — it maintains order at write time, not read time

Weak answers miss: The memoisation consequence — most candidates spot the redundancy but don't connect it to OnPush re-render behaviour.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Sorting inside a selector on top of selectAll
ts// ❌ Anti-pattern
export const selectSortedUsers = createSelector(
  selectAllUsers,
  (users) => [...users].sort((a, b) => a.name.localeCompare(b.name))
);
Why it seems fine: It works correctly — users appear sorted. The sort logic is readable and easy to understand.
What breaks in production: The projector returns a new [] reference on every emission, even when no user data changed. Every action that touches the users feature slice (loading state changes, selected ID changes, unrelated updates) causes selectSortedUsers to emit a new reference, triggering OnPush re-renders on every component subscribed to it. In a large app with frequent store activity, this can cause dozens of unnecessary re-renders per second.
Correct pattern:
ts// ✅ Sort defined once in the adapter — maintained at write time
export const userAdapter = createEntityAdapter<User>({
  sortComparer: (a, b) => a.name.localeCompare(b.name),
});
// selectAll already returns sorted users — no selector sort needed

Anti-Pattern 2 — Registering entity feature state in app.config.ts
ts// ❌ Anti-pattern — in app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideStore(),
    provideState('users', usersReducer),     // Eagerly loaded
    provideState('products', productsReducer), // Eagerly loaded
    provideState('orders', ordersReducer),    // Eagerly loaded
    provideEffects([UsersEffects, ProductsEffects, OrdersEffects]),
  ]
};
Why it seems fine: It's simple, all state is immediately available everywhere, and it matches how developers register global app config.
What breaks in production: All entity state and all associated effects are eagerly downloaded and initialized for every user on every page — including users who never visit the Users, Products, or Orders pages. This defeats lazy loading (Topic 40) and increases initial bundle size and startup time. Entity features are typically page-specific and should be co-located with their routes.
Correct pattern:
ts// ✅ In the route definition
{
  path: 'users',
  loadComponent: () => import('./users/users.component'),
  providers: [
    provideState('users', usersReducer),  // Loaded only when route activates
    provideEffects([UsersEffects]),
  ]
}

Anti-Pattern 3 — Nesting store.select() inside a component method for per-entity lookups
ts// ❌ Anti-pattern
@Component({
  template: `
    @for (id of userIds(); track id) {
      <app-user-card [user]="getUserById(id)" />
    }
  `
})
export class UsersListComponent {
  userIds = this.store.selectSignal(selectUserIds);

  // Called on every change detection cycle for every ID
  getUserById(id: string): User | undefined {
    let user: User | undefined;
    // New subscription created and immediately destroyed every CD cycle
    this.store.select(selectUserEntities).pipe(take(1))
      .subscribe(entities => user = entities[id]);
    return user;
  }
}
Why it seems fine: It looks like a convenient per-item lookup and developers familiar with services often write utility methods this way.
What breaks in production: A new Observable subscription is created and destroyed on every change detection cycle for every item in the list. With 100 users and 60fps CD cycles, this is 6,000 subscriptions created and destroyed per second — a serious memory and performance problem.
Correct pattern:
ts// ✅ Pass IDs to child components; child selects its own entity
// Parent component
@Component({
  template: `
    @for (id of userIds(); track id) {
      <app-user-card [userId]="id" />
    }
  `
})
export class UsersListComponent {
  userIds = this.store.selectSignal(selectUserIds);
}

// Child component — one selector per instance, stable subscription
@Component({ selector: 'app-user-card' })
export class UserCardComponent implements OnInit {
  @Input() userId!: string;
  user = signal<User | null>(null);

  ngOnInit() {
    // Created once per component instance
    this.store.selectSignal(selectUserById(this.userId));
  }
}

Section 16 — Mental Model Summary
Core concept in one sentence:

NgRx Entity normalizes a collection of records into a { ids[], entities{} } dictionary structure and provides an EntityAdapter with O(1) CRUD methods that write immutable reducers for you.
Key rules:

Always pass the feature selector to getSelectors(featureSelector) — the no-argument form reads from root state and returns undefined
Define sortComparer in createEntityAdapter(), never sort in selectors — sorting in projectors returns new array references and breaks memoisation
Use upsertOne for API sync (add or merge), updateOne for partial updates on known-existing records, addOne only for guaranteed new records
Extend EntityState<T> with extra state slices (loading, error, selectedId) and initialize them in getInitialState({ loading: false, ... })
Register feature state lazily in route providers with provideState() — never in app.config.ts
Always pair with ChangeDetectionStrategy.OnPush — the O(1) dictionary lookup makes selector memoisation most effective

The single most important Angular rule:

Never sort inside a selector on top of selectAll — define sortComparer in the adapter so order is maintained at write time, not recomputed at read time.
