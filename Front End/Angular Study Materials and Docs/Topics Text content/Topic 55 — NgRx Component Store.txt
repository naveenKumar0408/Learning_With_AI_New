Topic 55 — NgRx Component Store

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — Component Store introduces a new mental model (local vs global state) and a reactive updater/effect pattern that feels different from the global NgRx store, but builds directly on RxJS and NgRx concepts you already know.
Angular Relevance: High — Component Store solves a real gap in Angular architecture: state that is too complex for a single component's signals but too local and short-lived to justify polluting the global NgRx store — it is the right tool for self-contained feature sections like data tables, wizards, and sidepanels.

Section 1 — Explanation
The Whiteboard Analogy
Imagine your company has two types of information storage:

The central database (NgRx global store) — holds company-wide records that every department needs: employee roster, product catalogue, financial data. It persists across the whole app session. Everyone reads from it. Changes go through a strict approval process (actions → reducers → store).
A personal whiteboard in each meeting room — used only during a meeting to track progress on that specific discussion. When the meeting ends, the whiteboard gets wiped. Nobody else in the building cares what's on it. No approval process needed — whoever's in the room can write directly.

NgRx Component Store is the whiteboard.
It gives a single component (or a small feature section) its own self-contained reactive state with the same clean patterns as the global store — but scoped to the component's lifetime, requiring no actions, no reducers registered globally, and no DevTools ceremony for ephemeral UI state.
Technically:
@ngrx/component-store is a standalone state management service. You extend ComponentStore<StateType> and get:

setState() — replaces or partially updates state
updater() — creates a reusable state mutation function (like a mini-reducer)
select() — creates a memoised selector Observable from state
effect() — creates a side-effect handler (like NgRx Effects, but local)
patchState() — partial state update (like setState but only overrides specified keys)
Automatic subscription cleanup when the component is destroyed

Section 2 — Connection to Prior Concepts
Directly builds on:

Topic 51 — NgRx Core Concepts: The global store's one-way data flow (state → selectors → component → dispatch → reducer → state) is mirrored locally in Component Store. You already understand pure state updates and selector memoisation — Component Store uses the same mental model with less ceremony.
Topic 52 — NgRx Effects: The effect() method in Component Store works identically to NgRx Effects — it receives an Observable of inputs, performs side effects (HTTP, navigation), and feeds results back into state via updater() or patchState(). The same switchMap/concatMap/exhaustMap rules from Topic 52 apply.
Topic 20 — RxJS Subscription Management and Topic 21 — takeUntilDestroyed: Component Store handles its own subscription cleanup automatically when the component is destroyed — the same problem takeUntilDestroyed solves manually.
Topic 44 — State Management Patterns: The private state + public read-only projection + public write methods pattern from Topic 44's store service is exactly what Component Store formalizes with updater() and select().
Topic 27 — Services & Dependency Injection: Component Store is provided in the component's providers: [] array — it lives in the component's injector, not the root injector.

The single topic it extends most directly: Topic 44 — State Management Patterns.
In Topic 44 you built a hand-rolled store service with a private BehaviorSubject, public .asObservable() projection, and manual write methods. Component Store is that pattern — formalized, tested, and extended with reactive effects and automatic cleanup.
Bridging note: Topic 44's store service and Component Store solve the same problem (local reactive state with controlled mutation), but Component Store gives you updater() which enforces the pure-function mutation pattern from NgRx reducers, and effect() which enforces the Observable side-effect pattern from NgRx Effects — the same discipline at a smaller scope.

Section 3 — Code Example
Plain TS — What Component Store does under the hood
ts// Without Component Store — hand-rolled (Topic 44 pattern)
@Injectable()
class SearchStore {
  #state = new BehaviorSubject({ query: '', results: [], loading: false });
  readonly state$ = this.#state.asObservable();

  setQuery(query: string) {
    this.#state.next({ ...this.#state.getValue(), query });
  }
  // ... manual cleanup, no RxJS effect management
}

// With Component Store — same idea, less boilerplate
@Injectable()
class SearchStore extends ComponentStore<SearchState> {
  // updater() enforces the pure-function mutation pattern
  readonly setQuery = this.updater((state, query: string) => ({ ...state, query }));
  // select() gives a memoised Observable
  readonly query$ = this.select(state => state.query);
}
Full Angular Component Store Feature — Data Table with Pagination & Filtering
ts// data-table.store.ts
import { Injectable } from '@angular/core';
import { ComponentStore, tapResponse } from '@ngrx/component-store';
import { switchMap } from 'rxjs/operators';
import { Observable } from 'rxjs';
import { UserService } from './user.service';
import { User } from './user.model';

interface DataTableState {
  users: User[];
  loading: boolean;
  error: string | null;
  filter: string;
  currentPage: number;
  pageSize: number;
}

const initialState: DataTableState = {
  users: [],
  loading: false,
  error: null,
  filter: '',
  currentPage: 1,
  pageSize: 10,
};

@Injectable()
// ComponentStore<T> takes your state interface as a generic
export class DataTableStore extends ComponentStore<DataTableState> {

  constructor(private userService: UserService) {
    super(initialState); // Required — sets initial state
  }

  // ── SELECTORS ──────────────────────────────────────────────────────
  // select() creates a memoised Observable derived from state
  // Same referential equality rule as NgRx selectors (Topic 53)

  readonly users$ = this.select(state => state.users);
  readonly loading$ = this.select(state => state.loading);
  readonly error$ = this.select(state => state.error);
  readonly filter$ = this.select(state => state.filter);
  readonly currentPage$ = this.select(state => state.currentPage);

  // Composed selector — combines multiple slices (like createSelector)
  readonly filteredUsers$ = this.select(
    this.users$,
    this.filter$,
    // Projector runs only when users$ or filter$ emit new references
    (users, filter) =>
      filter
        ? users.filter(u =>
            u.name.toLowerCase().includes(filter.toLowerCase())
          )
        : users
  );

  // View model selector — single subscription for the template (Topic 53 pattern)
  readonly vm$ = this.select(
    this.filteredUsers$,
    this.loading$,
    this.error$,
    this.currentPage$,
    (users, loading, error, currentPage) => ({
      users,
      loading,
      error,
      currentPage,
    })
  );

  // ── UPDATERS ───────────────────────────────────────────────────────
  // updater() is a mini-reducer: (state, payload) => newState
  // Always returns a new state object — never mutates

  readonly setFilter = this.updater((state, filter: string) => ({
    ...state,
    filter,
    currentPage: 1, // Reset to page 1 when filter changes
  }));

  readonly setPage = this.updater((state, currentPage: number) => ({
    ...state,
    currentPage,
  }));

  readonly setLoading = this.updater((state, loading: boolean) => ({
    ...state,
    loading,
  }));

  // No payload needed — patchState works for simple flag flips too
  readonly clearError = this.updater(state => ({
    ...state,
    error: null,
  }));

  // ── EFFECTS ────────────────────────────────────────────────────────
  // effect() is like an NgRx Effect — receives Observable input,
  // performs side effects, calls updaters or patchState with results

  readonly loadUsers = this.effect((trigger$: Observable<void>) =>
    trigger$.pipe(
      // switchMap: cancel previous load if triggered again (search/refresh pattern)
      switchMap(() => {
        this.patchState({ loading: true, error: null });

        return this.userService.getUsers().pipe(
          // tapResponse is Component Store's safe response handler:
          // (successFn, errorFn) — always catches errors, never crashes the effect
          tapResponse(
            (users) => this.patchState({ users, loading: false }),
            (error: Error) => this.patchState({ error: error.message, loading: false })
          )
        );
      })
    )
  );

  readonly searchUsers = this.effect((query$: Observable<string>) =>
    query$.pipe(
      // switchMap cancels previous search (Topic 46 rule — correct for reads)
      switchMap((query) => {
        this.patchState({ loading: true });
        return this.userService.search(query).pipe(
          tapResponse(
            (users) => this.patchState({ users, loading: false }),
            (error: Error) => this.patchState({ error: error.message, loading: false })
          )
        );
      })
    )
  );
}
ts// data-table.component.ts
import { Component, OnInit, inject, ChangeDetectionStrategy } from '@angular/core';
import { AsyncPipe } from '@angular/common';
import { DataTableStore } from './data-table.store';

@Component({
  selector: 'app-data-table',
  changeDetection: ChangeDetectionStrategy.OnPush,
  // Key: provide the store in the component's providers array
  // This creates a NEW instance scoped to this component's lifetime
  // When the component is destroyed, the store is destroyed automatically
  providers: [DataTableStore],
  imports: [AsyncPipe],
  template: `
    @if (vm$ | async; as vm) {
      @if (vm.loading) { <p>Loading...</p> }
      @if (vm.error) { <p class="error">{{ vm.error }}</p> }

      <input
        (input)="onFilterChange($event)"
        placeholder="Search users..."
      />

      @for (user of vm.users; track user.id) {
        <div>{{ user.name }}</div>
      }

      <button (click)="prevPage(vm.currentPage)">Previous</button>
      <button (click)="nextPage(vm.currentPage)">Next</button>
    }
  `
})
export class DataTableComponent implements OnInit {
  // inject() — Component Store is in this component's injector (not root)
  private store = inject(DataTableStore);

  // Single subscription via view model selector (Topic 53 pattern)
  vm$ = this.store.vm$;

  ngOnInit() {
    // Trigger the effect by calling it with no argument (void trigger)
    this.store.loadUsers();
  }

  onFilterChange(event: Event) {
    const query = (event.target as HTMLInputElement).value;
    this.store.setFilter(query); // Calls updater directly — no action dispatch
  }

  prevPage(current: number) {
    if (current > 1) this.store.setPage(current - 1);
  }

  nextPage(current: number) {
    this.store.setPage(current + 1);
  }
}

Section 4 — Before & After Refactor
Before — Complex local state managed inside the component
ts// ❌ BEFORE — all state crammed into the component class
@Component({ ... })
export class DataTableComponent implements OnInit, OnDestroy {
  users: User[] = [];
  loading = false;
  error: string | null = null;
  filter = '';
  currentPage = 1;
  private destroy$ = new Subject<void>();

  constructor(private userService: UserService) {}

  ngOnInit() {
    // No separation of concerns — business logic inside component
    this.userService.getUsers()
      .pipe(takeUntil(this.destroy$))
      .subscribe({
        next: users => {
          this.users = users;
          this.loading = false;
        },
        error: err => {
          this.error = err.message;
          this.loading = false;
        }
      });
  }

  // Filter logic duplicated inline
  get filteredUsers() {
    return this.users.filter(u =>
      u.name.toLowerCase().includes(this.filter.toLowerCase())
    );
  }
  // filteredUsers recalculates on EVERY change detection cycle — no memoisation

  ngOnDestroy() {
    this.destroy$.next();
    this.destroy$.complete();
  }
}
What breaks:

State is scattered as individual class properties — no single source of truth, easy to get them out of sync
filteredUsers is a getter — recomputes on every CD cycle with no memoisation (Topic 45 anti-pattern)
Business logic (HTTP calls, filtering) lives inside the component — untestable in isolation
Manual Subject + takeUntil pattern for cleanup (Topic 20/21 boilerplate)
Cannot be shared with child components without prop drilling

After — Component Store
ts// ✅ AFTER
// Component: thin, only wires UI to store
// Store: owns all state, business logic, effects, selectors
// Testable independently, memoised, auto-cleaned up
@Component({
  providers: [DataTableStore], // Store scoped to component lifetime
  ...
})
export class DataTableComponent implements OnInit {
  private store = inject(DataTableStore);
  vm$ = this.store.vm$; // Single memoised subscription

  ngOnInit() { this.store.loadUsers(); }
  onFilter(query: string) { this.store.setFilter(query); }
}
Why this refactor matters in Angular:

The store is independently testable — inject it with a mock UserService and test updater() and effect() without any DOM
select() is memoised — filteredUsers$ only recomputes when users$ or filter$ emit
Cleanup is automatic — no Subject, no takeUntil, no ngOnDestroy
Child components can inject the same DataTableStore instance via the component injector hierarchy — no prop drilling


Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Providing Component Store in root instead of the component
What:
ts// ❌ Wrong
@Injectable({ providedIn: 'root' })
export class DataTableStore extends ComponentStore<DataTableState> { ... }
Why developers make it: It's the default Angular pattern for services — providedIn: 'root' makes things "just work" everywhere.
How to avoid it: Never use providedIn: 'root' on a Component Store. Always add it to the component's providers: [DataTableStore] array. The whole point of Component Store is that its lifetime is tied to the component's lifetime.
Angular-specific consequence: A root-provided Component Store is a singleton — it persists for the entire app session, its state accumulates across every component instance that has ever used it, and it never resets when the component is destroyed. Opening a data table modal twice shows stale state from the first open.

Mistake 2 — Mutating state directly inside updater()
What:
ts// ❌ Wrong — mutating state directly
readonly addUser = this.updater((state, user: User) => {
  state.users.push(user); // Direct mutation — same reference
  return state;           // Returns the same object reference
});
Why developers make it: push() works and the Angular template shows the correct values initially — it looks fine in development.
How to avoid it: Always return a new state object from updater(), exactly as you would in an NgRx reducer (Topic 51):
tsreadonly addUser = this.updater((state, user: User) => ({
  ...state,
  users: [...state.users, user] // New array reference
}));
Angular-specific consequence: Memoised select() derivations use referential equality — mutating and returning the same state object means select() never detects a change, Observables never emit, and the template silently displays stale data with OnPush.

Mistake 3 — Not using tapResponse inside effect() and letting errors crash the effect
What:
ts// ❌ Wrong — unhandled error kills the effect permanently
readonly loadUsers = this.effect((trigger$: Observable<void>) =>
  trigger$.pipe(
    switchMap(() =>
      this.userService.getUsers().pipe(
        tap(users => this.patchState({ users }))
        // No error handling — HTTP error will propagate to the outer stream
      )
    )
  )
);
Why developers make it: The same mistake as Topic 52's NgRx Effects catchError placement — it looks correct, and works fine in the happy path.
How to avoid it: Use tapResponse(successFn, errorFn) which is Component Store's built-in safe response handler, or manually add catchError inside the inner Observable. This is identical to the Topic 52 rule: catchError must be inside the inner Observable, not on the outer stream.
Angular-specific consequence: The first HTTP error permanently kills the loadUsers effect for the rest of the component's lifetime. Calling this.store.loadUsers() again silently does nothing — no error, no console warning. The component appears frozen.

Section 6 — Do's and Don'ts
✅ DO❌ DON'TProvide Component Store in the component's providers: [] array — ties lifetime to the componentUse providedIn: 'root' — creates a persistent singleton that never resets between component instancesUse tapResponse(successFn, errorFn) inside every effect() — it handles errors safely and keeps the effect aliveUse plain tap() with no error handling — an unhandled error permanently kills the effect with no warningReturn a new state object from every updater() — { ...state, changed }Mutate the state argument directly and return it — breaks select() memoisation silentlyUse the composed view model selector pattern (vm$) for a single template subscriptionSubscribe to each state slice separately — creates multiple subscriptions and multiple change detection triggers per state changeUse patchState() for partial updates when you don't need payload-based logicAlways use updater() for everything — patchState() is simpler and sufficient for flag flips and simple field updatesUse select() with multiple input selectors for computed/derived state — same memoisation as createSelectorDerive computed values in getters or template expressions — no memoisation, recomputes on every CD cycle

Section 7 — Debugging Tips
Bug 1 — Store state resets every time the component re-renders
Symptom: The data table loses its filter and pagination state every time the parent component triggers change detection.
Cause: The DataTableStore is being instantiated inside the component class directly (store = new DataTableStore()) instead of being injected via providers. Angular creates a new instance on every component initialization.
Fix:
ts// ❌ Wrong — new instance every time
store = new DataTableStore(this.userService);

// ✅ Correct — Angular manages lifecycle via injector
providers: [DataTableStore]
// Then: private store = inject(DataTableStore);
Angular-specific note: This is subtle because new DataTableStore() works and there's no error — it just creates an instance outside Angular's DI system, which means no lifecycle management, no automatic cleanup, and a new fresh state on every component creation.

Bug 2 — Child component cannot inject the parent's Component Store
Symptom: A child component tries to inject DataTableStore but gets NullInjectorError: No provider for DataTableStore.
Cause: The child component is trying to inject a store that is in the parent component's injector, but Angular's DI walks upward through the injector tree — the child must be a descendant of the component that provides the store, and the store must be in providers, not viewProviders.
Fix: Use providers: [DataTableStore] (not viewProviders) in the parent component. Child components in the template (and their descendants) can then inject it normally. Confirm the child is rendered inside the parent's template, not projected via <ng-content> from a grandparent.
Angular-specific note: Content-projected components (<ng-content>) use the projecting parent's injector, not the host component's injector — this is a common source of NullInjectorError with Component Store.

Bug 3 — effect() is called but nothing happens — no HTTP request fires
Symptom: You call this.store.loadUsers() in ngOnInit but no network request appears in DevTools and the loading state never changes.
Cause: The effect() method returns a function — calling this.store.loadUsers() calls that function which emits into the effect's internal Subject. But if the Component Store was not properly initialized (e.g. super(initialState) was omitted from the constructor), the internal streams are not set up and emissions are silently dropped.
Fix: Always call super(initialState) as the first line of the ComponentStore subclass constructor:
tsconstructor(private userService: UserService) {
  super(initialState); // Required — initializes internal BehaviorSubject
}
Angular-specific note: TypeScript will not warn you if super() is called without the initial state argument — it's a valid call. But Component Store's internal state stream is a BehaviorSubject — without an initial value it behaves unexpectedly.

Section 8 — Real-World Applications
Scenario 1 — Multi-step form wizard with per-step validation state
A checkout wizard has five steps. Each step has its own validation state, loading state (address lookup, payment processing), and the ability to navigate back without losing data.
ts// checkout-wizard.store.ts
interface WizardState {
  currentStep: number;
  stepData: {
    address: AddressForm | null;
    payment: PaymentForm | null;
    review: boolean;
  };
  stepErrors: Record<number, string | null>;
  submitting: boolean;
}

@Injectable()
export class CheckoutWizardStore extends ComponentStore<WizardState> {
  constructor(private checkoutService: CheckoutService) {
    super({
      currentStep: 1,
      stepData: { address: null, payment: null, review: false },
      stepErrors: {},
      submitting: false,
    });
  }

  // Updaters — step navigation
  readonly goToStep = this.updater((state, step: number) => ({
    ...state,
    currentStep: step,
  }));

  readonly saveStepData = this.updater(
    (state, payload: { step: keyof WizardState['stepData']; data: unknown }) => ({
      ...state,
      stepData: { ...state.stepData, [payload.step]: payload.data },
    })
  );

  // Selectors
  readonly currentStep$ = this.select(state => state.currentStep);
  readonly canGoBack$ = this.select(state => state.currentStep > 1);
  readonly vm$ = this.select(
    this.currentStep$,
    this.canGoBack$,
    this.select(state => state.submitting),
    (currentStep, canGoBack, submitting) => ({ currentStep, canGoBack, submitting })
  );

  // Effect — submit wizard
  readonly submitOrder = this.effect((trigger$: Observable<void>) =>
    trigger$.pipe(
      exhaustMap(() => { // exhaustMap: ignore duplicate submissions (Topic 52)
        this.patchState({ submitting: true });
        return this.checkoutService.submit(this.get(state => state.stepData)).pipe(
          tapResponse(
            () => { this.patchState({ submitting: false }); /* navigate to confirmation */ },
            (err: Error) => this.patchState({ submitting: false })
          )
        );
      })
    )
  );
}
When the wizard component is destroyed (user navigates away), the entire wizard state is automatically cleaned up — no lingering order data in the global store.

Scenario 2 — Infinite scroll list with independent state per widget
A dashboard shows multiple "activity feed" widgets — each widget fetches its own data independently with its own loading, error, and pagination state. The same ActivityFeedStore class powers all of them simultaneously with completely separate state.
ts// activity-feed.store.ts
@Injectable()
export class ActivityFeedStore extends ComponentStore<ActivityFeedState> {
  constructor(private feedService: FeedService) {
    super({ items: [], loading: false, page: 1, hasMore: true });
  }

  readonly loadNextPage = this.effect((trigger$: Observable<void>) =>
    trigger$.pipe(
      concatMap(() => { // concatMap: queue page loads — never skip a page
        const { page } = this.get();
        this.patchState({ loading: true });
        return this.feedService.getPage(page).pipe(
          tapResponse(
            ({ items, hasMore }) =>
              this.updater((state, result: { items: Item[]; hasMore: boolean }) => ({
                ...state,
                items: [...state.items, ...result.items], // Append
                page: state.page + 1,
                hasMore: result.hasMore,
                loading: false,
              }))({ items, hasMore }),
            () => this.patchState({ loading: false })
          )
        );
      })
    )
  );
}
ts// activity-feed.component.ts
@Component({
  providers: [ActivityFeedStore], // Each widget gets its OWN instance
  ...
})
export class ActivityFeedComponent { ... }
Three ActivityFeedComponent widgets on the same dashboard each get their own ActivityFeedStore instance — completely independent state, independent HTTP calls, independent page counters. This is impossible to achieve cleanly with a single global NgRx store slice without complex keying strategies.

Section 10 — Key Takeaways
Core concepts:

ComponentStore<T> is a self-contained reactive state service scoped to one component's lifetime — when the component is destroyed, the store is destroyed and all subscriptions are cleaned up automatically
updater((state, payload) => newState) is a mini-reducer — always return a new state object, never mutate the argument
select(projectorFn) creates a memoised Observable — identical referential equality rules to NgRx createSelector (Topic 53)
effect(trigger$ => Observable) is a local NgRx Effect — same switchMap/concatMap/exhaustMap rules apply (Topic 52)
tapResponse(successFn, errorFn) handles Observable responses safely — always use it instead of plain tap inside effects
patchState({ key: value }) is a simpler alternative to updater() for partial updates that don't need payload-based logic

Quick reference:
TaskAPI to useReplace or partially update state (no payload needed)patchState({ loading: true })Reusable state mutation with a typed payloadupdater((state, payload) => newState)Derive a value from state (memoised)select(state => ...) or select(slice1$, slice2$, projector)Perform a side effect (HTTP, navigation)effect(trigger$ => trigger$.pipe(...))Read current state snapshot synchronouslythis.get() or this.get(state => state.slice)
Angular-specific rules:

Always add Component Store to the component's providers: [] — never providedIn: 'root'
Always call super(initialState) in the constructor — omitting it leaves the internal BehaviorSubject uninitialized
Always use tapResponse inside effect() — unhandled errors permanently kill the effect with no warning
Never mutate state inside updater() — return a new object with spread
Use the view model selector (vm$) pattern for a single template subscription — same as Topic 53's recommendation for NgRx

One-Line Memory Aid:

Component Store is NgRx for one component — same updater/selector/effect patterns, but scoped to a single component's lifetime with no global boilerplate required.


Section 11 — Thought-Provoking Question + Answer
Question: If Component Store and a hand-rolled BehaviorSubject store service (from Topic 44) both solve local state management, what does Component Store actually add — and when is the simpler service the right choice?
Answer:
This is the right question to ask — Component Store is not always the answer.
What Component Store adds over a BehaviorSubject service:

updater() enforces pure-function mutation discipline — you cannot accidentally return the same reference, because the type system expects you to produce a new state object. A BehaviorSubject service lets you call .next(sameObject) with a mutation and it silently "works."
select() provides automatic memoisation — a BehaviorSubject's .asObservable() emits on every .next() call regardless of whether the projected value changed. select() uses distinctUntilChanged internally.
effect() manages inner Observable lifecycle — with a BehaviorSubject service you'd write switchMap, takeUntil, and catchError manually every time. effect() handles the inner subscription for you and applies the outer Subject's lifetime.
Automatic cleanup — a Component Store provided in providers: [] is destroyed with the component. A BehaviorSubject service requires manual takeUntilDestroyed() wiring.

When the simpler Topic 44 BehaviorSubject service is the right choice:

The state is one or two boolean flags — the overhead of extending ComponentStore is unnecessary
You need fine-grained control over subscription timing that Component Store's abstraction doesn't expose
The team is not already using NgRx — introducing @ngrx/component-store solely for one simple feature adds a new dependency

Practical rule: Use Component Store when the component has three or more interdependent state slices or at least one async side effect. Below that threshold, a simple signal or a lightweight BehaviorSubject service (Topic 44) is cleaner. Above that threshold, Component Store's discipline pays off significantly in maintainability and testability.

Section 14 — Common Interview Questions
Question 1
"What is NgRx Component Store and how does it differ from the global NgRx Store? When would you choose one over the other?"
Strong answer covers:

Global Store: app-wide lifetime, accessed anywhere, requires actions/reducers/effects wiring, full DevTools support
Component Store: component lifetime, scoped to injector subtree, no action ceremony, simpler API
Choose global store for: data shared across features, data that must survive navigation, data needed by unrelated parts of the app
Choose Component Store for: UI state local to one feature (pagination, filters, loading), wizard state, per-widget independent state
The key question: "Does anything outside this component need this state?" — if no, Component Store

Weak answers miss: The lifetime scoping argument — most candidates explain the API difference but not the lifecycle/ownership distinction.
Difficulty: Mid

Question 2
"What is tapResponse in NgRx Component Store and why should you use it instead of plain tap inside an effect()?"
Strong answer covers:

tapResponse(successFn, errorFn) is a safe response handler that catches errors inside the inner Observable
Plain tap() with no error handling: an HTTP error propagates to the outer effect stream and permanently kills it — same as the Topic 52 catchError placement rule
After the outer stream errors, calling the effect again silently does nothing — no error, no console warning
tapResponse ensures errors never reach the outer stream — the effect stays alive for the component's lifetime
Equivalent to: .pipe(tap(success), catchError(error => { handle; return EMPTY; }))

Weak answers miss: That the effect is permanently killed (not just skipped) when an unhandled error reaches the outer stream.
Difficulty: Mid

Question 3
"A developer provides their Component Store in providers: [] at the component level. A child component and a grandchild component both inject the same store. Explain exactly what each component gets and why — then describe the one scenario where this breaks."
Strong answer covers:

Angular's DI walks up the injector tree — child and grandchild components find the store in the parent component's injector and receive the same instance
This is by design — shared state between a parent and its children is a core Component Store use case
The scenario where it breaks: content projection — a component projected via <ng-content> uses its declaring parent's injector, not the host component's injector
So <app-parent><app-child /></app-parent> where app-child is projected gets its store from app-child's declaring context, not from app-parent — NullInjectorError if app-parent is the only provider
Fix: also provide the store in app-child's providers, or restructure to avoid cross-injector projection

Weak answers miss: The content projection (<ng-content>) edge case — most candidates understand the parent-child DI inheritance but not the projection injector boundary.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Using this.get() inside updater() to read current state
ts// ❌ Anti-pattern
readonly incrementByDouble = this.updater((state) => {
  const currentCount = this.get(s => s.count); // Reading state again inside updater
  return { ...state, count: currentCount * 2 };
});
Why it seems fine: It works — this.get() returns the current state synchronously, and the math is correct.
What breaks in production: updater() already receives the current state as its first argument — it is the current state snapshot at the moment the updater runs. Calling this.get() inside an updater introduces a race condition in concurrent update scenarios: if two updaters fire in quick succession, this.get() may return a state that is one step behind the state argument the NgRx internals already computed.
Correct pattern:
ts// ✅ Always use the state argument — never this.get() inside updater()
readonly incrementByDouble = this.updater((state) => ({
  ...state,
  count: state.count * 2  // Use the provided state argument
}));

Anti-Pattern 2 — Creating a new effect() call inside a method instead of as a class property
ts// ❌ Anti-pattern
@Injectable()
export class DataStore extends ComponentStore<DataState> {
  loadData(id: string) {
    // New effect created on every call — never cleaned up
    this.effect((trigger$: Observable<string>) =>
      trigger$.pipe(switchMap(id => this.service.load(id).pipe(...)))
    )(id);
  }
}
Why it seems fine: The effect fires correctly on the first call and data loads as expected.
What breaks in production: Every call to loadData() creates a brand new effect — a new internal Subject, a new subscription chain. These accumulate for the component's lifetime. A component that calls loadData() on every row click of a table leaks a new subscription chain on every click, all active simultaneously, all making HTTP calls. Memory and network usage grow linearly with user interactions.
Correct pattern:
ts// ✅ Define effect once as a class property — call it with new values
@Injectable()
export class DataStore extends ComponentStore<DataState> {
  // Created once — reused for every call
  readonly loadData = this.effect((id$: Observable<string>) =>
    id$.pipe(switchMap(id => this.service.load(id).pipe(...)))
  );
}
// In component: this.store.loadData(id) — triggers the existing effect

Anti-Pattern 3 — Sharing Component Store state between unrelated components via a parent provider
ts// ❌ Anti-pattern — using Component Store as an improvised global store
// app.component.ts
@Component({
  providers: [SharedDataStore], // Provided at root component level
  ...
})
export class AppComponent { }

// unrelated-feature-a.component.ts
export class FeatureAComponent {
  store = inject(SharedDataStore); // Reaches AppComponent's injector
}

// unrelated-feature-b.component.ts
export class FeatureBComponent {
  store = inject(SharedDataStore); // Same instance
}
Why it seems fine: It works — both components share state because they both reach the same AppComponent injector. No global NgRx boilerplate needed.
What breaks in production: You've created an informal global store with none of the DevTools support, action logging, or immutability enforcement of NgRx global store — and with the misleading mental model that this state is "local." The store persists for the entire app session, accumulates state from all features, and has no clear ownership or lifecycle. As the app grows, this becomes an unauditable state sink. There's no way to replay state changes, no action history, and no clear point of responsibility when state becomes inconsistent.
Correct pattern:
ts// ✅ Rule: if state is needed by unrelated features, it belongs in the global NgRx store
// Use Component Store ONLY for state that lives and dies with one feature component

// Global NgRx store for shared state (Topic 51)
provideState('sharedData', sharedDataReducer)

// Component Store for local feature state
@Component({ providers: [LocalFeatureStore] })
export class FeatureComponent { }

Section 16 — Mental Model Summary
Core concept in one sentence:

NgRx Component Store is a self-contained, component-scoped reactive state manager — the same updater/selector/effect discipline as NgRx, but with no global registration, no actions, and automatic cleanup when the component is destroyed.
Key rules:

Always provide Component Store in the component's providers: [] array — never providedIn: 'root'
Always call super(initialState) as the first line of the constructor — it initializes the internal BehaviorSubject
Always use tapResponse(successFn, errorFn) inside every effect() — unhandled errors permanently kill the effect silently
Always return a new state object from updater() — never mutate the state argument
Define effects as class properties (called once) — never create effects dynamically inside methods
Use Component Store when state has 3+ interdependent slices or async side effects; use plain signals or a BehaviorSubject service below that threshold

The single most important Angular rule:

Always use tapResponse inside every effect() — one unhandled HTTP error permanently kills the effect for the component's lifetime with no warning and no recovery.
