Topic 57 — NgRx Router Store

Section 0 — Difficulty & Priority Rating
Difficulty: Intermediate — Router Store introduces one new concept (connecting the Angular Router to NgRx) but relies entirely on patterns you already know: selectors, effects, and the global store. The new API surface is small; the value is architectural.
Angular Relevance: High — In any NgRx application where components read route params, query params, or the current URL to drive data loading, Router Store eliminates the direct ActivatedRoute injection inside components and makes the URL a first-class, selectable, testable slice of your NgRx state.

Section 1 — Explanation
The GPS Tracker Analogy
Imagine a logistics company. Every truck has a GPS unit broadcasting its position. Without a central system, each warehouse manager calls the driver directly to ask "where are you?" — direct, coupled, hard to monitor or replay.
With a central dispatch system, every GPS update is logged to a shared board. Any manager reads the board. The operations team can replay the route history. No one calls the driver directly.
NgRx Router Store is the dispatch system for your URL.
Without it: components inject ActivatedRoute directly and ask the router "where am I?" — direct, coupled, hard to test, impossible to replay in DevTools.
With it: every navigation event is dispatched as an NgRx action and the current router state (URL, params, query params, fragment) is stored as a slice of your NgRx state. Components and effects read it through selectors, just like any other state. DevTools can replay navigation. Tests can dispatch a fake router state.
Technically:
@ngrx/router-store provides:

A StoreRouterConnectingModule (or provideRouterStore()) that listens to Angular Router events and dispatches NgRx actions on every navigation
A routerReducer that stores the serialized router state in the NgRx store under a configurable key
A RouterSelectors API (selectUrl, selectQueryParams, selectRouteParams, selectRouteData) for reading router state via memoised selectors
Router actions (routerNavigationAction, routerNavigatedAction, routerCancelAction, routerErrorAction) that Effects can listen to

Quick Reference — Router Store Navigation Actions
ActionWhen it firesrouterRequestActionNavigation starts (before guards run)routerNavigationActionGuards passed — navigation is committingrouterNavigatedActionNavigation fully complete — component activatedrouterCancelActionA guard cancelled the navigationrouterErrorActionNavigation threw an error

Section 2 — Connection to Prior Concepts
Directly builds on:

Topic 38 — Angular Router: Router Store wraps the Angular Router's event system — you need to understand ActivatedRoute, route params, query params, and navigation events to know what Router Store is exposing to NgRx.
Topic 51 — NgRx Core Concepts: Router state is stored as a reducer slice in the NgRx store — the same createFeatureSelector and createSelector pattern from Topic 51 applies to reading it.
Topic 52 — NgRx Effects: The most powerful Router Store pattern is Effects that listen to routerNavigationAction and dispatch HTTP load actions — replacing the ActivatedRoute + switchMap pattern from Topic 38 with a fully NgRx-managed data loading pipeline.
Topic 53 — NgRx Selectors In Depth: Router Store provides built-in selectors, but composing your own feature selectors on top of them follows the exact layered selector pattern from Topic 53.
Topic 39 — Route Guards: Router Store's routerCancelAction fires when a guard blocks navigation — Effects can react to cancellations for analytics or UX feedback.

The single topic it extends most directly: Topic 38 — Angular Router.
Router Store is the bridge between the Angular Router (Topic 38) and the NgRx Store (Topic 51). It makes the URL a first-class NgRx state slice, replacing direct ActivatedRoute injection with selector-based router state access.
Bridging note: In Topic 38 you used route.paramMap.pipe(switchMap(...), takeUntilDestroyed()) to react to route param changes inside a component. Router Store moves that reaction into an Effect: the Effect listens to routerNavigationAction, extracts the param from the store via a selector, and dispatches a load action — the component never touches ActivatedRoute at all.

Section 3 — Code Example
Setup — registering Router Store
ts// app.config.ts
import { provideStore, provideState } from '@ngrx/store';
import { provideRouterStore, routerReducer } from '@ngrx/router-store';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideStore({
      // Register routerReducer under the 'router' key
      // This is where Router Store writes serialized navigation state
      router: routerReducer,
    }),
    // Connect Angular Router events to NgRx — dispatches router actions automatically
    provideRouterStore(),
  ],
};

Effect that reacts to navigation — the core Router Store pattern
ts// user.effects.ts
import { inject, Injectable } from '@angular/core';
import { Actions, createEffect, ofType } from '@ngrx/effects';
import { Store } from '@ngrx/store';
import { routerNavigatedAction } from '@ngrx/router-store';
import { switchMap, map, filter, withLatestFrom } from 'rxjs/operators';
import { catchError, of } from 'rxjs';
import { selectUserId } from './router.selectors';
import { UserService } from './user.service';
import { UsersApiActions } from './user.actions';

@Injectable()
export class UserEffects {
  private actions$ = inject(Actions);
  private store = inject(Store);
  private userService = inject(UserService);

  // Pattern: load data when the user navigates to a detail route
  // Instead of ActivatedRoute in the component, the Effect listens to routerNavigatedAction
  loadUserOnNavigation$ = createEffect(() =>
    this.actions$.pipe(
      // Fire only when navigation completes — component is now active
      ofType(routerNavigatedAction),

      // Read the current route params from the store via selector
      withLatestFrom(this.store.select(selectUserId)),

      // Filter out navigations that don't have a user ID in the route
      // (e.g. navigating to /users list vs /users/:id detail)
      filter(([, userId]) => userId !== undefined),

      // switchMap: cancel previous load if user navigates to a different user
      // before the previous HTTP call completed (Topic 46 / Topic 52 rules)
      switchMap(([, userId]) =>
        this.userService.getById(userId!).pipe(
          map(user => UsersApiActions.userLoaded({ user })),
          catchError(error =>
            of(UsersApiActions.usersLoadFailed({ error: error.message }))
          )
        )
      )
    )
  );
}
Component — reads route-derived state from the store, never from ActivatedRoute
ts// user-detail.component.ts
import { Component, inject, ChangeDetectionStrategy } from '@angular/core';
import { Store } from '@ngrx/store';
import { selectCurrentUser, selectUserId } from './router.selectors';
import { selectLoading } from './user.reducer';

@Component({
  selector: 'app-user-detail',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    @if (loading()) {
      <p>Loading...</p>
    } @else if (user()) {
      <h1>{{ user()!.name }}</h1>
      <p>{{ user()!.email }}</p>
    } @else {
      <p>User not found</p>
    }
  `
})
export class UserDetailComponent {
  private store = inject(Store);

  // Reads from NgRx store — no ActivatedRoute injection
  // selectCurrentUser combines router params + entity state (cross-slice selector)
  user = this.store.selectSignal(selectCurrentUser);
  loading = this.store.selectSignal(selectLoading);

  // No ngOnInit — the Effect handles loading when navigation completes
  // No takeUntilDestroyed — no direct subscriptions in this component
}
Custom Router State Serializer (optional but recommended)
By default, Router Store serializes the entire Angular RouterStateSnapshot — a large object that includes component references and can cause issues with Redux DevTools serialization. A custom serializer extracts only the fields you need:
ts// custom-route-serializer.ts
import { RouterStateSnapshot, Params } from '@angular/router';
import { RouterStateSerializer } from '@ngrx/router-store';

export interface CustomRouterState {
  url: string;
  params: Params;
  queryParams: Params;
  data: Record<string, unknown>;
}

export class CustomRouterStateSerializer
  implements RouterStateSerializer<CustomRouterState>
{
  serialize(routerState: RouterStateSnapshot): CustomRouterState {
    let route = routerState.root;
    // Walk down to the deepest activated route to get leaf params
    while (route.firstChild) {
      route = route.firstChild;
    }
    return {
      url: routerState.url,
      params: route.params,
      queryParams: routerState.root.queryParams,
      data: route.data as Record<string, unknown>,
    };
  }
}
ts// Register the custom serializer in app.config.ts
provideRouterStore({
  serializer: CustomRouterStateSerializer,
})

Section 4 — Before & After Refactor
Before — Direct ActivatedRoute injection in the component
ts// ❌ BEFORE — component is coupled to the router directly
@Component({ ... })
export class UserDetailComponent implements OnInit {
  private route = inject(ActivatedRoute);
  private userService = inject(UserService);
  private destroyRef = inject(DestroyRef);

  user: User | null = null;
  loading = false;

  ngOnInit() {
    // Topic 38 pattern — direct route param subscription in the component
    this.route.paramMap.pipe(
      switchMap(params => {
        const id = params.get('id')!;
        this.loading = true;
        return this.userService.getById(id);
      }),
      takeUntilDestroyed(this.destroyRef)
    ).subscribe({
      next: user => { this.user = user; this.loading = false; },
      error: err => { this.loading = false; }
    });
  }
}
What breaks with this approach:

The component owns HTTP logic — cannot be tested without a real router and real HTTP
State (user, loading) is local to the component — other components cannot access "the currently viewed user" without re-fetching
Redux DevTools cannot show "user was loaded because we navigated to /users/42"
If two components need the same current user, both subscribe to ActivatedRoute separately — two HTTP calls

After — Router Store + Effect pattern
ts// ✅ AFTER

// Effect handles all loading logic triggered by navigation
// (shown in Section 3 above — loadUserOnNavigation$)

// Component is completely clean — just reads from the store
@Component({ ... })
export class UserDetailComponent {
  private store = inject(Store);

  user = this.store.selectSignal(selectCurrentUser);  // Cross-slice selector
  loading = this.store.selectSignal(selectLoading);
  // No ActivatedRoute, no HTTP, no subscriptions, no ngOnInit
}
Why this refactor matters in Angular:

The component is now a pure view — it reads signals and renders. Testable with just a mock store.
The loaded user is in the global store — any other component can select it without a second HTTP call
DevTools shows the full chain: [Router] Navigation, [Users API] User Loaded — full audit trail
The Effect handles cancellation automatically via switchMap — navigating away mid-load cancels the request


Section 5 — Common Mistakes & Misconceptions
Mistake 1 — Forgetting to register routerReducer and getting undefined router state
What:
ts// ❌ Wrong — provideRouterStore() without routerReducer in the store
provideStore({ users: usersReducer }), // No router key
provideRouterStore(),                  // Connected but has nowhere to write state
Why developers make it: provideRouterStore() sounds complete — "I've provided the router store." But it only connects the Angular Router events to NgRx; the actual state needs a reducer slot.
How to avoid it: Always register routerReducer in your store config under a key (convention is 'router'), and pass that same key to getRouterSelectors().
Angular-specific consequence: All router selectors return undefined silently. Effects listening to routerNavigationAction fire correctly (actions are dispatched regardless), but any withLatestFrom(store.select(selectRouteParams)) returns undefined — causing effects to produce malformed actions with no error.

Mistake 2 — Using routerNavigationAction when you need routerNavigatedAction
What:
ts// ❌ Using the wrong action — fires before the component is activated
ofType(routerNavigationAction), // Guards haven't run yet — component not mounted
switchMap(([, userId]) => this.userService.getById(userId!).pipe(...))
Why developers make it: "Navigation action" sounds like "navigation happened" — but routerNavigationAction fires when navigation is committing (guards have passed but the component hasn't activated yet). routerNavigatedAction fires when navigation is complete.
How to avoid it: Use routerNavigatedAction for data loading triggered by navigation — the component is guaranteed to be active and the route params reflect the new route. Use routerNavigationAction only if you need to act before the component mounts (e.g. pre-fetching in an effect that runs ahead of the view).
Angular-specific consequence: If a Resolver or guard delays navigation, routerNavigationAction may fire before the final route is confirmed — loading data for a route the user never reaches.

Mistake 3 — Not using a custom serializer and hitting Redux DevTools serialization errors
What:
ts// ❌ No custom serializer — uses Angular's full RouterStateSnapshot
provideRouterStore() // Default serializer stores the entire snapshot
Why developers make it: The default works for basic usage and requires no extra setup.
How to avoid it: Always register a custom RouterStateSerializer that extracts only url, params, queryParams, and data. The full RouterStateSnapshot contains component class references and injector instances that cannot be JSON-serialized, causing Redux DevTools to display errors or crash when replaying state.
Angular-specific consequence: Redux DevTools time-travel fails with "Cannot serialize router state" errors. In production, strictStateSerializability: true (NgRx runtime check) throws on every navigation and crashes the app.

Section 7 — Debugging Tips
Bug 1 — All router selectors return undefined
Symptom: store.select(selectUrl) returns undefined. Effects using withLatestFrom(store.select(selectRouteParams)) produce [action, undefined].
Cause: Either routerReducer was not registered in provideStore(), or the key passed to getRouterSelectors() doesn't match the key used in provideStore().
Fix:
ts// Step 1: Register with a consistent key
provideStore({ router: routerReducer })

// Step 2: Use the same key in getRouterSelectors
const { selectUrl } = getRouterSelectors(); // Defaults to 'router' key
// If you used a different key:
const { selectUrl } = getRouterSelectors(selectCustomRouterState);
// where selectCustomRouterState = createFeatureSelector('myRouterKey')
Angular-specific note: Open Redux DevTools and look for the router key in your state tree. If it's absent, routerReducer is not registered. If it's present but empty, the serializer is returning undefined.

Bug 2 — Effect fires on every navigation, not just the target route
Symptom: Your loadUserOnNavigation$ Effect fires when navigating to /settings, /home, and /users/:id — not just the user detail route.
Cause: ofType(routerNavigatedAction) matches every navigation. Without filtering by URL pattern or param presence, the Effect runs unconditionally.
Fix: Add a filter() operator that checks the route params or URL before proceeding:
tsofType(routerNavigatedAction),
withLatestFrom(this.store.select(selectUserId)),
// Only proceed if the current route has a userId param
filter(([, userId]) => userId !== undefined),
switchMap(([, userId]) => ...)
Or use selectUrl to check the URL pattern:
tswithLatestFrom(this.store.select(selectUrl)),
filter(([, url]) => url.startsWith('/users/')),
Angular-specific note: This is the most common Router Store production bug — the effect silently fires on every navigation and makes unnecessary HTTP calls with undefined params.

Bug 3 — routerNavigatedAction fires but selectRouteParams returns previous route's params
Symptom: You navigate from /users/42 to /users/99. The effect fires, but selectRouteParams still returns { id: '42' }.
Cause: withLatestFrom reads the store at the moment of the outer emission — which is the routerNavigatedAction. Occasionally, the router reducer hasn't processed its own action yet when withLatestFrom reads.
Fix: Use concatLatestFrom from @ngrx/effects instead of withLatestFrom — it reads the store after the action has been fully reduced:
tsimport { concatLatestFrom } from '@ngrx/effects';

ofType(routerNavigatedAction),
// concatLatestFrom reads state AFTER the action is reduced
concatLatestFrom(() => this.store.select(selectUserId)),
filter(([, userId]) => userId !== undefined),
switchMap(([, userId]) => ...)
Angular-specific note: This is a subtle timing issue specific to effects that react to the action that also updates the state they read. concatLatestFrom is the NgRx-provided solution — prefer it over withLatestFrom in Router Store effects specifically.

Section 8 — Real-World Applications
Scenario 1 — Master-detail navigation with shared entity state
A CRM app has a contacts list (/contacts) and a contact detail view (/contacts/:id). When the user clicks a contact, the app navigates and loads the contact's full data. Both the list and detail view share the same NgRx entity state (Topic 54).
ts// contact.effects.ts
loadContactOnNavigation$ = createEffect(() =>
  this.actions$.pipe(
    ofType(routerNavigatedAction),
    concatLatestFrom(() => this.store.select(selectContactId)),
    // Only fire for the detail route (has a contactId)
    filter(([, contactId]) => contactId !== undefined),
    // switchMap: navigating quickly between contacts cancels previous loads
    switchMap(([, contactId]) => {
      // Check if already in store — avoid re-fetching (Topic 54 Entity pattern)
      const existing = this.store.selectSignal(
        createSelector(selectContactEntities, e => e[contactId!])
      )();
      if (existing) return of(ContactsApiActions.contactAlreadyCached());

      return this.contactService.getById(contactId!).pipe(
        map(contact => ContactsApiActions.contactLoaded({ contact })),
        catchError(err => of(ContactsApiActions.contactLoadFailed({ error: err.message })))
      );
    })
  )
);
ts// contact-detail.component.ts — no ActivatedRoute, no HTTP
@Component({ changeDetection: ChangeDetectionStrategy.OnPush, ... })
export class ContactDetailComponent {
  private store = inject(Store);
  contact = this.store.selectSignal(selectCurrentContact); // Cross-slice
  loading = this.store.selectSignal(selectContactLoading);
}
The list component can select the same contact entity without a second HTTP call — the entity is already in the store from when the detail loaded it.

Scenario 2 — URL-driven filter and pagination state
A products page at /products?category=shoes&page=3&sort=price keeps all filter state in the URL — shareable links, browser back/forward, and refresh all restore the exact view.
ts// product.selectors.ts
const { selectQueryParams } = getRouterSelectors();

export const selectProductFilters = createSelector(
  selectQueryParams,
  (params) => ({
    category: (params['category'] as string) ?? 'all',
    page: Number(params['page'] ?? '1'),
    sort: (params['sort'] as string) ?? 'name',
  })
);

// Cross-slice: combine URL filters with loaded products
export const selectFilteredProducts = createSelector(
  selectAllProducts,       // From NgRx Entity (Topic 54)
  selectProductFilters,    // From Router Store
  ({ category, sort }, products) =>
    products
      .filter(p => category === 'all' || p.category === category)
      .sort((a, b) => a[sort] > b[sort] ? 1 : -1)
);
ts// product.effects.ts — reload when URL filters change
loadProductsOnFilterChange$ = createEffect(() =>
  this.actions$.pipe(
    ofType(routerNavigatedAction),
    concatLatestFrom(() => this.store.select(selectProductFilters)),
    // Only reload if we're on the products route
    withLatestFrom(this.store.select(selectUrl)),
    filter(([[, ], url]) => url.startsWith('/products')),
    switchMap(([[, filters]]) =>
      this.productService.getFiltered(filters).pipe(
        map(products => ProductsApiActions.productsLoaded({ products })),
        catchError(err => of(ProductsApiActions.productsLoadFailed({ error: err.message })))
      )
    )
  )
);
ts// products.component.ts
@Component({ ... })
export class ProductsComponent {
  private store = inject(Store);
  private router = inject(Router);

  filters = this.store.selectSignal(selectProductFilters);
  products = this.store.selectSignal(selectFilteredProducts);

  // Changing filters updates the URL — Router Store picks it up automatically
  setCategory(category: string) {
    this.router.navigate([], {
      queryParams: { category, page: 1 },
      queryParamsHandling: 'merge'
    });
    // No store.dispatch() — the URL IS the state; Router Store syncs it
  }
}
This is the URL-as-source-of-truth pattern (Topic 38) combined with NgRx — the URL drives the store, the store drives the view, and the component only updates the URL.

Section 10 — Key Takeaways
Core concepts:

Router Store connects Angular Router navigation events to NgRx — every navigation dispatches an action and stores serialized route state in the NgRx store
routerReducer stores the router state; getRouterSelectors() reads it back as memoised selectors
The five router actions (routerRequestAction, routerNavigationAction, routerNavigatedAction, routerCancelAction, routerErrorAction) allow Effects to react to any phase of navigation
routerNavigatedAction is the correct trigger for data loading — navigation and component activation are both complete
A custom RouterStateSerializer is required in any production app to prevent DevTools serialization errors
concatLatestFrom (not withLatestFrom) is the safe way to read router state inside an Effect reacting to a router action

Section 11 — Thought-Provoking Question + Answer
Question: If the URL already contains all filter and param information, and Angular's ActivatedRoute makes it accessible inside any component, what does Router Store actually add — isn't it redundant complexity?
Answer:
This is the most common objection to Router Store, and it deserves a direct answer.
ActivatedRoute is sufficient when:

Components are self-contained and own their own data loading
State doesn't need to be shared between components
Testing the component doesn't require precise control over route state
You aren't using NgRx globally

Router Store becomes genuinely valuable — not just stylistically — in four specific situations:
1. Cross-slice selectors. When you need to combine route state with entity state (selectCurrentUser = combine(selectUserEntities, selectUserId)), you need both slices in the same NgRx selector. ActivatedRoute is not accessible inside a createSelector call — it requires a component-level subscription. Router Store makes route params first-class NgRx state, enabling cross-slice composition that ActivatedRoute cannot support.
2. Effects as data-loading orchestrators. In a fully NgRx app, components should not own HTTP logic (Topic 52 discipline). Moving data loading to Effects requires a trigger — and routerNavigatedAction is that trigger. Without Router Store, Effects have no clean way to know which route is active without subscribing to ActivatedRoute themselves, which defeats the purpose.
3. DevTools and time-travel debugging. When a user reports a bug on /users/42, Redux DevTools can replay the exact sequence: navigation action → data load action → state mutation → UI render. Without Router Store, the navigation is invisible to DevTools — you see only the data load, losing the "why was this loaded" context.
4. Testing. Testing a component that injects ActivatedRoute requires RouterTestingModule with carefully configured routes. Testing a component that reads from the NgRx store requires only a MockStore with a preset state — one line to set selectCurrentUser to any value, no router setup.
Practical rule: In apps that are partially NgRx (some state global, some local), ActivatedRoute in components is fine. In fully NgRx apps where Effects own all data loading, Router Store is not redundant — it's the missing piece that makes Effects the single data-loading entry point.

Section 14 — Common Interview Questions
Question 1
"What is NgRx Router Store, what problem does it solve, and how do you set it up?"
Strong answer covers:

Problem: ActivatedRoute in components creates a dual source of truth alongside NgRx state; Effects have no clean way to react to navigation; route state is invisible to DevTools
Solution: Router Store dispatches navigation as NgRx actions and stores route state (url, params, queryParams) as a selectable NgRx slice
Setup: provideStore({ router: routerReducer }) + provideRouterStore() + custom RouterStateSerializer
Selectors: getRouterSelectors() provides selectUrl, selectRouteParams, selectQueryParams, selectRouteData
Primary pattern: Effects listen to routerNavigatedAction + concatLatestFrom(selectRouteParam) to load data on navigation

Weak answers miss: The custom serializer requirement — most candidates describe setup without mentioning that the default serializer breaks DevTools serialization in production.
Difficulty: Mid

Question 2
"What's the difference between routerNavigationAction and routerNavigatedAction, and which should you use to trigger data loading in an Effect?"
Strong answer covers:

routerNavigationAction: fires when navigation is committing — guards have passed but the component hasn't activated yet
routerNavigatedAction: fires when navigation is fully complete — the new component is active and route params reflect the new route
For data loading: always use routerNavigatedAction — the component is mounted and params are finalized
routerNavigationAction use case: pre-fetching data before the component activates (rare, advanced pattern)
Practical risk: using routerNavigationAction loads data for routes that guards may still cancel

Weak answers miss: Why the distinction matters in practice — most candidates know the two actions exist but can't explain the guard-timing implication.
Difficulty: Mid

Question 3
"Why use concatLatestFrom instead of withLatestFrom when reading router state inside an Effect that reacts to a router action?"
Strong answer covers:

withLatestFrom reads the store at the moment the outer Observable emits — which is the routerNavigatedAction dispatch
The router reducer processes the same action to update the store — there's a timing window where the action has dispatched but the state hasn't been reduced yet
concatLatestFrom defers the state read until after the action has been fully reduced — guaranteed to reflect the new route
Practical symptom without concatLatestFrom: navigating from /users/42 to /users/99, the effect reads id: '42' from the store because the reducer hasn't run yet
concatLatestFrom is provided by @ngrx/effects specifically to solve this timing issue

Weak answers miss: The root cause — most candidates know to use concatLatestFrom as a rule but cannot explain the action-reduction timing race that makes it necessary.
Difficulty: Senior

Section 15 — Anti-Patterns to Avoid in Production
Anti-Pattern 1 — Using the default Router State Serializer in production
ts// ❌ Anti-pattern — no custom serializer
provideRouterStore() // Uses DefaultRouterStateSerializer
Why it seems fine: Everything works in development. The router state appears in DevTools and selectors return values correctly.
What breaks in production: The DefaultRouterStateSerializer stores the full Angular RouterStateSnapshot, which contains component class references, injector instances, and circular references. With strictStateSerializability: true (recommended for production NgRx), the app throws on every navigation. Without the check, Redux DevTools silently fails to serialize the state for time-travel, and any state persistence layer (e.g. ngrx-store-localstorage) corrupts its storage on the first navigation.
Correct pattern:
ts// ✅ Always register a custom serializer
provideRouterStore({ serializer: CustomRouterStateSerializer })
// CustomRouterStateSerializer extracts only: url, params, queryParams, data

Anti-Pattern 2 — Mixing ActivatedRoute and Router Store in the same component
ts// ❌ Anti-pattern — two sources of truth for route state
@Component({ ... })
export class UserDetailComponent implements OnInit {
  private route = inject(ActivatedRoute);      // Direct router access
  private store = inject(Store);               // NgRx store access

  user = this.store.selectSignal(selectCurrentUser); // Reads from store

  ngOnInit() {
    // Also reads route params directly — bypassing the store
    this.route.params.subscribe(params => {
      this.store.dispatch(UsersPageActions.userSelected({ id: params['id'] }));
    });
  }
}
Why it seems fine: The component works correctly. The ActivatedRoute subscription and the store selector both reflect the same route — they agree.
What breaks in production: Two systems now own the same information. If the Router Store serializer's timing differs from ActivatedRoute.params (which it can on complex navigation sequences), the component sees inconsistent state. Testing requires both RouterTestingModule and MockStore. And as the codebase grows, other developers cannot tell which source is authoritative — half the team uses ActivatedRoute directly, half uses Router Store selectors, and the codebase becomes inconsistent.
Correct pattern:
ts// ✅ Router Store is the single source of truth for route state
@Component({ ... })
export class UserDetailComponent {
  store = inject(Store);
  user = this.store.selectSignal(selectCurrentUser);
  // No ActivatedRoute, no ngOnInit, no manual dispatch
  // Effect handles dispatch on routerNavigatedAction
}

Anti-Pattern 3 — Dispatching a load action from a component on navigation instead of using an Effect
ts// ❌ Anti-pattern — component reacts to route changes and dispatches
@Component({ ... })
export class UserDetailComponent implements OnInit {
  private store = inject(Store);
  private route = inject(ActivatedRoute);

  ngOnInit() {
    this.route.paramMap.pipe(
      map(p => p.get('id')!),
      takeUntilDestroyed(this.destroyRef)
    ).subscribe(id => {
      // Component dispatching based on route changes
      this.store.dispatch(UsersPageActions.userDetailOpened({ id }));
    });
  }
}
Why it seems fine: This is a common and functional pattern — the component observes the route and tells the store what happened. It follows the "components dispatch actions" principle.
What breaks in production: The component now owns route-observation logic, making it harder to test (requires RouterTestingModule), harder to move to a different route structure, and impossible to pre-fetch (the component must be mounted before the dispatch fires). If two components on the same page both need to dispatch on navigation, both must independently subscribe to ActivatedRoute. The Effect-based pattern centralises all navigation reactions in one place.
Correct pattern:
ts// ✅ Effect reacts to navigation — component is a pure view
loadUserOnNavigation$ = createEffect(() =>
  this.actions$.pipe(
    ofType(routerNavigatedAction),
    concatLatestFrom(() => this.store.select(selectUserId)),
    filter(([, id]) => id !== undefined),
    switchMap(([, id]) =>
      this.userService.getById(id!).pipe(
        map(user => UsersApiActions.userLoaded({ user })),
        catchError(err => of(UsersApiActions.usersLoadFailed({ error: err.message })))
      )
    )
  )
);
// Component: inject Store, read selectCurrentUser — nothing else

Section 16 — Mental Model Summary
Core concept in one sentence:

NgRx Router Store logs every Angular navigation as an NgRx action and stores the current route state (url, params, queryParams) as a selectable NgRx slice — making the URL a first-class member of your application state that Effects can react to and components can read without touching ActivatedRoute.
Key rules:

Always register routerReducer in provideStore({ router: routerReducer }) alongside provideRouterStore() — one without the other leaves selectors returning undefined
Always write a custom RouterStateSerializer — the default stores un-serializable Angular objects that break DevTools and production serialization checks
Use routerNavigatedAction for data-loading Effects — navigation and component activation are both complete at this point
Use concatLatestFrom (not withLatestFrom) to read router state inside Effects triggered by router actions — avoids the action-reduction timing race
Never inject ActivatedRoute in components that use NgRx — Router Store selectors are the single source of truth
Compose typed selectors on top of getRouterSelectors() — extract and type-cast params once, reuse everywhere

The single most important Angular rule:

Always write a custom RouterStateSerializer — the default serializer stores Angular component references and injector instances that cannot be JSON-serialized, breaking Redux DevTools time-travel and any strictStateSerializability runtime check.
